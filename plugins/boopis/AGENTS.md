# AGENTS.md: plugins/boopis

The boopis Hermes plugin (Python, stdlib only at runtime). It adds governance, a ledger and the `plugin.boopis.*` RPC to **unmodified** Hermes (docs/ARCHITECTURE.md section 5). Read the root `AGENTS.md`, `docs/STANDARDS.md` and `docs/research/spike-s0.md` first.

## Invariants
- **Imports.** Relative inside the package (Hermes loads it as `hermes_plugins.boopis`). From Hermes, only what `hermes_cli/data/plugin_api.json` lists (`hermes_yaml`, `hermes_constants`), imported lazily inside the function that needs it. From contraprova, only the public modules: `events`, `log`, `projections`, `pricing`, `usage`, `interfaces`. **Never** copy its hash, canonical JSON or lock code.
- **Policy is one function.** `policy.check` serves the `pre_tool_call` hook and the exec kernel (`ctx.dispatch_tool` bypasses hooks). Do not add a second decision path.
- **Denied reads are a hard deny, first.** `policy/denied.py` applies `denied_read_paths` (`policy/defaults.json`: the host's secret socket, the old rendezvous file, hx's journal key; `//` absolute globs, matched by `rules.path_spec_matches` like `protected_extra`, case-insensitively) before anything else in `policy.check`, in both modes, ahead of an invalid config, `allow` rules and a hook's allow. It is never an ask. It covers every tool: the path arguments, any short single-line string argument read as a path (so an unknown tool's path argument is covered), command lines and code (`denied_read_script_keys`, word by word, following `cd`: best effort, the host's peer check is the boundary) and a mod's `fs.read`. `~`, environment variables, `file://`, `..` and symlinks are resolved first. **The filesystem is never walked.** A folder or glob is judged against the concrete locations (`denied_locations(home, root, env)`: the journal key and the old `host-channel.json` of this profile and of every `<root>/profiles/*`, and `BOOPIS_HOST_SECRETS_SOCKET`): a folder that is one or holds one is **refused, not filtered** (`search_files` and `pack` cannot exclude), and a glob is refused when its literal head holds one and it selects it. So a project at the Hermes root, or above it, cannot be searched. Known gap: a symlink inside a searched folder that points at a denied file is not seen; our tools do not follow it (`search_files` runs ripgrep without `-L`, `hx pack` refuses a symlink leaving the root), and a direct read of the link is caught by realpath. Contents, diffs and patterns (`denied_read_text_keys`) are never read as paths. A session adds globs through `SessionPolicy.denied_read` (matched against named paths only) and can never remove a default. The block is `reason: denied_read`, `rule: denied_read_paths`, and the `tool.called` carries both (`hooks.post_tool_call`), with a message that does not echo the path.
- **Patches are read with Hermes's grammar.** `policy/rules.py` `v4a_paths` copies `tools/patch_parser.py`'s markers (no space after `***`, any whitespace between words, both ends of `Move File: a -> b`) and reads every line, not only those between Begin and End; a `***` line that is not in the grammar makes the target unknowable, so the call is blocked. Bump it with Hermes.
- **Fail closed.** An exception in a policy hook or in `check` blocks. A config that fails validation allows read-only tools only. Observers log and swallow, and never invent a value.
- **Mode locks at the first prompt**, when Hermes renders the prompt section. After that `mode.set` raises `hx.mode.locked`.
- **Dollars are computed, never stored.** The ledger holds tokens. The cap value may be stored, spend never.
- **Arguments are hashed, never stored** (`tool.called.args_sha256`).
- **Project settings are trust-gated.** Untrusted: the gate command, timeout, `permissions.allow` and `data_policy` are ignored; `protected`, `permissions.deny` and `permissions.ask` still apply.
- **contraprova is vendored** (ADR-0015): `scripts/vendor-contraprova.sh <sha>` writes `_vendor/contraprova/` and `--check` (CI) re-fetches the commit and compares bytes. Import it relatively (`from .._vendor.contraprova.events import ...`). Its `gates` module imports siblings by absolute name, so `_vendor.load("gates")` aliases the copy first; use that for the gates.
- **Shared data is copied** (ADR-0016): `scripts/sync-shared-data.sh` (+ `--check`). The plugin's error codes live in `crates/hx-proto/errors.json`, not here.
- **hx types are generated**: `scripts/gen-hx-types.py` (+ `--check`) from `crates/hx-proto/schema/hx-v1.schema.json`. `hx/types.py` is excluded from ruff and never edited.
- **Only `ship` writes the workspace**, through `txn.validate` then `txn.apply` with the explicit effective `protected` list (shared defaults, the plugin's extras and the project's). A pass discards the journal and commits `refs/boopis/checkpoints/<session>`; a failure restores. The gate runs on a temp copy **inside the hx sandbox** (see "The gate's sandbox"); every `gate.decided` says how: `sandboxed`, `degraded:<dimensions>`, `unsandboxed:user_choice`, or `none` when no command ran.
- **No runtime dependencies.** `pyproject.toml` is tooling only and must not gain a `[project]` table (Hermes would treat the plugin as a package).
- RPC errors: Hermes turns an exception into `plugin_rpc_failed` with `detail` `"<Class>: hx.<code>: <message>"`. The code is first in `str(exc)` on purpose.

## Mods
- **Every `$` call is decided by `policy.check`** with `principal="mod:<plugin>"` and a capability (`policy/defaults.json`, `mod_capabilities`; the step is `policy/mods.py`). There is no second decision path, and a call missing from the table is refused. An `ask` is a `permission` form; closing it denies. Every call is a `tool.called` with the tool `mod:<plugin>/<call>` and hashed arguments.
- **A host call must not call `mods.*`.** The worker waits for the answer, so a handler that calls `mods.render` waits for the worker that waits for it. Redraws go through `ModService.invalidate`, which a draw thread serves.
- **Mods never loosen a decision.** In the bridge a mod can drop a prompt and deny or ask on a tool call; an `allow` is ignored; a rewrite is refused in governed mode and judged again otherwise; a `turn.step` model is refused in both. `fs.write` inside the workspace is refused in governed mode (only `ship` writes it).
- The hx client serves `mods.call`, `mods.diagnostic` and `mods.exited` (`HxClient.serve_peer`), each on its own thread. Mods are loaded at `on_session_start` (after the session is locked), unloaded at `on_session_finalize`.
- Mods run only if the plugin is enabled in Hermes and the content hash is approved (`mods/discovery.py`); `mod.install.*` copies, locks and approves (steps 5 and 6 of COMPAT section 9 are not built).

## Governed mode: the cascade
The orchestrator (the session model) has `pack` and `dispatch(brief)`; workers (delegated children) have `pack`, `exec` (when it exists) and `ship`. `policy.check` enforces that by role. **Governed mode has no `terminal`, for any role:** a command line cannot be proved read-only (the review found bypasses through `xargs`, `printf -v`, `sort --compress-program` and `file -C`), so the shell is `harness.sh` inside the kernel's sandbox. `policy.governed.command_is_read_only` stays as a strict, conservative definition for any other use (it refuses `$`, backticks, `xargs`, `printf -v` and the flags that make `sort`, `file`, `rg` and `find` write or run, abbreviated or not), but governed mode no longer asks it anything. Read-only Hermes tools are not a free pass either: `read_file` and `search_files` reach **only the workspace** (symlinks resolved; an unknown workspace refuses), and the URL-taking tools (`policy/defaults.json` `network_tools`: `web_search`, `web_extract`, `vision_analyze`, `video_analyze`, ...) are network tools: **a cell cannot call them while `exec.network` is not `on`** (the sandbox keeps the cell off the network, so the plugin must not lend it one), and in governed mode a direct call asks a human unless an allow rule names it. A session's governed toolset is fixed at `session.create` by the UI (`toolsets: ["boopis"]`, and a `mode.set` that fails closes the session): the policy is the guarantee, the toolset is defence in depth. Only a worker started by the plugin is a worker (a link made at `subagent_start`); never infer a role from `conversation_id` or `parent_session_id`, which an ordinary session has after its context is compressed.

**Frontier only (ADR-0037).** Governed mode runs only on frontier models: every ladder tier and the session's own model. `governance/frontier.py` reads `data/frontier-models.json` (a copy of `apps/shared/data/frontier-models.json`, kept by `scripts/sync-shared-data.sh`): families with a lowest version (Claude Opus 5.5, Claude Fable 5.2, GPT-6.2 Astra, GPT-6.2 Sol, Gemini 4 Carbon, Gemini 4 Neon, Gemini 4 Hydrogen, Grok 4.7), matched by family and version after normalising the id, never by a fixed id list. `ladder_problems` refuses a ladder with a tier that is not frontier (so `dispatch` and `describe` agree), `pre_llm_call` refuses a governed session whose own model is not, each in one sentence naming the model, why and the allowed families; an ungoverned session and the `@` mention are untouched. **Heavy models (`heavy: true` on a family: Claude Fable, Grok 4.7 and later; `frontier.is_heavy`).** A heavy model is frontier, so governed mode runs it, but nothing automatic puts it on a ladder: the default ladder (`ladder.DEFAULT_FRONTIER_LADDER`) is Opus alone on `anthropic`, not contraprova's haiku-first one, and the host's setup never writes one (a test holds the default free of heavy models). A ladder the user wrote that names one is accepted as the user's own specification. `describe.frontier` carries the list, the heavy ones, each tier's frontier and heavy flags and the session model's, which is what the UI reads. A new family is one entry in the data file and its `examples` (a `heavy: true` example for a heavy one).

Flow: `dispatch` refuses unless the ladder's providers exist in Hermes, `delegation.backend` is `boopis` and the project's trusted gate command exists (the brief's `test:` line is never used). It writes `task.created` (`max_attempts` from the ladder), then `launch` writes `route.decided` (propensity 1) and calls `ctx.dispatch_tool("delegate_task", ...)` with the orchestrator's agent as `parent_agent`. `delegation.route_task` reads the tier back from the ledger (the attempt's `route.decided`, the ladder in `session.opened`) and ignores everything else. The worker's `ship` ends at the gate and writes `gate.decided` for the task and tier; the policy then refuses a second `ship` in that attempt. A pure scope or protected block (the `T0.scope` gate, which hx can reach before writing) earns one same-tier retry (`TierLadder.next_index`); anything else climbs. The ledger is the state: `state.replay` rebuilds attempts, so there is no second copy to drift. A task that ends unsolved is closed with `task.closed` (`ladder_spent`, or `launch_failed` / `internal_error` when no gate decided), so the projection shows `failed` even before `max_attempts` (none is written when the last block already reached it). `outcome.scored` (labelled `source: project gate`, never a hidden score) and `cascade.updated` carry the end; a task that ended with no gate verdict gets no `outcome.scored`: nothing was scored. The brief is read by contraprova's own `contracts.parse_brief` (vendored).

**Mechanism chosen: (i), the plugin launches the next tier on the child's `subagent_stop`.** Reasons, all verified on real Hermes: the hook runs on the child's thread after its last tool call and before its result re-enters the orchestrator; the orchestrator's agent is still bound there (a context variable Hermes copies into the thread), so `delegate_task` works from it and runs in the background; the worker's verdict is already in the ledger. Nothing then depends on a model: a worker cannot claim success (the gate's verdict is read, not its report) and an orchestrator cannot give up or pick a tier. (ii), the orchestrator calling `dispatch` again, makes every escalation depend on the model remembering to. Noise: Hermes re-enters each child's completion as a turn. The completion of a blocked attempt, while the next tier already runs, is vetoed in `pre_llm_call` with a one-line status (no model call); the completion that ends the task carries the outcome as injected context (`lifecycle.turn_directive`), once. A completion that is not recognised (`ASYNC DELEGATION` in the message) is not vetoed: the model then gets a note and costs one turn.

Known limits: the delegation provider reads the attempt from a context variable, so it works in-process, not under `plugins.isolation: host`. `max_tokens` is recorded in the ladder but not applied: Hermes's delegation route has no such key. Forks are refused (`forks: true`).

## The gate's sandbox
- The gate's test command is code the agent may have written (`conftest.py`, a `package.json` script, a `Makefile`), so `ship/sandboxrun.py` runs it through `hx sandbox.run`: the **copy** of the post-apply tree is the only writable tree (plus a scratch directory for `HOME` and `TMPDIR`), `system_read` is on, the network is **off**, and the environment is `util.proc.safe_env()` with `HOME`/`TMPDIR` moved into the scratch. **The real workspace is not mounted at all** (Landlock cannot hide a file inside a directory it grants, so nothing of it is granted but the dependency directories below). **Never `dict(os.environ)`:** provider keys and the plugin's secret source must not reach it. contraprova's own runner (`_vendor/.../sandbox.py`, `run_command`) is not used.
- **The copy** (`ship/gatecopy.py`, names in `ship/gate.json`). Secret files are **left out**: `ship/secrets.py` reads the one shared never-pack list (`data/never_pack.json`, a copy of hx-pack's, synced by `scripts/sync-shared-data.sh`): `.env*` (except `.env.example` and the other templates), `*.pem`, `*.key`, `id_*` private keys, `.npmrc`, `.pypirc`, `.netrc`, credential files, `.ssh`, `.aws`, `.gnupg`, `.git`. The protected-path list is not the source (its other half, `tests/**`, is what the gate runs); a test checks the one list covers its secret globs. Dependency directories (`node_modules`, `vendor`, `__pypackages__`, a `.venv`/`venv` with a `pyvenv.cfg`) are **not copied**: each is a symlink in the copy to the real directory, and only that real directory is mounted read-only (`ro`). A dependency directory that is a symlink, or resolves outside the workspace, is refused. `target` beside a `Cargo.toml` is left out (cargo rebuilds it in the writable copy). Workspace symlinks are kept only when relative, inside the workspace and not at a secret. `.git` is provided read-only **only** with the project's `gate.git: true` (trusted project settings, default false: `.git/config` can hold a remote URL with a token); the output is redacted either way. A project's `.venv/bin` and `node_modules/.bin` come first in the child's `PATH`. Not covered: secret-pattern files that live *inside* a dependency directory are readable there (a read-only mount cannot filter), and a package that `require`s back into the real workspace path is denied.
- **Redaction.** What the command prints (and its argument vector) goes through `redact_or_withhold` **before** truncation, the verdict, the ledger or the model see it; if hx cannot redact, the output is `[withheld: redaction failed]`, also for the unsandboxed choice.
- **Offline.** A failed run whose output shows it wanted the network (signatures in `ship/gate.json`), or lacked a module in a project that declares dependencies (`package.json`, `pyproject.toml`) and has no installed directory for them, ends with "dependencies aren't installed; install them, then ship again" (in the output, the block reason and `CommandRun.hint`).
- **Toolchain.** `ship/toolchain.py` finds the command in the child's `PATH` (absolute entries only, as hx does), follows `#!` lines (`#!/usr/bin/env node` too) and returns the directories to mount read-only through `runtime_ro`: the real directory of each program and, when its `bin` belongs to a prefix that holds its files (a virtual environment, a Python or Node install, a Rust toolchain: `pyvenv.cfg`, `lib/python*`, `lib/node_modules`, ...), that prefix. Never a directory that only holds a symlink (`~/.local` is not mounted because `~/.local/bin` is on `PATH`). `util.roots.vet_runtime_roots` drops what hx refuses. A program that is a file of an npm package (`.../node_modules/pnpm/bin/pnpm.cjs`) mounts that package's directory. Verified with `pytest`, `python -m pytest`, `npm test`, `pnpm test`, `node`, `cargo test --offline` and `make`; a rustup proxy also gets `RUSTUP_HOME`. **Dependency caches under `$HOME`**, chosen by the program's name or the project's marker file (`Cargo.toml`, `go.mod`, a lockfile) and never all of `$HOME`: cargo gets `registry/{index,cache,src}` and `git/{db,checkouts}` of `CARGO_HOME` (never `credentials.toml`) through a `CARGO_HOME` in the scratch whose entries are symlinks to them (cargo needs a writable home); npm its `_cacache`; pnpm its store; go `GOMODCACHE`. They go through `runtime_ro` (hx vets them), with the tools' offline switches set. yarn, pip and uv caches are not covered: install into the project's own directory instead.
- **No sandbox, no gate.** `sandbox_problem(client)` (no hx, or no `sandbox.run`, `sandbox.fs` or `sandbox.net.off`) refuses the ship **before anything is written** (`ship/run.py`), and a sandbox that fails at run time raises `SandboxUnavailableError`, which restores the ship with the reason (no `gate.decided`: no verdict is invented). The one way past is the user's own setting `gate.allow_unsandboxed` (plugin settings, never a project file; default false), used **only** when there is no sandbox: it is logged as a warning on every run and recorded as `unsandboxed:user_choice`. A working sandbox is always used, whatever the setting says. A command that names nothing runnable is a plain gate failure (`test command could not start`), not an unavailable sandbox.
- Known limits: a toolchain whose state is outside these caches (a yarn or pip cache, a Maven repository) has none, since `HOME` is the scratch; cargo builds from scratch in the copy on every ship (the `target` cache is not reused).

## exec (ADR-0005)
- **Every kernel call passes the plugin's policy.** `ctx.dispatch_tool` bypasses hooks, so `exec/calls.py` runs `policy.check(ToolCall(..., source="kernel"))`, then `dispatch_tool` (or `call_mcp`), then `tool.called` (`hooks.tool_called_payload`, `via: "exec"`). The plugin counts the per-cell calls and bounds concurrency (its pool); the kernel is never trusted to. An `approve` answer is a refusal from a cell.
- **Roles (governed mode).** `exec` is a **worker** tool; the orchestrator gets `pack` and `dispatch` only, and the handler refuses an orchestrator through the same `policy.check`. A worker's kernel is keyed by its own Hermes session id, judged with the worker's role (`rt.policy_for(caller)`), and its events go to the parent's ledger tagged `role/task_id/tier/attempt`. Stopping a session stops the kernels of the workers that worked for it.
- **Claude Code hooks.** `dispatch_tool` bypasses Hermes's hooks, so each kernel call also runs compat's `Bridge.run_tool_event` (PreToolUse before the policy, PostToolUse after, feedback printed on the cell's stderr). A hook `allow` is consumed by `policy.check` as for a hook call; an `ask`, or a rewrite of `harness.sh`'s command, is a refusal; a bridge that fails refuses. PostToolUse does not run for `harness.sh` (the plugin never sees its output).
- **Redaction is hx's** (`redact.apply`, ADR-0016): every text in an exec answer (stdout, stderr, result, error) passes it, and text it cannot redact is replaced by a marker, never passed raw. The spill files in scratch keep the raw output. The same call redacts the ledger's free-text fields (`ledger/store.py` `FREE_TEXT`; an event is not written if hx is up but fails) and the plugin's log lines (`util/log.py`, only while hx runs; a failure withholds the line).
- **Governed mode:** write tools, `terminal` and `exec` itself are refused from the kernel; shell work is `harness.sh`, judged as a `terminal` call (`source="kernel_sh"`) by the user's deny and ask rules. Network tools are refused from a cell unless `exec.network` is `on` (see above).
- **User `Bash` deny and ask rules and exec (what they do and do not do).** They apply to `harness.sh` **as judged on the command string**: the kernel reports `command` (`shlex.join(argv)`) and runs its own `argv`, and the kernel is the agent's own Python. So a rule is an audit trail and a convenience, **not a boundary**: a cell can run any program through `subprocess`, or read any file its sandbox grants with `open()`, without a `harness.sh` call at all, and a hostile kernel can report a different `command` than the `argv` it runs. The boundary for exec is the sandbox: the workspace read-only (so `.env` inside it is readable, and what a cell prints goes through hx's redaction only), scratch the only writable path, the network off, an allowlisted environment. A rule such as `Bash(rm *)` does not make a cell safer than that, and a rule meant to guard a secret must not rely on binding exec. A tool reached with `harness.tool('terminal', ...)` in an **ungoverned** session is Hermes's own unsandboxed `terminal`, judged the same way on its command string. Running the argv plugin-side (so the plugin judges exactly what runs) was rejected: it would hold one of hx's request slots per command and still not cover `subprocess`. `harness.sh` runs **in the kernel's own sandbox** (children inherit Landlock and seccomp), not through a second `sandbox.run`: that would hold one of hx's few request slots per command (accepted, ADR-0005). Cancel and timeout kill each command's **process group** and reap its orphans. A grandchild that calls `setsid` escapes that (the kernel has no `/proc` to find it) but still dies when the kernel stops, because the kernel is init of its PID namespace where the host has one.
- **Cancel vs kill.** A cancel or the soft timeout cancels the cell's asyncio task (and the tasks it started) and keeps the kernel. A cell that never yields (`while True: pass`, `time.sleep`) cannot be cancelled: after timeout plus `kill_grace_ms` the plugin kills the kernel and the answer says `hx.kernel.dead`, variables lost. The next call starts a fresh kernel and says so in `notes`.
- **Interrupt.** (A worker's tools fire no `post_tool_call`, so only the root session's cells are cancelled this way.) Hermes reports an interrupted exec call as `post_tool_call` with status `cancelled` while the handler still runs (verified on v0.23.2); `hooks.post_tool_call` then cancels that session's cell. `agent_loop_stopped` is not fired by the desktop gateway's `session.interrupt`, so it is not used. The handler's kwargs carry no `tool_call_id`, so kernel calls are numbered `<cell id>:<n>`.
- **Windows:** no channel yet, so `exec_ready()` hides the tool and `run_exec` answers `hx.sandbox.unavailable`. Never run the kernel unsandboxed.
- **Forms from a cell** go through `forms/` (see "Secrets and forms"). `diagnostics` answers `unsupported`. Kernel start, stop and death go to the log (`exec.kernel`), not the ledger (no such event types exist upstream).
- The kernel's system read paths are hx's own (`sandbox.spawn` with `system_read: true`); the plugin adds only the kernel files and the workspace as plain `ro`, and the interpreter's own roots (base prefix, venv, the real directory of the executable) as `runtime_ro`, which hx vets (not `/`, `$HOME`, the workspace or a parent of it) and mounts read-only. That is what lets a Python managed under HERMES_HOME (uv) run the kernel.
- **A kernel the sandbox cannot start is `hx.sandbox.unavailable`, however it fails.** `sandbox.spawn` refuses an interpreter outside the read grants itself (`hx.sandbox.spawn_failed`, as with a uv-managed Python outside `/usr`), and a kernel that dies before `kernel.ready` says the same; `HxLauncher.spawn` and `KernelProcess.start` both answer "the kernel did not start inside the sandbox". Tests of that path must pass with the interpreter anywhere.
- Hermes's generic tool deadline (about 420 s) ends a call it has not heard from; keep `exec.max_timeout_ms` under it.

## Hermes facts this code depends on (verified on v0.23.2)
- `ctx.dispatch_tool` passes no `parent_agent` in the gateway; pass `parent_agent=agent.subagent_lifecycle.get_active_subagent_parent()` (public API), bound in tool handlers, hooks of the turn and `subagent_stop`.
- `delegate_task` has no per-task `toolsets`: a spawn inherits the parent's toolsets minus `delegate_task`, so a worker sees `dispatch`. The policy is the guarantee.
- A child is its own session. `subagent_start` fires on the launching thread after `route_task` (same context variables) with `child_session_id`; the child's hooks and tool handlers carry that id, `task_id` is its `sa-...` id. Hermes fires **no `post_tool_call` for a child's tools** (`pre_tool_call` does fire): worker `tool.called` is written by `pre_tool_call` (blocked) and the boopis tool handlers.
- A child's first message is `CONTEXT:` then `TASK:`; Hermes renders plugin prompt sections for children too.
- `subagent_stop` carries `child_summary` (a self-report), `child_status`, a metadata-only `tool_call_history`.
- Several completions that arrive together are coalesced into one orchestrator turn.
- `post_api_request.usage` is Hermes's normalised usage: `input_tokens` is already uncached. Do not subtract the cache read again.
- `pre_llm_call` fires once per user turn, so the cost cap is checked per turn. `pre_api_request` cannot block (its return is ignored: `agent/turn_api_request.py`), so a per-request cap is not possible with hooks; a turn that makes many requests can overshoot the cap by the cost of that turn. (`llm_execution` middleware could wrap the call; not used.)
- `session.create` accepts `toolsets: ["boopis"]` only once a tool is registered in that toolset.
- Hermes does not tell a plugin a session's cwd before its first prompt: `ctx.session_cwd()` in an RPC or in `on_session_open` returns the profile's terminal directory. The cwd comes from the prompt section's `info` (`Runtime.cwd_of`); until then it is unknown, and RPC says `null`.
- The prompt section callable runs at a session's first prompt, before `on_session_start` and `pre_llm_call`.
- `on_session_end` fires every turn; `on_session_finalize` ends a session.
- `ctx.session_cwd()` is right only inside a turn (hooks, tool handlers) and in the prompt section `info`.

## Secrets and forms
- **Secret source.** `register` adds `boopis_host` (`ctx.register_secret_source`). Hermes runs a source only when its section says `enabled: true`, so a bound key needs three config writes (`providers.<name>.key_env`, `secrets.boopis_host.env.<VAR>: secret://...`, `secrets.boopis_host.enabled: true`); the setup flow and `forms/effects.py` make them through Hermes's own config API. At startup (and after plugin discovery) Hermes asks the source, which fetches each ref over the host's socket (2 s timeout, 8 KiB reply cap on the host side). The socket's path and the channel token come from two environment variables of the gateway, set by the host in the `gateway ensure|attach --start` call that started it (no file holds them); `register` takes them first thing and removes the token from the process environment (`hostsecrets.channel.capture_environment`), so no child the gateway starts inherits it. The host serves only the gateway process itself, never a child of it. A gateway the host did not start has neither variable: `ErrorKind.NETWORK`, and Hermes keeps its own `.env`; there is no store of ours. A key saved after the gateway started applies when the gateway next starts (Hermes reads sources once per process).
- **Forms.** The tools `request_input`, `request_credential` and `ask` return at once with `{form_id, status: "pending"}`; the answer arrives as the agent's next message through `ctx.inject_message` (needs `allow_gateway_injection`) or inline with `wait=true` (bounded by `forms.wait_max_s`). Passing `form_id` reads an earlier form. exec's `harness.request_input/ask/request_credential` use the same service. Forms are kept in memory: a plugin restart forgets them and `form.list` then omits them.
- **Secrets never pass through the plugin.** `form.submit` refuses a secret field's value (`hx.form.invalid_values`, without echoing it); the UI saves it with the host and lists it in `provided`; the plugin asks the host `has` (never `get`) and answers the agent `{saved, ref}`. The ledger gets field names only.
- **Ledger.** `form.opened` and `form.resolved` are `tool.called` events until contraprova has the types (`docs/LEDGER.md`, "Pending upstream").
- **Hermes's own requests** (`clarify`, `approval.request`) are adapted by the UI from the canonical gateway events and answered through Hermes's `clarify.respond` / `approval.respond` (`apps/desktop/ui/src/host/forms.ts`); the plugin only sees them through the observer hook `on_human_input_request`, which carries no `prompt_id` or generation, so it does not mirror them.

## Setup the plugin depends on (set by the host's setup, with the user's consent)
- `tools.tool_search.enabled: "off"` in the profile in use, so `pack`, `ship` and `dispatch` show directly (ADR-0014).
- `delegation.backend: boopis`, so governed `dispatch` can route attempts to their tier.
- `plugins.entries.boopis.allow_gateway_injection: true`, so a Claude Code Stop hook that blocks can re-enter through `ctx.inject_message`. Without it a Stop block is logged and ignored, and `compat.inventory` warns. It also delivers a non-waiting form's answer.
- All of this is done by the host's first-run setup (`apps/desktop/AGENTS.md`, "First-run setup"), with the user's consent, through `hermes config set`.

# dev env: pytest and ruamel.yaml. Upstream contraprova (editable) is only used by the e2e tests, to run its own

hermes plugins validate .

End-to-end tests (`../../tests/e2e`) start a real, unmodified Hermes gateway against a fake OpenAI-compatible model (`fake_model_server.py`) with this plugin copied into a temp `HERMES_HOME`. Set `HX_E2E_HERMES_ENV` to the directory the spike's `install.sh` produced (it holds `hermes-home/installs`, `runtime`, `uv-python`); without it they skip. Hermes's venv has no contraprova yet, so the stack puts the test process's contraprova on `PYTHONPATH`. Type-check them with `pyright -p ../../tests/e2e`.

## Do not
- Import Hermes internals, patch Hermes, or register a tool before it works.
- Put a model id, a price, a protected glob or a timeout in code. Data goes in `defaults.json`, the schemas or settings.
- Add a new env var for non-secret config.
