# 120 fps for the desktop app on the owner's machine: research report

Date of research: 2026-11-19. Target: RTX 4070 laptop (hybrid), Arch, Hyprland (Wayland), 2880x1800 @ 120 Hz, scale 1.6. Stack read from the repo: Tauri 2.12.7, wry 0.57.3, webkit2gtk crate 2.0.2 (GTK3, `Cargo.lock`), UI in plain TypeScript with JS-driven rAF loops (orbs on 2D canvas, dock engine) and no `linear()` or OffscreenCanvas use today.

Labels: **[V]** verified (URL or file:line), **[I]** inference, **[?]** unverified.
"Tarball" means I downloaded `https://webkitgtk.org/releases/webkitgtk-<ver>.tar.xz` for 2.44.0, 2.46.0, 2.52.6, 2.54.0-2.54.3 and read the source; paths are inside it. Versions in play: latest stable WebKitGTK is 2.54.3 (released 2026-11-18, https://webkitgtk.org/); Arch `webkit2gtk-4.1` is 2.54.2-1 built 2026-10-23 (https://archlinux.org/packages/extra/x86_64/webkit2gtk-4.1/). ADR-0024's measurements were on 2.52.6.

---

## 0. Answer first

**Can the app reach 120 fps with WebKitGTK on this machine?** Yes in principle, but only if four independent things are all true, and today at least two are false by default. Nothing here is proven on the owner's hardware; the first step is a five-minute measurement (section 8).

1. **The page's rAF is released at 120.** By default WebKitGTK caps `requestAnimationFrame` and the page rendering update at 60 on a 120 Hz display (the "Prefer Page Rendering Updates near 60fps" preference, on by default). It can be switched off from the host. [V]
2. **WebKit knows the display is 120 Hz.** WebKitGTK reads the rate from a DRM vblank monitor; if `drmWaitVBlank` fails (reported on the NVIDIA proprietary driver) it falls back to a hard-coded 60 Hz timer that nothing can raise. On a hybrid laptop whose panel is on the iGPU this should be fine. [V code, I for this machine]
3. **The renderer is not the CPU path.** `WEBKIT_DISABLE_DMABUF_RENDERER=1` (how the owner runs) turns off accelerated compositing entirely on the GTK port: the CPU paints the whole page every frame, nothing runs on a compositor thread. 120 fps at 3600x2250 is not a realistic target there. [V]
4. **The machine is not in power-saver**, which WebKitGTK treats as "Low Power Mode" and halves rAF. [V]

If (2) fails, or the blank-window cause cannot be fixed on the GPU path, WebKitGTK tops out at 60 and **there is no credible Linux Tauri alternative today**: the only Chromium runtime (Tauri 3 alpha, `tauri-runtime-cef`) forces X11/XWayland on Linux. Details and ranking in sections 7 and 9.

## 1. WebKitGTK and high refresh rates

### 1.1 rAF does not simply follow the monitor: it is capped near 60 by default [V]

- The setting exists and applies to the GTK port. `PreferPageRenderingUpdatesNear60FPSEnabled`, `status: stable`, description "Prefer page rendering updates near 60 frames per second rather than using the display's refresh rate", default `true` for WebKit, WebKitLegacy and WebCore except `PLATFORM(VISION)`. No `exposed:` restriction, so it is exposed to every frontend including GLib. Same text and default in 2.44.0, 2.46.0, 2.52.6, 2.54.3 (`Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml`, lines 5247 / 5468 / 6327 / 6817 respectively). Upstream main: https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml (line 5140 at the time I fetched).
- Where it bites: `Source/WebCore/dom/ScriptedAnimationController.cpp:86` (rAF interval) and `Source/WebCore/page/Page.cpp:2773, 2797` (the page's whole rendering-update interval) both pass the setting into `preferredFrameInterval()` / `preferredFramesPerSecond()` (`Source/WebCore/platform/graphics/AnimationFrameRate.cpp:47-86`).
- The rule (`AnimationFrameRate.cpp:35-45`): `ratio = nominal / 60`, then pick the divisor of the refresh rate nearest to 60. For 120 Hz: **60**. For 144 Hz: 72. For 165 Hz: 82. Note `nominal / FullSpeedFramesPerSecond` is **unsigned integer division** assigned to a float (`FramesPerSecond = unsigned`, `AnimationFrameRate.h:38`), so the ratio is never fractional. [V]
- [I] consequence of that integer division: if the panel's rate is reported as 119 (a 119.99x Hz mode truncated by `refreshRate / 1000`, see 1.2), `ratio = 1`, the "nearest divisor" is 119 and **rAF runs at ~119 even with the preference on**. So `webkit://gpu`'s "VBlank refresh rate" line (1.3) tells whether the cap bites: `120Hz` = capped to 60, `119Hz` = not capped.
- If the display rate is unknown to the page (`nominalFramesPerSecond` empty) or exactly 60, the interval is 60 (`AnimationFrameRate.cpp:52-58`). [V]
- Real-world confirmation (third-party, not WebKit): a Tauri app on WebKitGTK 2.54.2 on a 240 Hz Wayland monitor measured a rAF loop at 60.1 fps with the feature on and 235.2 fps with it off (https://github.com/YuriiMurha/grooviq/pull/125, search-result summary; the page I fetched covered only the macOS half, so treat the Linux numbers as [?]). The same preference on macOS WKWebView: 120 Hz -> 60 and 144 Hz -> 72, fixed by turning it off (https://github.com/puang59/nuza/issues/317, https://github.com/YuriiMurha/grooviq/pull/125 measured 115-121 fps after).
- History of the preference: moved from developer/unstable to stable on 2023-10-27 (https://lists.webkit.org/pipermail/webkit-changes/2023-October/292766.html); present in every WebKitGTK tarball I read from 2.44 on [V]. Earlier 2.42 not checked [?].

### 1.2 DisplayLink on the GTK port [V]

- `Source/WebKit/UIProcess/glib/DisplayLinkGLib.cpp:35-65`: the UI process creates a `DisplayVBlankMonitor`, sets `m_displayNominalFramesPerSecond = refreshRate`, and notifies the web process on each vblank. The nominal rate reaches the page through `Page::windowScreenDidChange` (`Source/WebCore/page/Page.cpp:1809-1815`), enabled by `HAVE_DISPLAY_LINK` for `PLATFORM(GTK)` (`Source/WTF/wtf/PlatformHave.h:387-389`).
- `DisplayVBlankMonitor::create` (`.../DisplayVBlankMonitor.cpp:48-71`): DRM monitor if `drmWaitVBlank` works; otherwise **`DisplayVBlankMonitorTimer`**, constructed with `FullSpeedFramesPerSecond` = 60 (`DisplayVBlankMonitorTimer.cpp:41`). Also timer if `displayID == 0` or `WEBKIT_FORCE_VBLANK_TIMER` is set.
- DRM monitor (`DisplayVBlankMonitorDRM.cpp:80-148, 252-286`): finds the CRTC for the GDK monitor's connector over **all** DRM devices, calls `drmWaitVBlank`, and sets the rate to `gdk_monitor_get_refresh_rate(monitor) / 1000` (integer mHz -> Hz, truncating). On Hyprland the `wl_output` mode refresh sent to clients is `m_refreshRate * 1000.0` (https://raw.githubusercontent.com/hyprwm/Hyprland/main/src/protocols/core/Output.cpp, line 82).
- Only a **lowering** override exists: `WEBKIT_DISPLAY_REFRESH_THROTTLE_FPS` (must divide the refresh rate, `DisplayLinkGLib.cpp:49-62`). Nothing raises it. [V]
- NVIDIA proprietary driver: a third-party report (WebKitGTK 2.52.6, GTX 1080, GNOME Wayland, 240 Hz) says `drmWaitVBlank` fails on every output, WebKit falls to the 60 Hz timer, and the page gets ~62 fps whatever the preference says (https://github.com/Jackicus/GNOME-Turntable/issues/1). The WebKit code path they describe is exactly what I read above [V]; that NVIDIA's DRM returns an error from `drmWaitVBlank` is **their measurement, not verified by me** [?]. Relevance: only if the **panel** is driven by the NVIDIA GPU (MUX in dGPU mode, or an external monitor on a dGPU-wired port). On a normal hybrid laptop the eDP panel is on the iGPU's DRM device, so the DRM monitor is opened there [I].
- Versions: vblank synchronisation landed in 2.43.1, `webkit://gpu` vblank info and the timer fallback in 2.43.3, non-realtime display-link thread in 2.44.0 (`NEWS` in the 2.44.0 tarball, lines 10, 36-37, 60). So the DisplayLink path is in every stable release from 2.44 (March 2024). [V]

### 1.3 Other things that halve or cap the rate [V]

- **Power saver.** `LowPowerModeNotifierGLib.cpp:30-45` reads `GPowerProfileMonitor` (power-profiles-daemon); `AnimationFrameRate.cpp:33,54,61` halves the rate for `LowPowerMode` (also for `VisuallyIdle`, `NonInteractedCrossOriginFrame`, `AggressiveThermalMitigation`). A Linux report measured 16 -> 32 ms frame interval under `power-saver` on 2.52 (https://github.com/solutionscay/skiff/issues/7). On a laptop on battery in the power-saver profile, **120 becomes 60 even with the preference off**.
- **Out of the viewport / hidden window**: interval becomes the aggressive throttling interval.
- **Diagnostic**: `webkit://gpu` shows "VBlank type" (`Timer` or `DRM`) and "VBlank refresh rate" (`Source/WebKit/UIProcess/API/glib/WebKitProtocolHandler.cpp:689-690`, 2.54.3). `WEBKIT_SHOW_FPS`, `WEBKIT_DRAW_FPS`, `WEBKIT_SHOW_DAMAGE` also exist (grep of `getenv("WEBKIT_*")` in the 2.54.3 tarball). [V]

### 1.4 Can Tauri / wry change the preference? Yes, from the host, with a small FFI shim [V + I]

- GLib API: `webkit_settings_get_all_features()`, `webkit_feature_list_get_length/get`, `webkit_feature_get_identifier()`, `webkit_settings_set_feature_enabled(settings, feature, enabled)`, all **Since 2.42** (`Source/WebKit/UIProcess/API/glib/WebKitSettings.cpp:4219-4278`, `WebKitFeature.cpp`, 2.54.3). The feature identifier is the preference key minus the `Enabled` suffix: **`PreferPageRenderingUpdatesNear60FPS`** (`WebKitFeature.cpp:131-136`). The feature list is built from every `bool` preference not restricted by `exposed:` (`GeneratePreferences.rb:266-267`, `WebPreferencesFeatures.cpp.erb:39-47`), so this one is in it.
- Rust side: the `webkit2gtk` crate 2.0.2 that wry pins has features only up to `v2_40` (crate `Cargo.toml`, checked in the downloaded crate), so **no safe binding exists for `set_feature_enabled`**. 3.0.0 (published 2026-11-19) still stops at `v2_40` and is GTK3 (`gtk` 0.19). A host-side `unsafe extern "C"` (or `dlsym`, to survive WebKitGTK < 2.42 on old distros) is needed; the host already has one deliberate `unsafe` (ADR-0024 `set_var`).
- Getting the settings object: Tauri 2 `WebviewWindow::with_webview(|w| w.inner())` gives the `webkit2gtk::WebView` on Linux (https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri/src/webview/mod.rs lines 155-177, 1843-1906; the same API exists in Tauri 2). Then `WebViewExt::settings()` and `ToGlibPtr` give the `WebKitSettings*`. wry itself sets only a handful of settings and exposes no feature flags (https://raw.githubusercontent.com/tauri-apps/wry/dev/src/webkitgtk/mod.rs, `set_webview_settings`, lines 428-470). [V]
- Does it take effect live? `WebPreferences::setFeatureEnabled` goes through the normal preferences update to the web process and `Page::settings()` is read on every rAF scheduling call, so a change after creation should apply without reload; the macOS equivalent was verified live (grooviq PR #125). For WebKitGTK I did not run it [?].
- There is **no environment variable** for this preference (the `getenv("WEBKIT_*")` list in the tarball has none). [V]
- Sketch (not written into the repo, per instructions):
  ```rust
  // after the webview exists, on the main thread
  unsafe {
      let list = webkit_settings_get_all_features();            // WebKitFeatureList*
      for i in 0..webkit_feature_list_get_length(list) {
          let f = webkit_feature_list_get(list, i);
          if CStr::from_ptr(webkit_feature_get_identifier(f)) == c"PreferPageRenderingUpdatesNear60FPS" {
              webkit_settings_set_feature_enabled(settings_ptr, f, 0);
          }
      }
      webkit_feature_list_unref(list);
  }
  ```
  (`webkit_feature_list_find` would shorten it but is Since 2.54.)

## 2. Compositor-driven animation in WebKitGTK

Mode summary (all [V] from the 2.54.3 and 2.52.6 tarballs unless noted):

| Renderer mode | How it is chosen | Compositor-thread animation | 2D canvas |
|---|---|---|---|
| **CPU / "never"** (`WEBKIT_DISABLE_DMABUF_RENDERER=1`) | `rendererBufferTransportMode()` returns empty, `canUseHardwareAcceleration` false (`gtk/AcceleratedBackingStore.cpp:86-88, 139-144`) -> `HardwareAccelerationManager` sets `m_acceleratedCompositingModeEnabled = false` (`gtk/HardwareAccelerationManager.cpp:42-44`) -> web process uses **`NonCompositedFrameRenderer`** (`DrawingAreaCoordinatedGraphicsGLib.cpp:151-157`). Threaded scrolling also off (`gtk/WebPreferencesGtk.cpp:36-41`). | **No.** No layer tree, no compositor thread: all animation runs in the main thread's rendering update and the CPU paints the dirty area. | Unaccelerated (`html/CanvasBase.cpp:235-250`: `hardwareAccelerationEnabled == false` -> not accelerated). |
| **GL + shared-memory transport** (`WEBKIT_DMABUF_RENDERER_FORCE_SHM=1`) | transport mode = SharedMemory only (`AcceleratedBackingStore.cpp:96-100`) | **Yes** (accelerated compositing stays on) | Accelerated by Skia GL |
| **GL + DMA-BUF** (default) | needs EGL dma-buf import and a DRM main device (`AcceleratedBackingStore.cpp:102-113`; device from the UI process' EGL display or `WEBKIT_WEB_RENDER_DEVICE_FILE`, `glib/DRMMainDevice.cpp:188-247`) | **Yes** | Accelerated by Skia GL |
| `WEBKIT_DISABLE_COMPOSITING_MODE=1` | `HardwareAccelerationManager.cpp:45-46` | No (same non-composited renderer) | |

- ADR-0024's reading of the switches (policy `never` for DISABLE_DMABUF, FORCE_SHM keeps GL) matches the source. [V]
- What animates off the main thread: the animated properties flagged `animation-wrapper-acceleration` in `Source/WebCore/css/CSSProperties.json` (2.54.3): `opacity`, `filter`, `backdrop-filter`, `transform`, `translate`, `scale`, `rotate` ("always"); `offset-path/distance/position/anchor/rotate` ("threaded-only", not for us). CSS animations/transitions and Web Animations on those properties, on a **composited layer**, are applied by the compositor thread: `SkiaCompositingLayer::syncAnimations` calls `m_animations.apply(...)` (`platform/graphics/skia/SkiaCompositingLayer.cpp:426-461`), driven by `ThreadedCompositor` with its own run loop (`WebProcess/WebPage/CoordinatedGraphics/ThreadedCompositor.cpp:73-108`). Everything else (width/height/left/top/background/clip-path/mask, JS rAF) stays on the main thread. [V]
- Several animations are blocked from acceleration by `KeyframeEffect::canBeAccelerated` (additive/accumulate composite, reference filters, discrete transform intervals, animating size with a size-dependent transform, etc., `animation/KeyframeEffect.cpp:1970-2023`). [V]
- **`linear()` easing**: parsed since at least WebKitGTK 2.44.0 (`consumeLinear`, `css/parser/CSSPropertyParserHelpers.cpp:5976` in the 2.44.0 tarball) [V]. **But it forced main-thread animation until 2.54**: in 2.52.6 `KeyframeEffect::canBeAccelerated` unconditionally returns false when some keyframe or the effect uses `steps()` or `linear()` with points; in 2.54.x those two checks sit under `#if USE(CA)` (Apple only), so on GTK they no longer block (`KeyframeEffect.cpp:2016-2021` in 2.54.3 vs lines 1962-1965 in 2.52.6). The 2.54 highlights say the same: "CSS animations using the steps() and linear() timing functions no longer force main-thread animation" (https://webkitgtk.org/2026/09/16/webkitgtk-2.54-highlights.html). So **springs expressed as a sampled `linear()` curve on transform/opacity run on the compositor thread on WebKitGTK >= 2.54 (Arch has 2.54.2), and on the main thread (still correct, but exposed to main-thread jank) on 2.44-2.52.** [V]
- 2.54 also replaced the TextureMapper compositor with a Skia one with batched painting, damage-limited draws, GPU atlas, and a smoother async-scroll thread (same highlights page). The non-accelerated mode was reworked to "always use damage information ... at most one frame per vertical blank" [V, highlights], but the owner's `DISABLE_DMABUF` case still maps to `NonCompositedFrameRenderer` as shown above.
- Caveat [I]: compositor-thread animation does not make *content* cheaper. A `will-change: transform` layer that must be re-rasterised each frame (anything not purely transformed) still costs raster at 3600x2250; and the compositor frame rate is whatever the DisplayLink gives it (1.2).

## 3. OffscreenCanvas in a Worker (2D)

- **Version and default [V]**: in 2.44.0 the build option was tied to `ENABLE_EXPERIMENTAL_FEATURES` and the runtime preference defaulted off on GTK (`cmake/OptionsGTK.cmake:136-137`, yaml 4918-4932 in the 2.44.0 tarball). From **2.46.0** (Sept 2024) the build option defaults ON and both `OffscreenCanvasEnabled` and `OffscreenCanvasInWorkersEnabled` default to true for `PLATFORM(GTK)` (2.46.0 `OptionsGTK.cmake:138-139`, yaml 5086-5118; same in 2.52.6 and 2.54.3). Distro builds that pass explicit flags could differ; Arch's PKGBUILD not checked [?].
- 2.54 also added `image/webp` to `canvas.toDataURL()` and kept threaded Skia painting (NEWS 2.53.4). Not relevant to orbs.
- **Is a worker's 2D canvas GPU accelerated? [?]** The Skia accelerated backend uses `PlatformDisplay::sharedDisplay().skiaGLContext()` and `makeContextCurrent()` (`platform/graphics/skia/ImageBufferSkiaAcceleratedBackend.cpp:101-125`); a GL context can be current on one thread, and the main thread's compositing/painting uses it. I did not find worker-specific handling, so a worker canvas may fall back to `ImageBufferPlatformBitmapBackend` (Skia raster on the CPU, `ImageBuffer.cpp:98-107`) [I]. That is still the win that matters (draw off the main thread), but it is CPU raster plus a copy to the placeholder canvas, and at 3600x2250 for large canvases that copy and raster are not free. Needs a measurement with `OffscreenCanvas` + `getContext('2d')` and `WEBKIT_SHOW_FPS`.
- With the owner's CPU renderer a worker canvas is CPU either way (`CanvasBase::shouldAccelerate` requires `hardwareAccelerationEnabled`, `html/CanvasBase.cpp:235-250`). [V]
- Cost for us: the harness already measures the orbs; moving `orb-runtime.ts` drawing to a Worker means `transferControlToOffscreen()`, no DOM access in the worker (colour tokens via `postMessage`), and handling the quality ladder's width/height assignment (which empties the canvas, per the harness README) as a worker-side resize. Medium.

## 4. The GPU path on NVIDIA + Wayland + Hyprland, now

### 4.1 What the known blank-window / crash causes are

1. **Explicit-sync protocol error on GTK3 + NVIDIA EGL (the Wayland `Error 71` / "explicit sync is used, but no acquire point is set").** Root cause found and **fixed upstream**: [V]
   - WebKit bug 324551, RESOLVED FIXED, commit 322671@main on 2026-10-05 (https://bugs.webkit.org/show_bug.cgi?id=324551). The comment by the fixer explains it: `AcceleratedBackingStore` created its GdkGLContext while painting the first EGLImage buffer; GTK3 decides at frame start whether to use GL, so that frame was still committed as `wl_shm`; creating the first GL context mid-frame made NVIDIA's egl-wayland enable explicit sync on the surface and the compositor then disconnected the client. He tested on a **hybrid PRIME laptop under KWin**: 27 of 27 starts OK with the patch vs 0 of 9 without. He notes the same happens in a plain GTK3 program and is not WebKit-specific.
   - The fix is in the code: `Source/WebKit/UIProcess/gtk/AcceleratedBackingStore.cpp:776-785` (`#if !USE(GTK4)`, `ensureGLContext()` before the frame). **It is present in the 2.54.2 and 2.54.3 tarballs and absent from 2.54.0, 2.54.1 and 2.52.6** (I grepped each). Arch ships 2.54.2, so it has it. [V]
   - The older umbrella bug 280210 ("Error 71 ... NVIDIA proprietary on Wayland") is still NEW; it includes a report that 2.52.5 worked and 2.54.0 failed, and that `__NV_DISABLE_EXPLICIT_SYNC=1` then caused "extremely heavy" flicker (https://bugs.webkit.org/show_bug.cgi?id=280210). NVIDIA's egl-wayland maintainer's reading: "it is a protocol error to attach a buffer without setting explicit sync points ... webkitGTK should not be attaching a buffer here" (https://github.com/NVIDIA/egl-wayland/issues/179).
   - Downstream: a project gates its `__NV_DISABLE_EXPLICIT_SYNC=1` workaround on "WebKitGTK < 2.54.2" (https://github.com/music-assistant/desktop-app/pull/230) [third-party, consistent with the source].
2. **DMA-BUF framebuffer errors on X11 / old NVIDIA** (`nvidia_drm.modeset=1` needed on drivers < 545), collected in https://github.com/tauri-apps/tauri/issues/9394 and https://v2.tauri.app/develop/debug/linux-graphics/. [V as reports]
3. **Compositing off + page blank on NVIDIA**: bug 324551's comment notes that with compositing disabled the page stayed blank on the NVIDIA GPU, while `WEBKIT_DMABUF_RENDERER_FORCE_SHM=1` draws the page. Several reports say `WEBKIT_DISABLE_DMABUF_RENDERER=1` itself gives an all-blank window on 2.54 on some NVIDIA setups (search summary of https://github.com/NC1107/sink/issues/78, https://github.com/tarwin/tinyjsapp/issues/78) [?: those pages I did not open].
4. Hyprland-specific reports exist for AMD + Mesa (`EGL_BAD_PARAMETER`, blank window) where DISABLE_DMABUF alone did not help (search results, e.g. https://github.com/RongleCat/grok-app/issues/539) [?].

### 4.2 Can it work on Hyprland in 2026? [I]

Probably yes on the GL path for this laptop, **but I found no report of WebKitGTK 2.54.2 on Hyprland with a hybrid NVIDIA machine; it has not been tried by anyone I could find.** The fix in 4.1 was tested on KWin; the failure is a client protocol violation, so every compositor that implements explicit sync is exposed to it, and Hyprland, like KWin and mutter, kills or breaks the client on that violation [?: the Hyprland-side behaviour is from a search summary, not a verified source]. The strongest argument for trying it: the blank window the owner saw was seen on an older WebKitGTK that lacked this fix.

### 4.3 Which GPU should the webview use on a hybrid laptop? [I, source-backed mechanics]

- The web process renders on the DRM device of the UI process' EGL display (`glib/DRMMainDevice.cpp:212-247`), overridable with `WEBKIT_WEB_RENDER_DEVICE_FILE=/dev/dri/renderD12x` (line 205). On a hybrid laptop the default EGL vendor is normally the iGPU's Mesa, i.e. the **same GPU that drives the panel and Hyprland**: dma-bufs go straight to the compositor with no cross-GPU copy. [I]
- Forcing PRIME offload to the NVIDIA GPU (the repo's `laptop-nvidia` harness line: `__NV_PRIME_RENDER_OFFLOAD=1 __GLX_VENDOR_LIBRARY_NAME=nvidia __EGL_VENDOR_LIBRARY_FILENAMES=...10_nvidia.json`) puts the app on NVIDIA's EGL, which is exactly the egl-wayland path of bug 324551/280210, adds a cross-GPU buffer copy, and keeps the dGPU awake for a light 2D UI. **Do not do this as a fix.** Keep the webview on the display GPU; measure with the harness line only to learn. [I]
- ADR-0024 already makes the right call for the automatic rule (leave hybrid-iGPU alone). Its "Wayland plus NVIDIA is not auto-fixed" consequence is also still right; the new information is that on >= 2.54.2 the GTK3 explicit-sync crash cause is fixed upstream, so `renderer.rs` need not push Wayland+NVIDIA users to the CPU path.

## 5. The alternative engine: Chromium (CEF, Electron)

### 5.1 Tauri's CEF runtime: status [V unless marked]

- It exists, but only for **Tauri 3 (alpha)**: https://v3.tauri.app/develop/cef/ ("is new in the Tauri 3.0 alpha and is not available in Tauri 2.0", "Its APIs may still change before the stable release"). Crate `tauri-runtime-cef`: first `3.0.0-alpha.0` 2026-09-13, latest `3.0.0-alpha.7` 2026-11-06 (crates.io API), `tauri` itself 3.0.0-alpha.6; stable Tauri is 2.12.7. The CEF binding crate `cef` (cef-rs, Tauri org) is at 156.7.0 (Chromium 156), released 2026-11-19; the runtime's alpha.6 changelog bumps CEF to 154.5.0.
- Migration notes (https://v3.tauri.app/start/migrate/from-tauri-2/): runtime must be chosen explicitly (`.runtime(tauri_runtime_cef::Cef::default())`), `tauri::Wry`/`tauri::wry` removed, every `tauri-plugin-*` crate and `@tauri-apps/*` package must move to the 3.0 alpha line, GTK3 vs GTK4 chosen by feature, Tauri says "Keep production apps on 2.x".
- Size and cost (https://v3.tauri.app/develop/cef/): "bundles are hundreds of megabytes larger than with wry", more memory, first build downloads ~1 GB of the CEF distribution. Linux: AppImage cannot ship the setuid sandbox helper (sandbox dropped under AppArmor restrictions), deb/rpm install it. Only the `en-US` locale is bundled. A Linux first-run EULA bug with Chromium 151 stopped startup until `--no-first-run` was passed (https://github.com/tauri-apps/tauri/issues/15979, closed).
- **On Linux it forces X11.** `tauri-runtime-cef-3.0.0-alpha.7/src/runtime.rs:3313-3342` (crate downloaded from crates.io): pushes `--ozone-platform=x11` for every process type and sets `GDK_BACKEND=x11` because "CEF integration below uses XIDs for child windows/reparenting". `src/platform/linux/webview.rs` and `window.rs` create an X11 host window and reparent CEF children into it. So on Hyprland it runs under **XWayland**, not native Wayland. (CEF's own tracker still lists embedding CEF in third-party Wayland windows as an open issue, https://github.com/chromiumembedded/cef/issues/2804; the date of the last activity I did not check.) The community fork README also says it is only verified on Linux/X11 (https://github.com/SableClient/tauri-runtime-cef).
- Implication for our target [I]: XWayland at Hyprland scale 1.6 is either bitmap-upscaled from scale 1 (blurry) or the app handles scale itself (`xwayland:force_zero_scaling`, not verified by me [?]); CEF windowless (OSR) mode landed in alpha.6 but then the app, not Chromium, paints and handles input. Neither reads as a polished 120 Hz path today.

### 5.2 Does Chromium on Linux Wayland + NVIDIA reliably reach 120 fps? [?, with negative evidence]

- No first-party statement found. Chromium on Wayland follows the compositor's frame callbacks in principle [I]; an old report (KWin only, Chromium ozone Wayland): ~58 fps at 120/144 Hz, fine on GNOME and Sway (https://www.mail-archive.com/kde-bugs-dist@kde.org/msg665991.html, ~1700 days old, search summary).
- NVIDIA proprietary + native Wayland is currently the troublemaker for Chromium-based apps: Electron 38 made `--ozone-platform=auto` default (https://www.electronjs.org/blog/electron-38-0) and VS Code Insiders then showed a blank screen on NVIDIA + Wayland, VA-API init crash in the GPU process, workaround `--ozone-platform=x11` (https://github.com/microsoft/vscode/issues/280464, open); another project keeps NVIDIA proprietary on XWayland by default because the Electron 40 GPU process dies under Wayland ozone (error_code=1002, driver 615.71, RTX 4060 laptop) while also noting that is one report not reproduced on hardware (https://github.com/NousResearch/hermes-agent/pull/127048). ArchWiki warns of intermittent GPU-process crashes on NVIDIA proprietary under XWayland and suggests ANGLE Vulkan flags (search summary of https://wiki.archlinux.org/title/Chromium; page itself blocked for me).
- So: Chromium would have GPU raster, compositor-thread everything, and a rAF that is not capped near 60, but on this exact hardware class it is **not reliably native-Wayland today**, and the Tauri integration uses XWayland anyway. A reasonable expectation is "can reach 120 under XWayland on the iGPU path", unproven [I].

### 5.3 Electron as a reference point

Electron >= 38 runs native Wayland by default; on NVIDIA proprietary it needs `--ozone-platform=x11` in several 2026 reports (above). Chromium's rAF is not capped near 60. Switching to Electron is a re-platform of our Tauri host (see 5.4).

## 6. Fractional scaling (scale 1.6)

- **GTK3 renders scale 1.6 at 2x on Wayland and the compositor scales down: confirmed.** [V]
  - GTK3's Wayland backend only knows the integer `wl_output.scale` and `wl_surface_set_buffer_scale`; there is no `wp_fractional_scale` / `wp_viewporter` code in `gdk/wayland` of `gtk-3-24` (grep of `gdkwindow-wayland.c`, `gdkdisplay-wayland.c`, `gdkscreen-wayland.c`: only `wl_surface_set_buffer_scale` at lines 450, 936, 5304; `output_handle_scale` in `gdkscreen-wayland.c:1762`), from https://gitlab.gnome.org/GNOME/gtk/-/raw/gtk-3-24/gdk/wayland/.
  - Hyprland sends `wl_output.scale = ceil(monitor scale)`: `m_resource->sendScale(std::ceil(m_monitor->m_scale))` (https://raw.githubusercontent.com/hyprwm/Hyprland/main/src/protocols/core/Output.cpp:80). 1.6 -> 2.
  - So the window gets scale 2, `devicePixelRatio` 2, buffers of 3600x2250, and the compositor downsamples to 2880x1800. ADR-0024's wording is correct.
  - Community statements agree: GTK3 "will definitely not" get fractional scaling (GNOME bugzilla / Discourse threads via search; KDE discuss thread https://discuss.kde.org/t/wp-fractional-scale-v1-and-gtk-3-applications/48573).
- **GTK4 (`webkitgtk-6.0`) does real fractional scaling in GTK, but WebKitGTK still renders the page at an integer scale.** [V]
  - GTK4 supports `wp_fractional_scale_v1` + viewporter (initial support GTK 4.11.1, https://blog.gtk.org/2023/04/05/gtk-4-11-1/; enabled by default with the ngl renderer in the 4.14 cycle, `NEWS` line 4776-4800 at https://gitlab.gnome.org/GNOME/gtk/-/raw/main/NEWS).
  - WebKitGTK sets the page's intrinsic device scale from `gtk_widget_get_scale_factor()` (`Source/WebKit/UIProcess/API/gtk/WebKitWebViewBase.cpp:2580, 2590`, 2.54.3; the same code for both ports), and `gdk_surface_get_scale_factor()` is `(int) ceil(gdk_surface_get_scale())` (https://gitlab.gnome.org/GNOME/gtk/-/raw/main/gdk/gdksurface.c:2442). So 1.6 -> 2 in the page. **[I]**: GTK4 would take the 2x texture and scale it with its own renderer to the exact 2880x1800 grid, which gives a sharper final result but **does not reduce the raster cost** (still 3600x2250 tiles).
  - 2.54 added a `WebKitWebView:magnification` property for "visual scaling independent of zoom" (highlights page); I did not test whether it can express 1.6 [?].
- **Tauri / wry do not support the GTK4 port.** wry 0.57.3 depends on `webkit2gtk =2.0.2` and `gtk 0.18` (https://raw.githubusercontent.com/tauri-apps/wry/dev/Cargo.toml); Tauri 3's own docs: "wry is built on GTK 3 (through WebKitGTK) and CEF on GTK 4" (https://v3.tauri.app/develop/webview-runtime/). A `webkit6` crate for GTK4 exists in the gtk-rs ecosystem, but nothing in Tauri uses it. [V]
- **Cost lever that does exist** [I]: since the page is rendered at 2x regardless, the only way to lower raster cost is to repaint less (the harness already found cost tracks repainted area, ADR-0024 / perf README), keep composited layers small, and move animation to transform/opacity on layers (section 2).

## 8. Plain answer and ranked recommendation

**Can we reach 120 fps with WebKitGTK on the owner's machine?** Possibly, under these conditions: WebKitGTK >= 2.54.2 (Arch has it), webview on the iGPU that drives the panel, the GL renderer instead of `DISABLE_DMABUF`, the 60 fps preference off, DRM vblank monitor active, not in power-saver, and the page's own per-frame main-thread cost under ~8 ms at 3600x2250. **With the owner's present configuration (`WEBKIT_DISABLE_DMABUF_RENDERER=1`) it cannot reach 120**: that mode paints the full page on the CPU, has no compositor thread, and its rAF is capped at 60 by default. If the panel turns out to be NVIDIA-driven and `drmWaitVBlank` fails, WebKitGTK is stuck at 60 by construction.

**Ranked recommendation**

1. **Measure on the real session first (hours, no code).** On the owner's laptop, with the app stopped:
   - `webkit://gpu` (Settings > General > Diagnostics already opens it): read "VBlank type" (DRM vs Timer), "VBlank refresh rate" (120Hz = capped by the preference, 119Hz = not), the acceleration policy, and which GPU/render node WebKit picked.
   - `cat /sys/class/drm/card*-eDP-*/status` and which `card` has the eDP connector, to know which GPU drives the panel; `powerprofilesctl get`.
   - Run the repo's harness lines from `apps/desktop/ui/tests/perf/README.md` with `--engines webkit-cpu,webkit,webkit-shm` on WebKitGTK 2.54.2, with `WEBKIT_SHOW_FPS=1` for the engine's own compositor rate, and an rAF counter. This also answers the "blank window" question on the current version.
   - Cost: low. Decides everything below.
2. **Stay on WebKitGTK and remove the three software limits (days).** (a) Add the 60-fps-preference switch to the host, opt-in (`HYPOTAXIS_HIGH_REFRESH=1` or a Settings > General toggle, off on battery/power-saver); (b) stop running the owner on `DISABLE_DMABUF` once step 1 shows the GL path works on 2.54.2, and teach `renderer.rs` that Wayland + NVIDIA is no longer a CPU-path case on >= 2.54.2 (the gate is the WebKitGTK version at runtime, e.g. via `webkit_get_minor_version()`); (c) make motion cheap: transform/opacity only on composited layers, springs as sampled `linear()` curves (compositor thread on >= 2.54; `ui/` currently uses none), orbs to an OffscreenCanvas worker (>= 2.46, GPU acceleration in the worker unverified), repaint less. Cost: low to medium, all in our repo; risk: the 8.3 ms main-thread budget at 3600x2250 may still miss, and there is no 2x-raster escape hatch on GTK3.
3. **Accept 60 fps as the guaranteed floor and 120 as best-effort, and say so in Diagnostics** (the harness already reports frame times): if step 1 shows the Timer vblank monitor or a CPU-only renderer is forced by the hardware, nothing the app does lifts it.
4. **Upstream/fallback ideas, only if (2) is blocked by the vblank timer**: a WebKit patch so `DisplayVBlankMonitorTimer` uses the GDK monitor's real rate (the Turntable reporter proposes exactly that; `DisplayVBlankMonitorTimer.cpp:41` hard-codes 60) is small but is upstream work and a distro wait. Not recommended as a plan.
5. **Tauri 3 alpha + CEF: not now (weeks of work, wait for beta and native Wayland).** It would remove the 60 cap and give GPU raster, but on Linux it is alpha, forces X11/XWayland (verified in the crate source), adds hundreds of MB, and moves the whole plugin set to an alpha line. Revisit when Tauri 3 is stable and `tauri-runtime-cef` supports native Wayland, and only if step 1 proves WebKitGTK cannot get there.
6. **Electron: do not.** It solves nothing the CEF option does not, replaces the Rust-host architecture (ADR/AGENTS authority model), and has the same NVIDIA + native Wayland GPU-process problems in 2026 reports.
7. **GTK4 `webkitgtk-6.0`: not available through Tauri/wry**, and would not lower raster cost anyway (integer page scale). No action.
