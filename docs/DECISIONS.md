# Architecture decisions

Each record has a context, the decision, and its consequences. A superseded record stays and points to its replacement.
Records before ADR-0028 name the product *hypotaxis*, its name when they were written; they are history and are not rewritten (ADR-0028 says what changed).
Evidence for 0001–0010: `research/hermes.md` (Hermes v0.23.2 read from source), `research/audit.md` (first-pass code), `research/contraprova.md`, `research/formats.md`. These are kept with the W0 spec notes.

## ADR-0001 Hermes's organisational model
**Context.** The owner's constraints:
- Hermes updates must flow in;
- every Hermes plugin, skill and custom code must work unchanged;
- the harness should be organised the way Hermes is.

Hermes's rules are "the core is a narrow waist; capability lives at the edges". Its desktop app splits into machine, experience and work authorities, and its wire is generated from OpenRPC.

**Decision.**
- Adopt all three: edges only, three authorities (host, UI, Hermes backend with our plugin), generated contracts.
- Mirror Hermes's repository shape: AGENTS.md hub, per-area AGENTS.md, `plugins/`, `apps/desktop`, `apps/shared`, `skills/`.

**Consequences.** Hermes is never patched. Anything hypotaxis adds must be expressible as a Hermes plugin, a skill, an MCP server or host-side code.

## ADR-0002 No Rust model gateway
**Context.**
- The plan put a Rust gateway with per-provider adapters between Hermes and every model.
- Hermes already ships about 40 provider plugins, prompt caching, models.dev data and the Claude subscription relay (`claude-subscription-directsdk`, official).
- Hermes can use a single endpoint as its only provider by config alone.

**Decision.**
- Model traffic goes through Hermes providers.
- Routing, cost caps and usage accounting live in the hypotaxis plugin, through `post_api_request`, `pre_llm_call` and per-session or per-subagent model selection.

**Consequences.**
- One layer per mechanism.
- We inherit Hermes's provider coverage and fixes.
- Provider-specific features (thinking, tool formats) are whatever Hermes supports.
- Gaps get fixed upstream as pull requests, never in a fork.

## ADR-0003 Governance is a Hermes plugin built on contraprova's Python
**Context.**
- Contraprova (stdlib-only Python) is the measured system.
- The first-pass Rust "kernel" is wire-incompatible, with invented router and lane semantics and no state machine.
- The owner requires the generic harness to keep contraprova's behaviour.

**Decision.**
- The hypotaxis plugin imports contraprova's kernel modules (events, log, projections, contracts, gates, forks, pricing) as a pinned dependency.
- Generalising them is done upstream in contraprova: neutral `ModelRef`/`Usage`/`PriceTable`/`TierLadder`, the extra event types, a portable file lock for Windows.

**Consequences.**
- One implementation of the policy.
- Contraprova's own tools read hypotaxis ledgers.
- The Rust kernel crate is deleted.
- Contraprova gets a small, reviewed set of upstream changes, which need the owner's approval to push.

## ADR-0004 `hx`: one Rust binary for the parts Rust earns
**Context.** Three parts need Rust:
- ship's file transaction must be capability-safe (the first pass had a confirmed symlink escape and lost file modes);
- pack wants ripgrep's crates and tree-sitter;
- OS sandboxing needs native APIs, including AppContainer on Windows.

**Decision.**
- A single binary `hx`, built from library crates `hx-proto`, `hx-pack`, `hx-txn` and `hx-sandbox`.
- It speaks JSON-RPC 2.0 over stdio, and the plugin keeps one warm `hx serve` child per Hermes process.
- The app bundles it, and it installs standalone for plain-Hermes users.
- Reused from the first pass: ship's edit matching and its tests, pack's walker and secret patterns.

**Consequences.**
- Plugin logic stays in Python, next to Hermes. Heavy and unsafe work stays in Rust.
- One process boundary, with a schema.

## ADR-0005 Our own exec kernel
**Context.**
- Hermes's `execute_code` kernel is persistent but synchronous.
- It can call only 7 whitelisted tools.
- It loses state on timeout.

**Decision.**
- An asyncio Python kernel, started inside the `hx` sandbox, talks to the plugin over a private socket, never stdout.
- The plugin executes tool calls with `ctx.dispatch_tool` and `ctx.call_mcp`.
- The S0 spike showed `dispatch_tool` bypasses hooks, middleware and toolset gating; only Hermes's dangerous-command approval still fires. So the plugin runs **its own policy and ledger step** before every kernel-originated call, through the same function `pre_tool_call` uses:
  - one implementation, two entry points;
  - in governed mode, write-capable tools (`write_file`, `patch`, a `terminal` that writes) are denied from exec;
  - shell work inside exec runs through `hx sandbox.run`.
- An interrupt cancels the running cell without killing the kernel. A hard timeout kills it and says so.

**Consequences.**
- `harness.parallel`, tools as functions, `leave_blank`, `diagnostics` and `apple.*` are all possible.
- Every plugin tool is callable from code.
- The user's `Bash` deny and ask rules judge `harness.sh` by the command string the kernel reports, and the kernel runs its own argv: they do not bind exec (a cell can use `subprocess` or `open()` with no `harness.sh` call). The sandbox is the boundary; the rules are an audit trail (security review, 2026-11-19). Network tools called through `tool.call` are refused unless `exec.network` is `on`.

## ADR-0006 Attach to the user's active Hermes profile by default
**Context.**
- "Every Hermes plugin should work" means the user's existing profile, with its plugins, skills, memory and MCP servers.
- Hermes's gateway multiplexes clients per home, as Hermes Desktop does.

**Decision.**
- Attach to the active profile by default.
- Install the hypotaxis plugin there.
- Keep hypotaxis state under `<home>/hypotaxis/`.
- A setting switches to a dedicated profile.
- Teammates are separate profiles.

**Consequences.**
- hypotaxis sessions are visible in the Hermes CLI and TUI.
- Our tools are scoped by `session.create {toolsets}`, so other clients' sessions are unaffected unless they opt in.

## ADR-0007 Per-attempt model selection: a hypotaxis delegation provider
**Context.** The S0 spike (`research/spike-s0.md` 4e, 4f) confirmed two mechanisms:
- `delegate_task` routed by a delegation-provider plugin: `route_task -> {provider, model}`, children in the background;
- `session.mutate {operation: "model"}`, with revision fences and named providers only.

**Decision.**
- **Governed attempts** are `delegate_task` children routed by the plugin's delegation provider (`delegation.backend: hypotaxis`). The provider ignores any tier the model asks for: it reads the task's cascade state from the ledger and returns the next tier's `ModelRef`.
- Children complete in the background and re-enter the orchestrator as a turn, which is contraprova's own orchestrator loop: the orchestrator reads the gate verdict and calls `dispatch` again or stops. The tier is always the plugin's choice.
- **Pinned models** (Smart off) and ungoverned sessions use `session.mutate` with named providers. The host and plugin never use the bare `custom` provider.
- Every provider hypotaxis configures is a named entry under `providers:`.

**Amendment (after implementation, 2026-11-18).** Escalation happens in the plugin, not through the orchestrator:
- On a worker's `subagent_stop`, the plugin reads the gate verdict from the ledger and launches the next tier itself (`delegate_task`, routed by the delegation provider).
- A blocked attempt's completion is vetoed in `pre_llm_call`, so it costs no model call. The orchestrator is told the final outcome once.
- The orchestrator re-calling `dispatch` was dropped, because escalation must not depend on a model remembering to do it.
- This needs `plugins.isolation: in_process` (Hermes's default); host isolation can't bind the orchestrator's agent from the hook.
- `delegate_task` has no per-task toolsets, so the role policy is the guarantee that workers can't dispatch and orchestrators can't ship.
- A tier's `max_tokens` is recorded but not applied (Hermes's delegation route has no such key).

**Consequences.**
- Escalation works in plain Hermes too, with no model in the loop.
- Interim attempts cost no orchestrator turn.
- The tier ladder and the provider entries must stay in sync. The plugin writes both from one ladder definition.

## ADR-0008 Ledger format is contraprova's
**Decision.**
- The envelope `{seq, type, actor, ts, payload, prev_hash, hash}`, `seq` from 0, a SHA-256 over the canonical JSON of the whole envelope, and a locked, verifying, validating, fsyncing single writer.
- Harness event types are added to contraprova's vocabulary (`docs/LEDGER.md`).
- Verification on append is incremental (tail hash plus a periodic full verify), to meet the 5 ms budget.
- A golden log is shared by both repositories.

## ADR-0009 UI is the v6 design system, ported to TypeScript
**Context.**
- The owner approved the v6 mock-up: a vanilla module system and component library, keyboard-first, accessible, themeable.
- The first-pass React UI implements a design the owner rejected.

**Decision.**
- Port v6's modules and `HX.ui.*` library to typed ES modules with Vite and no framework. Delete the React UI.
- Keep `orbMath`/`LivingOrb` only if the orb2 web component does not cover them (it does today).
- Reuse `@hermes/shared`'s gateway client (MIT) behind a Tauri-IPC transport.

**Consequences.** No redesign and no re-implementation of approved behaviour. The mock data layer is replaced by live streams.

## ADR-0011 Hermes desktop plugins come later
Hermes desktop plugins (`plugin.js` against `@hermes/plugin-sdk`) are React and Electron-specific. Phase 3 hosts a compatible subset of the SDK in a sandboxed pane. Until then, the Python halves of unified Hermes plugins work and their desktop halves are listed but not loaded.

## ADR-0013 Claude Code hook commands run as shell strings
**Context.** STANDARDS section 5 forbids building shell strings. Claude Code hook commands *are* shell strings, and compatibility requires running them unchanged.

**Decision.** Translated hook commands from Claude Code settings and plugins run through the platform shell (`sh -c`, `cmd /c`). Conditions:
- only after the user trusts the project or plugin (content-hash pinned);
- with an allowlisted environment plus Claude Code's documented variables;
- with the hook's timeout, clamped to Hermes's callback limit;
- with an output cap;
- with the project root as cwd.

They're not sandboxed, matching Claude Code. This is the only exception to the no-shell-string rule.

**Addendum (security review, 2026-11-19).** The tools a hook runs load project files outside the hash (`package.json` scripts, lint and format configs, a `Makefile`, `conftest.py`), and the agent writes the workspace through `ship`. So a ship that touches such a file, or a hook's own script, switches the project's trusted hooks off and asks the user again (`compat/rearm.py`); the list of files is data and a heuristic. Sandboxing hooks like the gate was considered and rejected: formatters must write the workspace and notifiers reach the network, which are the Claude Code behaviours this ADR exists to keep.

## ADR-0014 Direct tool surface: tool_search off in hypotaxis sessions
**Context.**
- Hermes defers every plugin and MCP tool behind three `tool_search` bridge tools unless `tools.tool_search.enabled: "off"` (`tools/tool_search.py`).
- No plugin flag exempts a toolset.
- Governed and ungoverned sessions must show `pack`, `exec`, `ship` (and `dispatch`) directly.

**Decision.**
- At setup, with the user's consent, hypotaxis sets `tools.tool_search.enabled: "off"` in the profile it uses, and explains the effect: other clients of that profile see plugin and MCP tools eagerly too.
- If the user declines, hypotaxis offers a dedicated profile (ADR-0006's alternative).
- We open an upstream Hermes pull request for a per-toolset "direct surface" declaration (manifest or `register_tool` flag). Once it ships, the global switch is dropped.

## ADR-0015 contraprova is vendored by exact copy
**Context.**
- The plugin needs contraprova's kernel modules.
- Contraprova isn't on PyPI.
- Hermes admits plugin dependencies only through its package manager, which may not accept git URLs.

**Decision.**
- `plugins/hypotaxis/_vendor/contraprova/` holds an **exact copy** of contraprova's engine modules at a pinned commit, written by `scripts/vendor-contraprova.sh <sha>`, with the commit SHA and licence recorded in `_vendor/contraprova/VENDOR.json`.
- CI re-fetches that commit and fails if the copy differs by a single byte.
- Changes are made upstream and re-vendored, never edited in place.

**Consequences.** No fork can drift. The plugin installs with no external Python dependency.

## ADR-0016 Shared data files are copied, never re-typed
**Decision.**
- `errors.json` (from `crates/hx-proto`), `redact.rules.json` and `never_pack.json` (from `crates/hx-pack`) and `protected.default.json` (from `crates/hx-txn`) have one source of truth each.
- `scripts/sync-shared-data.sh` copies them into the plugin package, so the plugin installs standalone.
- CI fails if a copy differs from its source.
- Codes the plugin owns (`hx.config.*`, `hx.policy.*`, `hx.mode.*`, `hx.ledger.*`, `hx.budget.*`) are added to `crates/hx-proto/errors.json`, not kept in a second catalogue.
- **Exception:** the redaction rules are not copied. Hermes's plugin-install security scan rejects a file of secret-matching patterns, so the plugin redacts by calling `hx` (method `redact.apply`). The rules keep a single implementation, in Rust.

## ADR-0017 Sandbox mechanisms per OS
**Context.** ARCHITECTURE section 7 named bubblewrap, Landlock and seccomp for Linux, Seatbelt for macOS and AppContainer for Windows. The `hx-sandbox` work settled the details.

**Decision.**
- **Linux:** Landlock (ABI 3 or later, probed at runtime) for the filesystem, seccomp for network syscalls and a syscall deny-list, and a private network namespace for loopback-only. Every child also gets `setsid` plus `killpg`, a PID namespace when user namespaces allow it, `no_new_privs`, dropped capabilities and rlimits. There's no bubblewrap and no setuid helper.
- **macOS:** a Seatbelt profile run through `sandbox-exec`, with paths passed as parameters, ported from Codex (Apache-2.0, notice kept).
- **Windows:** a per-run AppContainer with filesystem ACLs and capability SIDs for the network, plus a kill-on-close job object with limits. This beats Codex's dedicated-user design for us: no elevated setup, and reads are actually blocked.
- **Fail closed everywhere:** a dimension the platform can't enforce returns `hx.sandbox.unavailable` unless the policy explicitly accepts degraded enforcement, and every run reports what was enforced. A host allowlist the OS can't enforce falls back to network off. A real allowlist comes later through a host-side proxy.

**Consequences.** Linux is verified with real processes in CI. macOS and Windows compile in CI and are verified on real machines before release (`crates/hx-sandbox/tests/{macos,windows}.rs`).

## ADR-0018 Homes and vaults: multi-device and user-owned cloud
**Context.** The owner wants sessions on any device (desktop, a phone app, other machines), stored in infrastructure they choose: Google Drive, OneDrive, S3, R2, B2, WebDAV, SFTP, a hosted server, a local server or a drive.

**Decision.** Two separate concepts.
- **A home** is where the work runs: Hermes, the plugin, `hx` and the workspace. Only a machine that can run programs can be a home: the desktop (default), a home server, a VPS, a cloud VM.
  - Every device attaches to the home over `hermes-gateway-v1`, which Hermes's own desktop already does for remote backends (SSH, URL plus token).
  - Transports: SSH, a tailnet (Tailscale or WireGuard), a Cloudflare Tunnel, or TLS with per-device tokens, which are revocable and kept in the OS keychain.
  - There is exactly one live home per Hermes home directory (Hermes's rule).
- **A vault** is where the data rests: any storage the user picks, reached through **Apache OpenDAL** (Rust, Apache-2.0), which covers S3-compatible stores, Google Drive, OneDrive, WebDAV, SFTP and the local filesystem.
  - Data is encrypted on the device before upload, with the key in the OS keychain.
  - The vault holds **snapshots, not live files**: Hermes state through `hermes backup`; ledgers, which are append-only and hash-verified so they sync safely; artifacts and settings.
  - A lease file in the vault names the live home, so a second machine can take over only after the lease is released or expires. That makes a "travelling home" possible.
- **Clients:**
  - the desktop app;
  - a phone app from the same UI through Tauri v2 mobile (Android directly; iOS through the macOS VM path or a rented Mac);
  - a web client served by the home.
  Hermes's chat platforms already reach phones meanwhile.

**Seams built now (phase 1):**
- The host's gateway connection is an endpoint abstraction, `Local` (ensure/attach) or `Remote` (URL plus token, SSH, tailnet), behind one interface.
- The UI never assumes it runs on the home's machine: paths are home-relative, and file pickers and opening files go through the home.
- Everything hypotaxis persists (ledgers, artifacts, the price cache, settings) goes through one storage interface, so a vault can mirror it.

**Phases.** Remote homes and vault backup and restore are phase 2. The phone app is phase 3.

## ADR-0019 Cloud sessions run the whole stack in a sandbox you own
**Context.**
- The owner wants a "cloud session" option beside local sessions, like Claude Code's: it keeps running with the laptop closed, opens from any device, and can't touch the computer unless allowed.
- Research (`research/cloud.md`) compared two options:
  - (a) the whole Hermes gateway, plugin and `hx` in an ephemeral sandbox;
  - (b) Hermes's terminal environments, which only move tool execution, so the session dies when the laptop does.

**Decision.**
- Build (a), as specified in `docs/CLOUD.md`:
  - the cloud image (official Hermes image + plugin + `hx`);
  - a self-hosted control plane `hx-cloud` (environments, sessions, device sign-in, relay, queue, secrets);
  - runners behind a sandbox-provider interface, Docker first;
  - an egress proxy that injects credentials so no key lives in the sandbox;
  - a git proxy limited to the session's branch prefix;
  - the session store on the user's vault (ADR-0018).
- Handoff between local and cloud forks; it never shares a live session.
- Remote Control lets a cloud session use an approved folder on the user's computer through the desktop host.
- (b) stays available as a Hermes setting ("remote tools"), not as a cloud session.
- This refines ADR-0018: a cloud session is an ephemeral home; a persistent remote home is a cloud environment with no idle timeout.

**Consequences.**
- Phase 1 builds only the seams: the `Cloud` endpoint kind, headless-safe plugin and `hx`, checkpoint pushes, one storage interface.
- The control plane is the one internet-facing component the user runs, so it gets the strictest review.

## ADR-0020 Forms: one schema-driven card for every request to the user
**Context.** The owner's rule: usability first. Nobody should leave the app to set up keys or settings when the agent or a teammate could send a form. Claude Code shows how: a credential card that saves and wires the key without the model seeing it, multiple-choice questions, permission prompts, plan approval, environment-change approvals, trust prompts, sign-in. Hermes has its own interactive requests (clarify, approval, secret, sudo, vault), and MCP has elicitation.

**Decision.**
- One form primitive (`docs/FORMS.md`): MCP elicitation's schema plus hypotaxis extensions (secret, multi-select, other, previews, pickers, upload, sign-in, hold-to-approve), drawn by one renderer in the card family.
- `kind` templates decide where the result goes: credential, question, approval, permission, signin, setup, connector, choice, plan, feedback.
- Hermes's requests and MCP elicitations are adapted onto it. Agents and teammates send forms through `request_input`.
- Secret values go from the UI to the host and on to the keychain or control plane, never to the agent, the transcript, the ledger or logs.

**Consequences.**
- New needs become a new `kind` (a template plus an effect), never a new component.
- The owner designs the visual family as an extension of the approved cards.

## ADR-0021 Automation: reuse Hermes's drivers, one capability and grant model for every tool
**Context.**
- The owner wants agents, on any model, to operate other programs and browsers (not only Chrome), and wants one way to give them permission across many tools.
- Research (`research/automation.md`) found the following.
  - Hermes already ships the drivers:
    - `browser_exec`: Chromium over CDP, model-written Python;
    - `browser_vault`;
    - a real-profile copy;
    - `computer_use` on cua-driver: the accessibility tree plus screenshots, for any tool-calling model;
    - camofox.
  - Its approvals leave three gaps:
    - no approval or per-site grant for `browser_exec`;
    - `computer_use` grants keyed by action, not by app;
    - MCP trust is binary.
  - Firefox has no CDP, so Hermes can't drive it. Claudezilla and Mozilla's BiDi server can.
  - Claude in Chrome needs an Anthropic plan, so it isn't model-agnostic.

**Decision.**
- Build no drivers. Reuse Hermes's first, then add MCP servers where Hermes has none: Chrome DevTools MCP for the live Chrome, Claudezilla and firefox-devtools-mcp for Firefox. Build only the policy, cards, ledger records and revocation (`docs/AUTOMATION.md`).
- **One vocabulary of capabilities** for every tool, mapped from tool names by a data file:
  - `web.read`, `web.act`, `web.script`, `web.identity`;
  - `desktop.observe`, `desktop.act`, `desktop.display`;
  - `app.<server>`, `fs.*`, `secret.use`, `net.egress`.
- **Grants:**
  - each grant has a subject (an origin, an app, a folder, a server and tool) and a scope (once, turn, session, always), with expiry;
  - grants only narrow down the layers;
  - a project can't grant reach;
  - each teammate has its own grant set and browser identity.
- They're enforced by the one permission function, `hypotaxis.policy.check`, which both the `pre_tool_call` hook and the exec kernel call.
- **Protected action classes** always ask, whatever the grants say: spend, send as the user, irreversible delete, credentials, download and run, upload, authorise, account creation, identity upgrade, script injection.
- **A short never-allowed list:**
  - CAPTCHA bypass;
  - input to OS security prompts;
  - Hermes's hard-blocked key combinations;
  - cloud metadata addresses.
- Content from pages and screenshots can never create or widen a grant. A taint rule escalates the outbound classes after untrusted content arrives.
- Permissions reach the user as forms (ADR-0020): `permission`, `approval`, and `signin` as a takeover under Hermes's control lease.

**Consequences.**
- A1 (capability map, grant store, policy step, cards, ledger, revocation) covers every tool at once. The per-driver work after it is thin.
- `grant.decided` and `grant.revoked` go upstream into contraprova with `form.*`. Until then, they're written as `tool.called`.
- Four spikes come first: one card instead of two for `computer_use`; native-Wayland capture on Arch; an agent-owned display; DevTools MCP annotations.

## ADR-0022 Claude Code mods run unchanged in a sandboxed runtime and draw through the design system
**Context.**
- The owner wants Claude Code mods to work in hypotaxis, compatible and looking right.
- A mod is a plugin whose JavaScript or TypeScript module hooks Claude Code's events, calls a `$` API, and draws element trees into panes, a band above the prompt, toasts, a status line, transcript rows, a backdrop and Claude Code's own message views (`research/mods.md`).
- Mods run inside Claude Code, unsandboxed, and no public spec covers running them anywhere else.

**Decision.**
- Implement the mods API from the docs (`docs/MODS.md`), as a new `hx-mods` library in the `hx` binary:
  - an embedded JavaScript engine and a TypeScript/JSX transform, chosen by a spike;
  - one isolate per session, inside `hx-sandbox`, whose only way out is `$`.
- The plugin maps Hermes's hooks and the gateway's events onto mod events, through the same bridge as Claude Code's hooks. Every `$` call is decided by `hypotaxis.policy.check`, with the mod as principal.
- Element trees travel to the UI as data, and one component draws them with the v6 library. Theme keys and colour names map onto semantic tokens, and each mod surface maps onto an app surface.
- Report `surface: 'desktop'`. Headless sessions run hooks and draw nothing, as `claude -p` does.

**Consequences.**
- Compatible but stricter than Claude Code: `$.fs`, `$.http`, `$.process`, `$.mcp` and `$.model` calls can ask, through forms, where Claude Code would let them through.
- New surfaces (the band above the composer, mod panes, the mod status line, placed rows, the mod origin) need the owner's design in v6 first.
- A conformance suite against pinned public mods tracks support per Claude Code version.

**Update 2026-11-19, spike M0.** The engine is QuickJS-NG through `rquickjs`, and the transform is `oxc`. Boa has no wall-clock interrupt or heap limit; V8's prebuilt library alone is about 40 MB against a 4.35 MiB delta here. Isolate start plus three mods took 2.7 ms (budget 50 ms), an event 7 to 48 microseconds (budget 1 ms). Evidence, deviations from the docs and the risks for M1 (a shared realm, an in-process isolate, synchronous host calls): `docs/MODS.md` section 8.

**Update 2026-11-19, M1.** Three of the spike's open risks were decided and built (`docs/MODS.md` section 9):
- **One QuickJS context per mod** in the session's runtime, the chain in a context of its own, JSON messages between them, intrinsics frozen. The heap limit is still the runtime's, shared; QuickJS cannot account per context.
- **The runtime runs in an `hx mods-worker` process inside `hx-sandbox`**, reached through an inherited socket pair, with no unsandboxed fallback (Windows has none yet: mods are off there, with a reason). Alternatives rejected: in-process (a memory-safety bug in the engine would hold `hx`'s authority), and a runtime per mod (separate heaps but a process or runtime each; kept as the answer if the shared heap or a shared worker proves too weak).
- **Host calls are asynchronous**, and `hx` sends requests to the plugin (`mods.call`): `hx serve` binds a `Link` to its writer. Alternative rejected: a long-poll method the plugin calls for pending `$` calls, which is more machinery and adds a round trip to every call.
The decision of every `$` call is `policy.check` with the mod as principal; the bridge for Claude Code hooks also delivers mod events.

**Update 2026-11-19, M2a.** The runtime runs **one worker per mod**, and the chain runs in `hx` (`docs/MODS.md` section 11). Measured before building it: about 10.6 MiB resident and 12 ms to spawn and load per worker, at 1, 5 and 20 workers (release), under the 15 MiB and 150 ms bar. The alternative (a runtime per mod in one worker) would have left risk 3, a memory-safety bug reaching other mods' authority, open. The plugin restarts a worker that ends, with a backoff of 1, 5 and 30 s, and starts a replacement before the sandbox's one-hour ceiling.

## ADR-0023 One self-contained app: Hermes ships inside it
**Context.**
- The first build asked the user to install Hermes with a terminal command before running the app.
- The owner: it must ship as a single app with its own installer. Building on Hermes stays (ADR-0001): its plugins work and its updates flow in.
- Hermes is MIT-licensed, so bundling it is allowed with its notice.

**Decision.**
- Each installer carries:
  - a pinned, unmodified Hermes;
  - a private, relocatable Python runtime;
  - `hx`;
  - the plugin.
- On first run the host unpacks the runtime, checking its hash, into the app's data folder, with a private `HERMES_HOME`. No terminal, no separate install, and no contact with any other Hermes on the machine.
- One updater ships the app and the runtime together, and a Hermes release reaches users only after CI passes on it. Hermes's self-update is off inside the bundle.
- Large optional pieces (Chromium for automation, the desktop-control driver, Node) are downloaded on first use, with consent, into the private home, through Hermes's own package manager.
- Pointing the app at an existing Hermes stays as an advanced setting.

**Consequences.**
- The release pipeline builds the runtime per platform, and the end-to-end tests run against that same artifact, so CI tests what ships.
- Installer size grows by the runtime's size, so its footprint is measured and kept lean.
- Signed updates need an update-signing key, which the owner creates and stores as a CI secret. It never goes in the repository.
- ARCHITECTURE §4 is amended: the earlier plan had the host run Hermes's installer on the user's machine.

**Amendment (what was built).**
- The runtime is Hermes's own sealed payload (the layout its desktop app and Docker image use), made by calling its build functions (`scripts/bundles/native.py`, `scripts/build/agent.py`), not by a script of ours that copies their results: `tools/` holds python-build-standalone and uv at the pins in `pm/lock.json`, `pm-runtime/` the package manager's own environment, `venv/` the locked dependencies, `manifest.json` the layout. A first version without `pm-runtime` could not enable the plugin.
- Why Hermes's layout: every path is found relative to the payload, so the directory works unpacked anywhere (proved by `scripts/verify-runtime.sh`), and a sealed payload's package manager puts what it downloads on first use in `<HERMES_HOME>/tools`, not in the replaceable runtime folder.
- Hermes's self-update is off by two of its own mechanisms: the install stamp (`distribution: desktop-app`, `updateMechanism: external`, written by Hermes's `write_install_stamp.py`) makes `hermes update` refuse, and `updates.check: false` in the private home's config (key read in `hermes_cli/source_check.py` and `update_cmd.py`) stops the passive check.
- Two crates join the host: `tar` and `zstd` (MIT or Apache-2.0; `zstd-sys` builds the BSD-licensed C library), to unpack the archive in the host without a system `tar` or `zstd` (Windows has neither).
- The host keeps the choice of Hermes in one pure function: the bundled runtime unless `HYPOTAXIS_HERMES=existing` (or `hermes_source` in `settings.json`) says otherwise; a build without a runtime uses the Hermes on the machine, and a broken `runtime.json` is a setup error.

## ADR-0024 The host picks WebKitGTK's renderer from evidence, never blanket
**Context.**
- Tauri draws with WebKitGTK on Linux. Its renderer is chosen by environment switches read when the web view is created: `WEBKIT_DISABLE_DMABUF_RENDERER` (shared-memory buffers instead of DMABUF), `WEBKIT_DISABLE_COMPOSITING_MODE` (no accelerated compositing), `__NV_DISABLE_EXPLICIT_SYNC` (NVIDIA on Wayland).
- They cure a blank window or a crash on some NVIDIA setups (WebKit bugs 259644, 261874; Tauri's Linux graphics guide). They cost frames wherever the default works, and Tauri's own guide says not to ship them unconditionally.
- They are not equivalent. Checked on WebKitGTK 2.52.6 with `webkit://gpu`: `WEBKIT_DISABLE_DMABUF_RENDERER=1` makes the acceleration policy `never` (no GL context, the CPU paints every frame), while `WEBKIT_DMABUF_RENDERER_FORCE_SHM=1` keeps policy `always` and GL compositing and copies frames through shared memory. Ubuntu ships a patch that forces that shared-memory transport for NVIDIA (2.52.6-0ubuntu0.24.04.2).
- The owner's laptop is a hybrid NVIDIA machine on Hyprland (Wayland, scale 1.6) and runs with `WEBKIT_DISABLE_DMABUF_RENDERER=1` from the start: so it paints on the CPU at 3600x2250 buffer pixels. The frame drops measured there (see `apps/desktop/ui/tests/perf`) are largely the page's work in that path.

**Decision.**
- `renderer.rs` probes the GPUs (`/sys/class/drm`: vendor, bound driver, boot display), the session type and the compositor, and decides before any thread starts. It is a pure table, unit-tested.
- Automatic rule: only the NVIDIA proprietary driver as the display GPU (or as the GPU the app renders on, ADR-0025) on X11 gets `WEBKIT_DMABUF_RENDERER_FORCE_SHM=1` (the GPU stays). A hybrid machine whose display is the integrated GPU, any other vendor, and any Wayland session are left to WebKitGTK. On Wayland with NVIDIA the rule takes the runtime WebKitGTK version into account: from 2.54.2 (the GTK 3 explicit-sync fix, WebKit bug 324551) the machine gets the default GL renderer and the rule says so (`nvidia_wayland_fixed`); before that, or when the version cannot be read, the rule is the one above (`nvidia_wayland_untouched`). Both set nothing; the version changes the reason in the log and the report, and the report's note names a CPU-painting switch that is set in the environment.
- The version is read from `libwebkit2gtk` at run time (`webkit_get_major_version` and its siblings, through `dlsym`), not from what the build linked: the AppImage carries its own copy.
- `HYPOTAXIS_RENDERER=auto|default|shm|cpu|nosync|software` is the owner's explicit choice (`shm` is `FORCE_SHM`, `cpu` is `DISABLE_DMABUF_RENDERER`). A WebKit or NVIDIA switch already in the environment wins over everything.
- The decision is logged at startup. Settings > General > Diagnostics copies a report (session, GPUs and drivers, rule, environment, the page's size and `devicePixelRatio`) and opens WebKitGTK's `webkit://gpu` page in its own window, with no access to the host's commands.
- `set_var` is an `unsafe` call (`#[allow(unsafe_code)]` with its SAFETY note): it runs first in `run()`, before the logger, tokio or Tauri start a thread. ADR-0025 adds the same call for the GPU rule and one `dlsym` block.

**Consequences.**
- No machine pays for a workaround it does not need. A machine that does need one sets a variable and sends the report.
- Wayland plus NVIDIA is not auto-fixed: the evidence is crashes and blank windows, which the host cannot see in advance. The diagnostics and the variable make the fix one step.
- Distribution patches differ (Ubuntu forces the shared-memory transport for NVIDIA in 2.52.6; Arch's package is not known to), so the report, not an assumption, says what a machine does.

## ADR-0025 Motion at the display's refresh rate: compositor-driven, WebKit's 60 fps cap lifted, current WebKitGTK
**Context.**
- The owner's panel runs at 120 Hz and they want 120 fps with no stutter. The research (`research/120hz.md`, read in WebKitGTK's source) found three limits.
  - **WebKit's 60 fps preference:** WebKit caps `requestAnimationFrame` and page rendering updates to 60 fps on fast displays by default (`PreferPageRenderingUpdatesNear60FPS`). It can be turned off from the host (`webkit_settings_set_feature_enabled`).
  - **The renderer:** only the GL renderers (DMA-BUF, or shared memory) run `transform` and `opacity` animations on the compositor thread. The CPU renderer the owner was forced into paints every frame on the main thread.
  - **The WebKitGTK version:** the GTK3 explicit-sync crash with NVIDIA on Wayland is fixed in WebKitGTK 2.54.2 and later, and CSS `linear()` easing only stops forcing main-thread animation in 2.54.
- GTK3 on Wayland renders a 1.6 scale at 2x (3600x2250 here). Tauri has no GTK4 port, and Tauri's Chromium runtime is a Tauri 3 alpha that runs under XWayland.

**Decision.**
- **Lift the cap:** the host turns WebKit's 60 fps preference off on displays faster than 60 Hz, with a setting to force 60.
- **Renderer rule:** the renderer rule (ADR-0024) takes the WebKitGTK version into account. On 2.54.2 and later, Wayland with NVIDIA gets the default GL renderer, not a workaround.
- **Motion:**
  - motion runs on the compositor: `transform` and `opacity` only, springs as `linear()` curves or Web Animations;
  - the orbs draw in an OffscreenCanvas worker where the engine supports it;
  - STANDARDS §6 makes the display's full rate the budget, with 60 fps as the floor only where the machine forces it.
- **Packaging:** ship on a current WebKitGTK.
  - Arch gets a native package that uses the system's WebKitGTK (2.54.2 or later).
  - The AppImage's bundled WebKitGTK version is reported in Diagnostics and raised as builds allow.
- **Frame rate setting:** `HYPOTAXIS_FPS=auto|60|max`. `auto` (the default) turns the preference off when GDK reports a refresh rate above 60 Hz for the window's monitor, `60` keeps WebKit's default, `max` always turns it off. The cap is only ever lifted. The preference is reached through `webkit_settings_set_feature_enabled`, resolved with `dlsym` and called only after the runtime version (2.42 or later), the symbols and the feature's existence are checked; the host reads the value back and Diagnostics reports it.
- **GPU rule:** `HYPOTAXIS_GPU=auto|integrated|dedicated`, also in Settings > General (saved, applied at the next start; `HYPOTAXIS_GPU` overrides it). `dedicated` is PRIME render offload to the NVIDIA GPU: the environment that switcheroo-control advertises for the discrete GPU (`net.hadess.SwitcherooControl`, read with `busctl` in a child process so no thread starts before the environment is set), else NVIDIA's documented `__NV_PRIME_RENDER_OFFLOAD=1`, `__GLX_VENDOR_LIBRARY_NAME=nvidia`, `__VK_LAYER_NV_optimus=NVIDIA_only`. Only GPU-selection variables are taken from the service. The host sets no EGL vendor file and no `WEBKIT_WEB_RENDER_DEVICE_FILE`: WebKit takes the DRM render node from its EGL display, and NVIDIA documents `__NV_PRIME_RENDER_OFFLOAD=1` as enough for an EGL client. A GPU-selecting variable already in the environment wins, and then the host sets none.
  - `auto` offloads only on AC power (a `Mains` supply online in `/sys/class/power_supply`), with a separate NVIDIA GPU whose proprietary driver is bound, a runtime WebKitGTK of 2.54.2 or later and a known session type. On battery, with an unknown power source, with an older or unreadable WebKitGTK, or with no such GPU it uses the integrated GPU (it sets nothing).
  - `dedicated` is allowed on an older WebKitGTK and warns in Diagnostics that it may crash or stay blank on Wayland. It supports the NVIDIA proprietary driver only.
  - The GPU is fixed when the process starts. If the power source changes, Diagnostics and Settings offer "Restart to switch"; the app never switches silently.
  - When offload is on, the renderer rules (ADR-0024) judge the NVIDIA GPU, not the display one.
  - Diagnostics reports the GL renderer the page really gets (WebGL's unmasked renderer string, which goes through the web process' EGL display), the power source, and what was requested.
  - `docs/research/120hz.md` section 4.3 advises against forcing offload as a fix for blank windows (a cross-GPU copy, the dGPU awake for a light UI, NVIDIA's EGL path). This rule is the owner's choice for a demanding app, and `auto` is gated on the fix for that path.
- **Not now:** Chromium (Tauri 3 alpha with CEF). Revisit when it reaches beta with native Wayland.

**Consequences.**
- The perf harness measures at the owner's geometry, and its numbers gate motion changes.
- A machine stuck on the CPU renderer or WebKit's fixed 60 Hz timer gets a smooth 60, said plainly in Diagnostics, never a stutter at an unreachable 120.

**Addendum (the dock's orbs stay in one layer, `w26/dock-orbs`).**
- An `<orb-avatar>` in the worker draws on an OffscreenCanvas the worker owns. WebKitGTK drops the picture of such a canvas that is taken out of the page and put back until the worker's next commit (4 of 40 shots blank in a real WebKitGTK under Xvfb; forcing a redraw on reconnect does not help, and WebKitGTK has no `moveBefore`). The dock moved each live orb into the slot of the view showing (`relocateLive()`), so its orbs blinked empty whenever they changed place: opening a bot, expanding, minimising.
- Now every live orb is connected once, in one `.dk-orbs` layer inside the Bots page (`modules/dock/layer.ts`), and follows its slot by transform. A view holds an empty slot. The orb is two elements so no two motions write one property: a `.dk-op` point (`transform`: the slot's place at rest, the row's magnification, the roster's scroll, written from what the engine already knows, with no layout read in a frame) and the live orb itself (`transform`, `opacity`: the slot's FLIP and entrance, played again as Web Animations with the same keyframes). The layer is inside the page's section, so a page that slides or fades takes its orbs along, and the stage's sink and clip apply to them. Motion stays transform and opacity only.
- A card that moved between two views took its origin orb with it, so a wait's compact card now has one element per place that shows it (the key `card:<id>:<size>` is shared, so the morph still carries one to the other). The one in the session is marked `data-mirror`, and the cards module does not count it in `hx:attention`: it is the same ask, not a second one.
- Guards: the lab's `orbs: 'stay'` is on for every dock interaction, and `tests/e2e/dock_webkit.py` looks for lit pixels over each orb in a real WebKitGTK.

## ADR-0026 The terminal art is data, with one renderer per language that cannot link the others
**Context.**
- boopis has three terminal faces: the installers (`install.sh` for Linux and macOS, `install.ps1` for Windows), the app's own binary (`boopis --version`, `boopis doctor`) and the Arch package's install script. All three show the logo and the bots.
- The installers run from a pipe, so they are one file each and cannot read the repository. The host is Rust. A shell, PowerShell and Rust cannot share code.

**Decision.**
- **The art exists once, as data:** `packaging/brand/boopis.art` (pixel grids, palette, scenes, animation frames), a line-based text format. The wordmark's pixels are the real logo's outlines sampled on the terminal's pixel grid (a cell is 2x2 pixels, drawn with the quadrant blocks); the bots' colours are `design/v6/data.js`'s.
- **One renderer per language, kept equal by golden files:** the host's (`brand.rs`) is the reference, `render.awk` is what `install.sh` carries, `render.ps1` what `install.ps1` carries. `packaging/brand/golden/` holds what the host draws for every colour level; `scripts/test-brand.sh` checks that awk draws the same bytes. The PowerShell renderer follows the awk one line by line and has no golden test yet (it needs a Windows or PowerShell runner).
- **The installers embed the art** between `>>> brand` markers, written by `scripts/embed-brand.sh` and checked by `--check`, the same pattern as the repository's other generators.
- **Capabilities are read, never assumed:** `NO_COLOR`, `TERM=dumb`, a pipe, `COLORTERM`, `TERM`, the locale, `CI` and `BOOPIS_NO_ANIMATION`, in the same order in all three.

**Consequences.**
- Changing the art is one file and `scripts/embed-brand.sh`. Changing the renderer's rules is three edits and the goldens.
- Alternatives refused: pre-rendered ANSI in the scripts (four colour levels times every frame: large and unreadable); a second art copy per language (drifts); downloading the art at install time (the installer would depend on the repository being reachable and public).

## ADR-0027 Hermes's free models in first-run setup: the Desktop declaration, never `HERMES_DESKTOP`
**Context.**
- The owner wants the models Hermes offers for free to work with no configuration. Research (`research/free-tier.md`, read in Hermes v0.23.2 and checked against a real Hermes) found three facts.
  - **The Nous free tier** is one anonymous model, `nous/welcome`, on its own host. Hermes claims it only for a connection that declared itself the Desktop on this machine (`client.capabilities {desktop_local: true}`, counted only on a ticket from the gateway's private control socket), on a first install, once per OS user. It has no usage gauges; its limits arrive as refusals with a wait.
  - **`HERMES_DESKTOP=1` is not that mechanism.** It changes the session platform, the toolsets every session gets and the system prompt (fixed at `session.create`, invariant 4), the telemetry offer and more.
  - **The browser challenge** is a portal page whose URL fragment (`#working`, `#interactive`, `#done`, `#failed`) tells the host when to show or close its window.
- Whether Nous's Terms let a third-party distribution of Hermes use the anonymous tier is **not stated** anywhere (`research/free-tier.md` section 5).

**Decision.**
- Setup's models question has "Free models (Nous free tier, no account)" first and chosen when no key is present, then "OpenRouter free models" (a `credential` form for the key, then the catalogue's free rows), then the Claude ladder and the named models.
- Choosing the Nous tier makes the host declare its gateway link the Desktop, on that link only and only while that is the choice (`setup/state.rs::free_tier_chosen`, asked on every dial). Hermes makes the claim through its own path (`free_tier.provision`); the host writes no model, key or secret for it, only the governed ladder. `HERMES_DESKTOP` is never set and Hermes is never patched.
- The ladder is chosen at run time. The free tier has one model, so one tier of `nous/<what free_tier.status reports>` at every level, and setup says so. For OpenRouter it is up to three of the catalogue's free models ordered by the size each name states (smallest, middle, largest), and models that state none are offered but not proposed.
- The challenge: the host listens for `free_tier.challenge` on each gateway link, opens the page in a hidden webview window that matches no capability, is pinned to the portal origin, refuses popups and downloads, reveals it on `#interactive` (never for an optional challenge), closes it on `#done` or `#failed`, and reports `free_tier.challenge_result` as a hint. The window sits behind a trait so the flow is tested without a display.
- The plan is shown as Hermes reports it (`free_tier.status`, `model.options`, a refused turn's `error_surface`) and nothing else: no allowance size, no bar where Hermes sends none. A refusal raises a notice that offers "choose another model", which asks setup's models question again.
- `config::FREE_TIER_ENABLED` removes the Nous choice from a build, so the owner can decide the terms question without touching anything else.

**Consequences.**
- The declaration makes Hermes write `onboarding: {run: true}` into the private home and the machine marker under the real `$HOME`, and the claim uses up the once-per-user trial for Hermes's own Desktop app too. The choice form says so.
- The account service sees `surface: desktop` from a client that is not Hermes Desktop; the block is self-reported and proves nothing, but the service cannot tell the two apart.
- `nous/welcome` has no price in the user's price table, so its cost reads unknown (ADR-0012) and a session with a cost cap blocks on it. The host writes no zero for it.
- The mechanism is proved live against a real Hermes without calling Nous (`setup_live`: `enabled` is false to a link that does not declare and true to one that does). The hidden window itself is untested against the real page: no call to Nous is made from tests, and a hidden WebKitGTK page may be throttled (Tauri has no background-throttling control on Linux), in which case the check times out after 90 s as Hermes Desktop's would.

**Owner decision (19 November 2026).** Ship both the Nous free tier and OpenRouter's free models. If problems arise with Nous (terms or service), turn the Nous free tier off with `config::FREE_TIER_ENABLED` and keep OpenRouter.

## ADR-0029 The Claude subscription runs through the user's own Claude Code (owner decision)
**Context.**
- The owner wants boopis to run on a Claude Pro/Max subscription, and has decided it several times. Agents kept forgetting and re-raising Anthropic's rule against third-party apps offering claude.ai login.
- Hermes's official plugin `claude-subscription-directsdk` (Nous Research, `hermes-official-plugins`, pinned in Hermes's plugin catalog) drives the **unmodified, official Claude Code executable**, which the user installed and signed in to themselves (`claude auth login`).
  - The plugin has no credentials of its own and never opens, copies, refreshes or prints Claude Code's credential files.
  - Hermes keeps its own agent loop, tools, approvals and compaction.
- Anthropic's legal page does not prevent "an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code".

**Decision.** boopis offers the Claude subscription as a model choice, through that plugin and the user's own Claude Code. **Owner decision, 2026-11-19. Settled: do not re-raise it.**
- boopis never sees, stores, reads or forwards Claude credentials or session tokens. Authentication belongs to the `claude` CLI.
- boopis never offers its own claude.ai login screen. It shows the user `claude auth login`, the official CLI's own login, and checks the result through the CLI.
- The plugin is installed from Hermes's catalog, pinned, through Hermes (`hermes plugins install`). boopis does not vendor or modify it.
- The ledger marks its usage `subscription: true` (LEDGER.md). Its native cost figure is a list-price estimate, never a charge.

**Consequences.**
- First-run setup and Settings → Models offer "Claude subscription (your Claude Code login)" when `claude` is installed, and say what is missing when it is not or is signed out.
- Anthropic API keys, Bedrock, Vertex and Foundry stay available beside it.

**Partly superseded by ADR-0030** (19 November 2026): the plugin is no longer installed through `hermes plugins install`; it ships inside boopis's runtime, and "Sign in to Claude" runs Claude Code's own `claude auth login`. The rest stands.

**Finding Claude Code on every system, and when it is missing (amendment, 22 November 2026).**
- **Why.** On Windows the owner's first run drew the Claude card red, "failed", with `npm install -g @anthropic-ai/claude-code`, although Claude Code was installed. Two causes, both in the host's lookup: it asked for the variable `PATH` by its exact name, and Windows spells it `Path`, so nothing on the path was ever seen; and npm's default global folder there, `%APPDATA%\npm`, was not among the places it looked. The plugin that runs Claude Code reads the environment through Python, without case, and would have found it. "Not installed" was also drawn as a failure, and the command it showed is no longer Anthropic's recommended install.
- **Where Anthropic's installers put `claude`** (<https://code.claude.com/docs/en/setup> and <https://code.claude.com/docs/en/troubleshoot-install>, read on 22 November 2026): the native installer at `~/.local/bin/claude` on macOS and Linux and `%USERPROFILE%\.local\bin\claude.exe` on Windows, where "it prints the fix ... but doesn't change PATH itself"; npm in its global folder (`%APPDATA%\npm\claude.cmd` by default on Windows, `<prefix>/bin` elsewhere), now the same native binary behind a postinstall step; WinGet as a portable package linked from `%LOCALAPPDATA%\Microsoft\WinGet\Links`; Homebrew and the apt, dnf and apk packages on the system's `PATH`. An older Claude desktop app registers `WindowsApps\claude.exe`, which opens the app.
- **Decision: the lookup.** The plugin's own order first (its override variable, `PATH` with Windows' `PATHEXT`, its `_install_prefixes`), then the places it does not know (`%APPDATA%\npm`, winget's links and package folder, npm's prefix from `~/.npmrc`, the newest nvm Node), never the desktop app's alias, never a relative `PATH` entry or home. It is pure over the system and the file system, so each system's layout is a unit test on any machine. When boopis finds a `claude` the plugin would miss, or the plugin would run the alias, every engine call carries the plugin's own override variable, `CLAUDE_SUBSCRIPTION_DIRECTSDK_COMMAND`, set to that path (`hermes::cli::child_vars`), so setup and the engine run the same file; a variable the person set is never replaced.
- **Decision: the desktop app's built-in Claude Code does not count.** Anthropic: "The desktop app includes Claude Code, so you don't need to install Node.js or the CLI to use the Code tab", and "Want `claude` in your terminal: install the CLI separately" (<https://code.claude.com/docs/en/desktop-quickstart>); its comparison lists scripting (`--print`, which the plugin runs) as "Not available" in the desktop app (<https://code.claude.com/docs/en/desktop>). The app keeps its copy in its data folder's `claude-code/<version>/` (`%APPDATA%\Claude`, the Store build's `Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude`, `~/Library/Application Support/Claude`, `~/.config/Claude`; <https://claude.com/docs/third-party/claude-desktop/data-storage>), replaces it as it updates, and signs it in with the app's own sign-in. Pointing the plugin at it would break at the app's next update and is not a use Anthropic offers. When it is the only Claude Code here, the card says so: "boopis needs the Claude Code command-line tool, which is separate".
- **Decision: the states.** Not installed is its own status, `needs_install`, never a failure: the card says it calmly and shows Anthropic's installer for the person's system (`irm https://claude.ai/install.ps1 | iex` in PowerShell, `curl -fsSL https://claude.ai/install.sh | bash` in a terminal), Copy command, Install guide (Anthropic's page) and Check again. "Failed" is only a Claude Code that was found and did not start (`hx.provider.cli_failed`: the system refused the file, or it was silent for 20 seconds), in plain words with the installer; the operating system's message goes to the log. Too old (`claude update`, with Copy and the update guide) and a login that bills the API (the sign-in button) are steps, said without red. Signed out keeps the sign-in button, which runs `claude auth login --claudeai`; the card's words say "Choose Sign in", which fits the button on every surface (the kit's branded "Sign in with Claude" on the first run and in Settings, "Sign in to Claude" on the setup form). A command in the host's words shows as code in a Settings row too, not as raw backticks.
- **Decision: no button that runs the installer.** It was weighed and declined. The installer is a script fetched from claude.ai at the moment it runs and piped into a shell (`irm | iex`, `curl | bash`); boopis would be running code it cannot check, and it never runs an installer (fail closed, and the host's own rule for `hermes_install`). A visible terminal is not portable: Windows can open PowerShell, but macOS needs Terminal automation (a permission prompt) and Linux has no standard terminal (the owner's Hyprland has none boopis could name). And the installer's own outcomes (the PATH note, an execution policy, a proxy, an antivirus lock) are read best by the person in their own window, next to Anthropic's troubleshooting page. Copy, paste and Check again is one more step and keeps the run the person's own.
- **Proof.** Unit tests for the Windows, macOS and Linux layouts (`claude.rs`), the engine override (`hermes::cli`), every card state (`claude-card.test.ts`), lab stories for every state (first run and Settings). `.github/workflows/claude-cli.yml` installs Claude Code for real on `windows-latest` and `ubuntu-22.04` (macOS on request) with Anthropic's installer and with npm, each with its folder on `PATH` and off it, and checks that the host finds it, reads its version and Claude Code's own `auth status`, and that the plugin's own `_resolve` (at the commit the engine's catalogue pins, in the engine's environment) resolves the same file. First green run: <https://github.com/aphesist/boopis/actions/runs/44970874060> (Claude Code 2.1.330). For the native install and for npm, each off `PATH`, it also starts what the card's sign-in button starts (the host's own `connectors::engine::login_command`: `claude auth login --claudeai` from the file boopis found, the login environment, stdin closed, no console window), checks that Claude Code names Claude's own sign-in page (`https://claude.ai/oauth/authorize?...`) from that file and that the page answers (behind Cloudflare's browser check, which answers a script with 403), then stops it and everything it started. Green on `windows-latest`, `ubuntu-22.04` and `macos-latest`: <https://github.com/aphesist/boopis/actions/runs/44981396954>. Not proven on a machine: WinGet, the desktop app's copy and its alias, and a completed sign-in (the step after the page needs a person and a Claude account).

A real ChatGPT account was not signed in to.

**The ChatGPT sign-in on OpenAI's program (amendment, 21 November 2026, ADR-0039 point 3).**
- **Why.** OpenAI's Sign in with ChatGPT terms for third-party apps took effect on 4 November 2026 (<https://openai.com/policies/sign-in-with-chatgpt-terms/>). boopis signed in with the Codex CLI's client id, which is not a registration of boopis's own. The owner: "there's no application needed, it's built for open source software. add it". He was right, and nothing is left for him to do: OpenAI's open-source flow registers the app itself. The program says (all read on 21 November 2026): "ChatGPT plan usage is available to all open-source partners" and the flow "registers your client and issues OAuth credentials for eligible Responses API requests, without a client secret or partner API key" (<https://developers.openai.com/siwc>, full text <https://developers.openai.com/siwc/llms-full.txt>); the cookbook says it is for "open-source projects, personal projects that run locally, and selected private apps" (<https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt>). Hosted and commercial apps use an interest form instead; boopis runs on the person's own computer.
- **The flow** (<https://developers.openai.com/siwc/token-sharing-open-source/sign-in>): authorization code with PKCE (S256) and OpenID Connect, **not** a device code (the device code in OpenAI's pages is for the Codex CLI on a headless machine only). The first authorization of an installation carries `client_id=dynamic_agent_client`, the app's name `agent_name_hint=boopis` and a stable `ext_agent_host_id` (`urn:uuid:` and a version-4 UUID, chosen and kept before the first sign-in); OpenAI's callback returns the issued `oaiapp_` client id, which is kept and used from then on (and omits the name). Endpoints from `https://auth.openai.com/.well-known/openid-configuration` (fetched on 21 November 2026): authorize `/api/accounts/authorize`, token `/api/accounts/oauth/token`, revoke `/api/accounts/oauth/revoke`, keys `/.well-known/jwks.json`, ID tokens RS256. Redirect `http://127.0.0.1:<port>/auth/callback` (only the port may vary; the host takes 1455 when it is free, else any free port, and never `localhost`). Scopes `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`, `resource=https://api.openai.com/v1`.
- **What the token can call:** the public Responses API, `POST https://api.openai.com/v1/responses` with `store: false` and `stream: true`, and `GET /v1/models`; "do not point it at ChatGPT's `backend-api` endpoints" (<https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference>). Not the Codex backend, not the API's other services ("does not grant extra usage or access to other OpenAI services"), and not Chat Completions. The preview omits some request fields (`max_output_tokens`, `temperature`, `prompt_cache_retention`, and others), hosted tools (file search, image generation, Code Interpreter, hosted MCP, `tool_search`) and audio or video input (<https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations>). Access tokens live an hour; refresh tokens 30 days and rotate (<https://developers.openai.com/siwc/token-sharing-open-source/token-reference>). The plan's five-hour limit is shared across every app on Plus, and the person can cap each app weekly at <https://chatgpt.com/settings/usage>.
- **What the host does** (`chatgpt/`): `oauth` (the wire: PKCE, the authorization address, the exchange, the ID token checked with RS256 against OpenAI's keys by issuer, audience, expiry and nonce, the refresh with `resource` and no `scope`, the revocation), `callback` (a listener on `127.0.0.1` bound before the browser opens, answering only a `GET` of the callback path with the listener's own `Host` and this attempt's `state`, so a stray request cannot end or hijack the wait), `mod` (the service). The host opens the browser itself with the full address (it may carry the retained ID token as `id_token_hint`, which the program asks never to reach a log or a page); the card is given the address **without** it. A sign-in that does not grant `chatgpt.tokens.use.direct` keeps nothing and says so; the next one asks for the consent screen again. The registration (the issued client id, the host id, the account's subject and email) stays across a sign-out, as the program asks, so signing in again reuses the client; a different account than the registration's, or a client OpenAI no longer knows, drops it and registers anew. Sign-out asks OpenAI to end the renewable session (twice at most) and removes the tokens whatever it answers; when OpenAI did not confirm, the person is told, and can disconnect boopis in ChatGPT's settings. Keychain entries (`secret://chatgpt/…`): `access_token`, `refresh_token`, `id_token`, `registration`, and `base_url`.
- **What the engine gets:** still the access token only, through the pool row of `plugins/boopis/signins/chatgpt.py` (now over the shared `signins/pool.py`), and now also the address the token is called on (`secret://chatgpt/base_url`, `https://api.openai.com/v1`). The engine's `openai-codex` provider takes the row's address as it takes any pool row's (`_pool_entry_mode_and_url` keeps it unless it is the canonical Codex URL), speaks the Responses API, and, being the `openai-codex` provider, builds its request the Codex way: from reading `agent/transports/codex.py`, it sends no `max_output_tokens`, no `temperature` and no `prompt_cache_retention` (the fields the preview refuses), and always `store: false`. Verified with a real engine (v0.23.2): `resolve_runtime_provider(requested="openai-codex")` resolves exactly the host's token on `https://api.openai.com/v1` with `codex_responses`. Not verified (no ChatGPT account here): a real turn (so whether OpenAI accepts every other field the engine sends, such as `include`, `reasoning`, `prompt_cache_key` and its `session_id` headers), and the engine's model catalogue (`GET /v1/models` with the token, which the program documents as `{models: [{slug, visibility}]}`, the shape the engine reads).
- **People who signed in before the program were cut off (owner decision, 21 November 2026: "cut it off now, no one besides me used it").** Their Codex-client tokens are no longer renewed and nothing calls the old address. At the next launch or status check the host removes them from the keychain (`ChatGpt::retire_older`: tokens with no issued client and no address) and records `ended: older_route`; Settings > Models and setup show one plain notice that says why and offer Sign in with ChatGPT, and the plugin never hands such a token to the runtime. The older route's refresh code, its issuer path and its base URL are deleted; a test keeps the cut-off itself. This replaces the earlier "keeps working until the person signs in again" rule.
- **Terms boopis keeps:** the plan is used only for boopis (the host never shares a token); tokens stay local, in the keychain, and out of logs; the sign-in button reads "Sign in with ChatGPT", one of the program's two recommended labels; nothing pools, resells or shares plan usage.
- **Tested** (`chatgpt/tests.rs`, `plugins/boopis/tests/test_signins.py`): the flow's ends (approved, a returning account, cancelled, timed out, declined, a stray request, refused, a refused client, an ID token with a bad signature, audience, nonce, issuer or expiry, plan use not allowed, another account), what reaches the keychain, the refresh (renewed, rotated, revoked, client gone, rate-limited) on both routes, sign-out with and without OpenAI's confirmation, the migration, a locked keychain, no secret in a message, an error or a debug print, and the real HTTPS transport against a loopback server (with no redirect followed). **A real ChatGPT account was not signed in to.**

## ADR-0031 boopis is the product; its engine is invisible (owner decision)
**Context.**
- boopis runs on unmodified Hermes, bundled (ADR-0023), and the app said so everywhere: setup's "Hermes runtime" step, "This makes a Hermes profile for jabuti", "Hermes did not answer", raw engine errors ("hermes refused updates.check: OSError: ..."), the "Use my own Hermes" setting, `hermes` in `--version` and `doctor`, the private folder `<app data>/hermes-home/` shown when a bot is made.

**Decision.** boopis is the product. Hermes stays the engine inside, bundled and never patched, and the person using the app never reads its name. **Owner decision, 2026-11-19.**
- **Allowed places for "Hermes":** the repository (README credits, docs, code identifiers, licences and `NOTICE`), and an item the user downloads from the Hermes plugin store whose own name or publisher is Hermes's. That item is the only in-app exception; a component that draws one marks it `data-store-item` (`ui/src/core/engine-words.ts`).
- **The app names the thing, not the engine:** "boopis's engine" where the engine itself is the subject, and better what failed in the user's terms; a teammate is a "bot", never a "profile". Meaning stays exact: boopis never claims to do something the engine does differently. The inventory is `docs/BRANDING.md`.
- **Errors:** one mapper in the host (`error::user_message`) gives every error the UI sees a boopis sentence, a stable `hx.*` code and the next step, from the catalog's new `user` field (`crates/hx-proto/errors.json`, synced to the plugin, read by the UI). The engine's raw words go to the log and to Settings, General, Diagnostics only. The engine's own JSON-RPC answers pass the proxy untouched (frames are never altered), so the UI applies the same catalog's `hx.engine.refused` sentence to an answer without an `hx.*` code (`GatewayError.fromFrame`). Codes that a person reads no longer name the engine: `hx.hermes.*` is `hx.engine.*`, `hx.setup.hermes_missing` is `hx.setup.engine_missing`, `hx.bots.hermes_failed` is `hx.bots.engine_failed`.
- **The private engine home** is `<app data>/engine/` (was `hermes-home/`). The engine has no profile-root override, so a bot's folder keeps the engine's layout inside it, `engine/profiles/<name>`.
- **"Use my own Hermes" leaves the app.** The capability stays for developers, as `boopis --engine existing` and `BOOPIS_HERMES=existing`, documented in `docs/ENGINE.md`. Settings no longer offers it, and the saved `hermes_source` setting is no longer read; `engine_source_get` (read-only) tells the first-run screen which engine this run uses.
- **Guards:** a vitest (`ui/src/engine-words.test.ts`) and a Rust test (`src-tauri/src/engine_words.rs`) fail on the word in any user-facing source literal, with an allowlist for code identifiers, logs, error detail and store items; `cli/tests.rs` checks `--version`, `doctor` and `--help`; `scripts/test-brand.sh` checks the installers and the Arch package. The design system's voice section carries the rule as an owner decision.

**Migration.** `migrate::engine_home`, once, at start, before anything runs from the folder (like ADR-0028's rename):
- `<app data>/hermes-home` becomes `<app data>/engine` with one rename; the absolute paths that its `config.yaml` and each `profiles/*/config.yaml` hold (`hx_path`) are rewritten;
- a gateway an earlier run left serving from the old folder is stopped first (`gateway stop --yes` with the bundled launcher, this build's or the one an earlier build unpacked, then a wait until its control socket is quiet); one that will not stop keeps the old folder for that run only (`runtime::Plan::home`), and the move is tried on the next start;
- when both folders exist nothing is touched and a warning says so; a machine without the old folder is untouched; every step is logged and tested (`migrate/tests.rs`). Nothing reads the old name after the move. The user's own Hermes home is never touched.

**Consequences.**
- The model sign-in flows (setup's models question, Settings > Models, the plan, the Claude subscription) were rewritten in boopis's words when ADR-0030's branch merged with this one; both guards' `PENDING` lists are empty.
- A saved `hermes_source: existing` is ignored after the update: start with `--engine existing` instead.
- Diagnostics is the one screen where the engine's own words appear.

## ADR-0032 Smart runs in the UI, per message, through the engine's own switches (owner decision on the need, 2026-11-20)
**Amended 23 November 2026 (0.1.10): the per-session switch described below never worked on the engine boopis runs.** The canonical owner gateway refuses `config.set {key: "model"}` with JSON-RPC 4001 `use_session_mutation_model` before reading or writing anything (read in the pinned engine, Hermes v0.23.2: `gateway/session_busy_controls.py`, `gateway/session_mutations.py`, `gateway/session_mutation_model.py`, `gateway/session_controls.py` `mutate`, `gateway/session_cli_turn.py`, `tui_gateway/contracts/canonical_projections.py`). From v0.1.5/v0.1.6 to 0.1.9 every ungoverned pick (the model menu, or Smart's tier) therefore failed, and every message after it was not sent. The pick is now the engine's own `session.mutate` operation `model` (`ui/src/host/live/model-switch.ts`): one request id per pick, kept across its retries; fenced with the session's `revision` and `execution_generation` (from `session.create`/`session.resume`, the receipts and the events), retried once with the fresh fences a `revision_conflict` or `stale_generation` refusal carries; checked by the engine's selection guard, whose `confirmation_required` is shown to the person with the engine's warning, and only their choosing that model again resends it with the engine's `confirm` token (nothing is switched before); a pick on a running session is `deferred` by the engine to its next turn, and the turn says so. `confirm_expensive_model` is no longer sent. The governed path (`cascade.start_tier`) is unchanged. The text below is kept as it was decided.

**Context.**
- The owner: "Smart (the automatic model choice) is not built yet", "a quicker way to change models ... a menu in the chatbox where you can just choose who will answer you next". Smart had been a switch that refused with "not built yet".
- The plugin's hooks (`pre_llm_call` and the others) can add context or block a call; they cannot change the model of a request, and mods may not either (`turn.step` model is refused). The engine does have a per-session model switch (`config.set` key `model` with `--provider X --session`; at creation `session.create` takes `model` and `provider`), and the plugin has a start tier for a governed task.

**Decision.** Smart is a pure function in the UI (`ui/src/data/smart.ts`), run in the live provider just before `prompt.submit` (`details.prepareSend`). It is not in the plugin and not in the Rust host.
- **Why there.** The UI is where the message, its attachments and the session's recent failures are all known at the moment of sending, and where the choice must be visible (the chip previews it while typing; the turn's meta says "Smart: debugging"). Neither the plugin nor the engine can switch a model per request, so a plugin rule would still need the UI to carry it out. A rule in the UI is unit-tested with no engine.
- **The rule.** A level 0, 1 or 2 from the message: design, architecture or migration words, over 1,500 characters, over 40 lines of code, 4 or more attachments, or two of the last three turns failed raise it to 2; debugging words, refactoring words, a diff or code block, over 400 characters, any attachment or `@file` mention, or the last turn failing give 1; anything else is 0. The highest signal wins and is the reason. The level is spread over the session's ladder (cheapest first): 0 the first tier, 2 the last, 1 the middle (the lower of two). The cheapest tier answers by default. With no ladder known Smart refuses to turn on and says so; it never guesses.
- **Ungoverned:** the pick is applied with `config.set model ... --session` once per change (`--session` always, so nothing is written to the profile's configuration). **Governed:** the pick is where the ladder starts, through the new plugin RPC `cascade.start_tier` (allowed after the first prompt, unlike `mode.set`, because the start tier is read at dispatch and does not touch the cached prompt); the gate still escalates past it. In governed mode only the ladder's tiers can be picked.
- **Who answered** is the engine's word: `usage.model` of `message.complete` (ungoverned), and the tiers of `plugin.boopis.cascade.updated` in order (governed, shown as the route). Smart's reason is shown in the turn's meta.
- **Names.** Model ids are written for people by a small parser over `apps/shared/data/model-names.json`; the engine reports no label for a model, so only a provider's name is the engine's, and the provider's plan is secondary text.

**Consequences.**
- A failed switch stops the message with a sentence saying which model; nobody is answered by a model nobody chose.
- Smart is off by default (the engine's own model answers until the user chooses), so nothing changes silently.
- The ledger does not record a start-tier change or a Smart pick yet; the turn's meta is the record for now.

## ADR-0033 Talking to bots, and team chat on the engine's Group Chat rooms
**Context.**
- The owner, 20 November 2026: "the session works, but i can't send any bots messages nor create bot groups." A bot was a profile whose room could only show its schedule and sessions; `docs/ARCHITECTURE.md` section 10a left open which engine primitive carries team chat (**[verify]**: group sessions `groups.*`, bot relay `bot_relay.*`, agent-to-agent `a2a.forward`, Kanban).
- Read in the engine's source (v0.23.2, `tui_gateway/methods_groups.py`, `gateway/hosted_room_*.py`, `gateway/session_bot.py`, `gateway/session_a2a.py`):
  - **`groups.*` (Group Chat rooms) is a group chat.** A room is a name and a frozen roster of two to six local profiles (`member_id`, `profile`, `handle`, `display_name`). `groups.send` appends a `message.user`; the room worker (the gateway's, started with it) runs a *Discussion*: it hands the message to every member, or to those the text names with `@handle` (`resolve_mentions`; `@all` and `@everyone` are reserved), each member answers as its own profile in its own session, and the answers are republished to the others for up to three rounds and ten messages; a bare "pass" is silence. Every message is an event of a durable, monotonic log (`groups.log`, `message.member` with the member's id), and the engine pushes `groups.changed`. `groups.rename`, `groups.stop`, `groups.continue` (after the cap), `groups.state` (who is working) and `groups.context` (purpose, notes, routing `everyone`, `lead` or `auto`) exist.
  - `bot_relay.*` carries messages between a *client's own* bots and the engine (roster sync, deliver, reply, an outbox): it is for a desktop that hosts bots itself, not for the engine's profiles.
  - `a2a.forward` forwards one session's message to another gateway's session (`session_a2a.py`): one hop between two sessions, with no room, no roster and no shared thread.
  - Kanban (`kanban.db`) is a durable task board: right for a hand-off that must survive, wrong for conversation.

**Decision.**
- **Group Chat rooms (`groups.*`) carry team chat.** A boopis group is a room; its members are bots (profile names); the thread is the room's log; `@name` is the engine's own `@handle` (the handle is the profile name), so boopis does not route anything itself. `a2a.forward` and Kanban stay what hand-offs use later (the contract lane of section 10a); `bot_relay.*` is not used.
- **A conversation with one bot is a session of its own profile**, on the bot's own link (`connect(profile)`; the engine binds a ticket to one profile): `session.create` on the first message, `prompt.submit`, the reply streaming back as `message.*` events attributed to the bot, `approval.respond`, `session.interrupt`. The bot's recent sessions are the ones `session.list` gives on that link; `session.resume` opens one as the thread. It runs with the profile's own soul, memory, skills and model; boopis's governed mode (the `boopis` toolset) is the Sessions section's and is not applied to a bot's conversation (the room worker cannot apply it to a member's turn either).
- **What the engine's rooms cannot do is said, not faked.**
  - *Members:* a roster is frozen at creation. Changing the members makes a new room with the same name and archives the old one; the form says so before it does. The new room starts empty; the old one's messages stay readable in Archived.
  - *Archive:* a room can only be disbanded for good (`groups.disband`). Archiving is boopis's own mark on this computer (`core/settings`, `hx.v6.bots.archivedGroups`), reversible with Restore; the room and its log are untouched. Another computer's boopis, or another client of the same engine, still lists it.
  - *Replies arrive whole*, not word by word: the engine publishes a member's message when the member has finished it. The room shows who is replying (`groups.state`, `member_activity`) in the meantime.
  - *Who answers:* with no `@name` every member answers, then reads the others; so a group is a conversation among bots that each see the others' replies, not a router that picks one.
- **The UI says what it is:** the empty room and the new-group form carry `GroupsSource.nature` ("Each member reads what you write and what the others said, and answers in its own words. Write @name to ask one of them."). Where the room worker is off or the engine has no `groups.*`, the form and the room say so (`GroupsSource.note`) and nothing is pretended.

**Consequences.**
- No plugin change, no new RPC and no engine patch: everything above is the engine's public methods, typed by the vendored contract (ADR-0023).
- A group holds two to six bots; a user with one bot cannot make one yet.
- A group's thread is the engine's, so it survives a restart and is the same in any client of that engine.

**Round 2 (the owner, 22 November 2026): a message in a room must never end a bot's work.**
- Read in the engine's source (v0.23.2): `gateway/hosted_room_discussion.py` `plan_publication` turns every task of a thread into `cancelled` (`superseded_by_newer_user_event`) once a newer `message.user` exists in the same thread, even a task that settled, and publishes no answer. The running turn is not interrupted (`tui_gateway/hosted_room_service.py` `prepare_room` waits for live tasks), so its work is spent and its answer dropped. `groups.send` has no queue, steer or interjection option. A room member has no steer either (`session.steer` is for a one-bot session; the member's session is the hidden `bot_room` one).
- **Decision.** The room's composer never sends into a busy room on its own. A message written while a Discussion is open is **held in boopis** (`Group.queued`, shown above the composer, each one can be taken back or sent now) and sent when the Discussion is over. "Send now" stops the running turns first (`groups.stop`) and the strip says so before it is pressed. Busy is read from the log the way the engine reads it (`_pending_discussion`: the newest user message of a thread with no later `room.activity` settled or bounded, after the last `room.continued` and the last `room.stop_requested`), or a member working; a Discussion with no sign of life for 45 s counts as stuck. Held messages go one at a time, each after the Discussion the one before opened. Held messages live in the running app: closing boopis drops them.
- A turn dropped by a newer message from another client is said in the thread (`turn.cancelled`).
- **Kanban.** The engine gives a room member the kanban tools and none of the task guidance (injected only into a dispatcher-owned worker), so a cut-off turn files its cards again, ordered cards run in parallel and one bot is two sessions. boopis gives every bot a skill (`plugin.boopis.bots.guide`, `plugins/boopis/bots/guides.py`, tagged `environments: [kanban]`): list the board first (a worker the dispatcher started has no `kanban_list` and reads its own card), pass an `idempotency_key`, order with `parents`, work in the project's folder (`workspace_kind: "dir"`: a card made without it runs in a scratch folder under the board, whatever the board's `default_workdir`), one place per hand-off (a room turn looks at its own cards before it starts work a card covers), and a `todo` duplicate gets a comment and goes to the owner (no tool archives a card). The host gives it to every bot it prepares (`bots::give_handoffs`, at creation and at every start-up repair), so a bot made from the command line, or one that only runs from cron or kanban, has it too. A bot that is also running a kanban card (`profiles.list` `worker_session`, source `kanban`, wrote within 90 s) is said so in its state and in the group. Steering a member mid-turn, a per-bot claim across rooms, kanban and cron, and cards of a cut-off turn in the next prompt need the engine (drafts in the owner's `upstream/round2/`).

## ADR-0034 Tasks sent to the models the user names, through the engine's own delegation (owner decision on the need, 21 November 2026)
**Context.**
- The owner: "send this task to opus, this one to codex, and this one to carbon, and this one to grok should automatically separate those tasks as the message stated ... if it can happen in-engine, without [patches], that's fine by me."
- Read in the engine's source (v0.23.2): `delegate_task` (`tools/delegate_tool.py`) already runs child agents in the background with a fresh context (`goal` and `context`), in parallel, and returns their results to the parent. A model cannot choose a child's provider or model: those task parameters are reserved and stripped. A *delegation provider* (`agent/delegation_provider.py`) chooses: it may declare extra per-task parameters (an enum is enforced by the engine before `route_task` runs) and returns a route (`provider`, `model`, `label`). The tool's schema is built from the provider when a session's tools are built and pinned with them (`agent/delegation_backends.py`). Events `subagent.spawn_requested|start|progress|thinking|tool|complete` carry the child's goal, model, status, summary, duration and `child_session_id`; `subagent.interrupt` stops one; `session.transcript` reads a session without attaching it.
- boopis already registers one (`governance/delegation.py`, `BoopisDelegation`, `delegation.backend: boopis`), which refused every delegation not started by its own governed `dispatch`.

**Decision.** No engine change and no new tool: the session's own model splits the message (it understands it) and calls `delegate_task` with one task per model; the boopis backend decides where each goes.
- **`target`.** `BoopisDelegation` declares one task parameter, `target`, an enum of the words of the models the person can use now. The words come from the shared names table (`apps/shared/data/model-names.json`, copied into the plugin by `scripts/sync-shared-data.sh`): the Claude aliases (`opus`, `sonnet`, `haiku`), a provider's words (`codex`, `gpt`, `grok`, `gemini`), the model's family word, and always the model's own id. A word goes to the first model that claims it, so none is ambiguous.
- **Where the list comes from.** The plugin cannot list the user's signed-in models through Hermes's public plugin API, but the desktop already does (`model.options`, the ladder). Just before `session.create` and `session.resume` the UI sends `plugin.boopis.dispatch.roster {models: [{provider, model}]}`; the plugin keeps the roster for the process and `task_parameters` reads it when the session's tools are built. A session's tools are fixed at creation (invariant 4), so **a model signed in later is named by the next session** (the UI does not yet say so; left for the owner to place).
- **Guard (invariant 2's spirit).** `route_task` accepts a `target` only if the user wrote that word in the message that started the turn. The plugin records each session's `pre_llm_call` `user_message` and matches the word (case-insensitive, whole word; in an id a space, hyphen or dot are the same). A word the user did not write is refused ("the user did not name 'grok'..."), so the model can never buy a stronger or different model on its own. A word that matches nothing (the engine refuses it from the enum, or the plugin when the roster changed since: "No model called 'carbon' is available. The models that can take a task are: ...") ends in a message the model reports to the user.
- **Governed sessions keep the refusal.** `route_task` answers a governed session (or a cascade launch) exactly as before: only `dispatch` starts work and the ladder's tier is the route; a `target` is refused with that explanation. The user-directed path is open when `user_directed_allowed(state)` says so, which is today any session that is not governed (the owner's chosen default). A turn that runs ungoverned by the user's one-message choice reaches the same function.
- **The UI.** `subagent.*` frames become cards in the turn that raised them (`ui.child`: the model's logo and readable name, the goal, what it does now, status, a running clock, the summary), with *open* (reads `session.transcript` of `child_session_id`, read-only and never attached) and *stop* (`subagent.interrupt`). The engine keeps children as live state only, so the cards are kept in the turn book (ADR-0036): a resumed transcript draws them again, read-only (the model, goal, final status, summary, tool count and time; *open* still reads the child's session, there is no *stop*, and a card the book has as queued or running is drawn as stopped, never as working).

**Consequences.**
- A message that names models and no one else works with no new tool, no patch and no extra model call; results return to the session's model, which reports.
- A task without `target` in an ungoverned session is refused with a sentence ("Set `target` to the model the user named..."), not run on a model nobody named.
- The guard is a word match, not an understanding: a message that mentions "opus" in passing allows a task to opus. It never allows a model the user did not write.
- The roster is the process's, not the session's: two windows with different sign-ins share the last one sent.
- A card is kept when its turn completes. A `subagent.*` frame that arrives after `message.complete` is not in the book; the engine's `delegate_task` waits for its children, so that is rare. A summary is kept to 1500 characters and a goal to 400 (see ADR-0036); a cut summary says so on the card.

## ADR-0035 The council: several models answer one message and one combines them (owner decision, 2026-11-21)
**Amended 23 November 2026 (0.1.10): the one-turn switch is `prompt.submit`'s `model_override`, not `config.set ... --once`.** The canonical owner gateway refuses `config.set {key: "model"}` (4001 `use_session_mutation_model`; read in the pinned engine, Hermes v0.23.2: `gateway/session_busy_controls.py`, `gateway/session_mutations.py`, `gateway/session_mutation_model.py`, `gateway/session_controls.py` `mutate`, `gateway/session_cli_turn.py`, `tui_gateway/contracts/canonical_projections.py`), so councils could not start from 0.1.6 to 0.1.9. The council's message now carries `model_override: {model: "boopis-council", provider: "moa"}` (`COUNCIL_OVERRIDE`): the engine resolves it with the same `switch_model` pipeline for that admission only (an explicit `moa` provider names the preset, `hermes_cli/model_switch.py`) and never writes the session's model, so there is nothing to restore and no agent to wait for: the 5001/5032 retry loop is gone. Writing the preset with `cli.exec config set moa.presets...` is unchanged. The text below is kept as it was decided.


**Need.** The owner wants any model to answer any turn of one session, and "a council": several models answer one question, one combines them, and each answer is visible.

**What the engine has.** The mixture of agents, a virtual provider `moa` (`agent/moa_loop.py`, `hermes_cli/moa_config.py`). A preset in the profile's `moa:` section names reference models (any providers) and an aggregator. The references answer once, in parallel, without tools; the aggregator is the model that runs the turn, with the session's tools. The engine emits `moa.progress`, `moa.reference` (one per member, with its text), `moa.phase` and `moa.aggregating`.

**Decision.**
- **No engine change.** boopis keeps one preset, `boopis-council` (a name that is plainly ours, so a preset of the user's own is never overwritten), and writes it with the engine's own command: the gateway's `cli.exec` runs `config set moa.presets.boopis-council.reference_models|aggregator|fanout <json>` (the host never edits the file, ADR-0014). Only the fields that differ from the saved preset are written, so asking the same council again writes nothing. **The first write leaves the engine's setup as it was:** the seeded `default` preset lives in DEFAULT_CONFIG, and a user's explicit `moa.presets` map replaces it outright (`apply_user_moa_presets`), so writing only ours would make `default` vanish and `/moa` would run ours. When the profile has no map of its own, boopis reads the merged presets (`config get moa.presets --json`) and writes them with ours in one `config set moa.presets <json>`; if they cannot be read, nothing is written. `fanout` is `user_turn`: the members answer once per message, not once per tool step.
- **One turn, through `config.set`, not `/moa`.** `config.set model "boopis-council --provider moa --once"` then `prompt.submit`. `/moa` was the alternative, and it is built for a fresh session, but it runs only the profile's `default_preset`: using it would mean rewriting `moa.default_preset`, a profile setting the user may rely on, for every council. `--once` names the preset, restores the session's model after the turn through the engine's own restore, and is the same switch "who answers next" uses. Its cost: it needs a built agent, and a session made a moment ago has none until the engine builds it, so the switch is tried again (engine codes 5001 and 5032, up to 12 times at half a second) before the message is refused. A refused switch never lets the message go to a model nobody chose.
- **Who sits.** The form starts from the last council (read back with `config.get full`, `moa.presets.boopis-council`) while every model in it is still on offer; else from the best model of each provider the user is signed in to (the highest tier of the ladder where the provider has one, else the newest main model, never a small one), and the session's model as the combiner. Fable is never a default: it bills usage credits on a Pro plan from the first request (the ladder leaves it out for the same reason, `claude.rs`), so it is the user's to add. At least two members.
- **Governed sessions: not offered.** Invariant 2 says only a gate failure buys a stronger model and the plugin chooses it. A council buys several models without a failure, and the session's toolsets and mode are fixed at the first prompt. The menu entry is disabled with that reason. It is a default; the owner can allow it.
- **What the turn shows.** One quiet, collapsible row per member (the provider's mark, the readable name, a state word: thinking, done, failed), the combiner's byline ("Claude Sonnet combined 3 answers"), then the combined answer as the entry's own prose; the call number names the combiner and "Council of N". The card says what is true: members answer without tools, the combiner keeps them, and the cost is one call for each member plus the combiner's own turn, which may take several steps. A member's failure is said in plain words, never the engine's text.
- **Honest limits.** The members' answers are events; the engine keeps no copy of them in the transcript (references are side calls and would break role alternation), so the plugin's turn book keeps them (ADR-0036) and a resume draws the member rows again from it. The engine's own transcript still has only the combined answer. The `moa.*` events follow the profile's reasoning display (`display.show_reasoning`, on by default): if the user turned it off, the card says no answers were reported. The engine's one-turn switch also leaves its "model switched" note in the history.

- **The chip.** The engine names a council turn by its preset on its virtual provider (`boopis-council`, provider `moa`), which is not a model. The UI never lets it be the session's model: `session.info` and `session.usage` reports (events and reads, in the live provider and in the details) drop a model that is the preset or on `moa`, so the session's own model stays (also for a council a slash command started). While a council answers, the model chip reads "Council of N", as the turn's call number does (`GovernanceState.council`). A resumed council turn is the combiner's, not the preset's.
- **After a resume.** Member answers survive in the turn book: for each member the model, a state word (`answered`, `failed`, `waiting`) and its text, and the combiner. A failed member keeps the state word only, never the engine's text. A member the book has as waiting never reported, and a resume says "It did not answer". A turn with no record draws no block.

**Consequences.** No new RPC, no plugin change, no host command; `cli.exec`, `config.get`, `config.set`, `prompt.submit` and the `moa.*` events are typed by the vendored contract (ADR-0023). Checked against the engine's source and over fake frames; a real council needs a signed-in engine (`tests/e2e` has no fake for `moa`).

## ADR-0036 Who answered each message, "@" for one message, and one ungoverned turn (owner decisions, 20-21 November 2026)
**Amended 23 November 2026 (0.1.10): "@model" rides on `prompt.submit`'s `model_override`.** What the record below says the engine offers was read in the legacy `tui_gateway` sidecar; the canonical owner gateway boopis runs refuses `config.set {key: "model"}` (4001 `use_session_mutation_model`; read in the pinned engine, Hermes v0.23.2: `gateway/session_busy_controls.py`, `gateway/session_mutations.py`, `gateway/session_mutation_model.py`, `gateway/session_controls.py` `mutate`, `gateway/session_cli_turn.py`, `tui_gateway/contracts/canonical_projections.py`), so from 0.1.6 to 0.1.9 every "@model" message was refused, and the silent restore after a refused submit could not run either. `prompt.submit` does take a per-admission `model_override: {model, provider?, reasoning?}` (`CanonicalModelOverride`, committed as `cli_turn_v1`, applied by `one_turn_route` for that turn only). The mention is now sent that way: the session's model is never written, so nothing is put back. A one-turn override does not pass the engine's selection guard (the classic CLI asks on its own side); boopis did not ask before either (it sent `confirm_expensive_model: true`), so no confirmation the person used to get was lost, and none is added here. A governed session still arms `mode.once` first, and a running session still refuses the mention in words. The text below is kept as it was decided.

**Context.**
- The owner, 20 November 2026: "centralize all the models in a single session on the session tab": any of his models answers any turn of one session, with one shared context, and every reply shows its model's logo. He approved a record of the model per message that survives a resume, a divider where the model changes, and "@" in the composer ("@codex fix this") to have one message answered by one model, the session's default unchanged.
- The bug: `transcriptToTurns(res.messages, c.model, ...)` stamped the *current* model on every past reply after a resume. The engine does not remember who answered: its messages table has no model column (it only writes a "[Model switched to X via provider Y]" row, a stored user row with `display_kind: model_switch`, of which it keeps the newest).
- What the engine offers (read in v0.23.2: `tui_gateway/methods_config_set.py`, `model_switch.py`, `prompt_turn.py`): `config.set {key: "model", value: "<model> --provider <slug> --once"}` switches the live agent at once and arms a restore that runs when the next turn ends; `prompt.submit` has no model field; a switch asked of a running turn is only stashed. `message.complete.persisted_turn` gives the turn's stored row ids. The plugin's `post_api_request` hook sees every model request with its real provider, model and `turn_id` (also after a fallback).

**Decision: who answered.**
- The plugin records it (`plugins/boopis/turns.py`), not the host. The plugin already sees the real provider and model of each request; the host would only know what the UI was told. The record is a *turn book*: one JSON line per answered turn in a file beside the session's ledger (`<ledger>.turns.jsonl`), `{turn_id, model: "provider/model", route: [...worker tiers], ungoverned, user_row_id, row_ids, at}`. It is a sidecar and not ledger events because the ledger is contraprova's format, byte for byte (invariant 3), and a new event type would have to go upstream first.
- Two RPCs: `plugin.boopis.turns.bind {session_id, user_row_id?, row_ids}` (the UI calls it when `message.complete` carries `persisted_turn`: the plugin takes the model requests it saw since the last bind and writes the line) and `plugin.boopis.turns.models {session_id}` (read on a resume). The answering model of a turn is the last request of the session's own model; a governed turn also keeps the tiers its workers ran on, so it still shows its route.
- `usage.recorded` now carries `turn_id` (an extra field; contraprova allows them), so the ledger and the book can be joined. (The brief said it already did; in the code it did not.)
- A turn with no line is **unknown**: `transcriptToTurns(rows, idPrefix, book)` gives it an empty model and the call number says "Model unknown". It never falls back to the session's current model (invariant 5). A branched session has an empty book for its copied turns (unknown); copying the book across a branch is left.
- The UI hides the engine's own switch-note rows (they are user-role rows) and draws a **divider** instead: a hairline row with both models' logos and names ("Claude Haiku -> GPT-6 Luna") before each reply whose model differs from the last known one. An unknown reply neither draws nor hides a divider.
- Cost of the choice: a turn finishing while no UI is connected is not bound and so shows as unknown after a resume. That is the honest outcome and rare (the host keeps the UI's link while the app runs).

**Decision: "@" for one message.**
- Typing "@" at the start of a word opens a menu of the same models as "who answers next" (without Smart), with logos and readable names; picking one writes `@<readable name>` into the text, drawn as a mention chip (a composer mark of kind `mention`). The reader (`data/mentions.ts`) is the one place that says what a mention is; the composer and the send use it.
- A message whose only mention is **one model** (however many times it is named) is sent through the engine's one-turn switch: `config.set ... --once`, then `prompt.submit` with the text as written, on an idle session (a running session refuses it in words). The session's own model and the sticky pick are never touched: the engine restores itself, and the UI holds the session's model for the chip while the mentioned model is named by the engine's reports. If the submit fails after the switch, the previous model is put back. **Smart does not override a mention.**
- A message that mentions **two or more different models** is left as written for the session's model: the task-splitting tool (ADR-0034) reads it. The UI does not split.

**Decision: one ungoverned turn (the owner's change to the default, 21 November 2026).**
- The owner: *"@ in governed mode can turn off governed mode for that message specifically."* This replaces the first default (in governed mode only ladder tiers can be mentioned). In a governed session, a message with one "@model" runs **ungoverned for that turn only**: any available model can be named, it answers directly with no cascade and no gate escalation, and the next message is governed again.
- How governed mode really works, and what could change: the mode, the policy and the toolsets are fixed at the first prompt (prompt caching, invariant 4), and a governed session is created with `toolsets: ["boopis"]`. So the exception cannot change the mode. `plugin.boopis.mode.once {session_id, armed}` **arms** the next orchestrator turn; `pre_llm_call` starts it (`turns.begin`) and `on_session_end` ends it. While it runs, `SessionState.effective_mode` is `ungoverned`: no turn directive, the ungoverned policy (`policy_for`), and `ship` without the governed rule that demands a configured gate command. The session's `mode` field never changes, and an ungoverned session answers `armed: false`.
- It resets itself whatever happens: `on_session_end` fires for a completed, failed or interrupted turn; a turn whose end was never heard of is closed by the next turn's start (`reason: lost`); an armed session that sends nothing lapses after 120 seconds; the UI withdraws it (`armed: false`) when it could not switch the model or submit; a cost-capped turn clears it. A worker's turn end does not end it.
- **What that turn can and cannot do.** The toolset is still the governed `boopis` one (`pack`, `exec`, `ship`, `dispatch`, forms), because toolsets are fixed at creation. So the ungoverned turn **can** read (`pack`), compute (`exec`) and write files through `ship` itself (the orchestrator may ship; in governed mode only workers can), and answer in prose. It **cannot** use the engine's own tools (terminal, file edit, web), because they are not in the session, and `dispatch` is refused ("available in governed mode only"). The system prompt still carries the governed contract (it is cached and cannot change); the plugin adds a one-line context to the turn saying governance is suspended for it. `ship` still ends at the project's gate when the project has a gate command, as in any ungoverned session: it is not a way to skip a gate that is configured.
- **The audit trail.** Both edges are `mode.changed` ledger events with `scope: turn` (`from`/`to`, `reason`: `armed`, `completed`, `failed`, `interrupted` or `lost`, and on the start `gate: skipped`, `cascade: skipped`, `turn_id`), so the ledger shows which turn skipped governance. The turn book marks the turn `ungoverned: true`, so it keeps its mark after a resume.
- **The UI says it plainly:** the "@" menu in a governed session lists every model with "Runs without governance" and a foot note ("This message runs without governance: no cascade, no gate. The next message is governed again."); the assumptions row under the composer says "to X only, ungoverned"; the sent turn carries a quiet "ungoverned" badge beside its model, with the sentence in its tooltip.

**Consequences.**
- Plugin: `turns.py`, three RPCs (`mode.once`, `turns.bind`, `turns.models`), `on_session_end` hook, `usage.recorded.turn_id`. UI: `host/live/attribution.ts`, `data/mentions.ts`, `modules/session/attribution.ts`, the "@" menu and chip in the session composer. No engine patch (ADR-0023).
**Decision: what a turn showed, kept in the same book (0.1.6).**
- The owner's standard: what a turn showed is still there after a resume. The engine keeps no copy of a council's member answers (references are side calls) nor of the task cards (children are live state), so `turns.bind` takes two more optional fields and `turns.models` returns them: `council: {members: [{model, state, text, cut?}], combiner}` and `children: [{model, goal, status, summary, child_session_id, tool_count, duration_ms, cut?}]`. The UI sends them in the bind it already makes (`bindTurn`, from the finished turn's live `council` and `children`); `transcriptToTurns(rows, idPrefix, book)` attaches them and the existing council block and task cards draw them. A line without them reads as before, and a malformed field is dropped without losing the line's model.
- **Bounds, and why.** A resume reads the whole book, so a line is bounded: 6000 characters for a member's answer, 1500 for a summary, 400 for a goal, 12 members and 20 cards a turn, which keeps a line near 100 KB at worst while nearly every real answer or report is kept whole. A cut is never silent: the plugin marks it (`cut: true`) and the UI says so ("This answer was shortened when it was saved. The rest is not kept." on a member, the same in a card's summary).
- **Never the engine's error text.** A member that did not answer is stored as its state word with empty text, whatever text came with it. A card's summary is what the card showed.
- **Resumed means read-only.** A resumed card has no subagent id, so no *stop*; it keeps the child's session id, so *open* reads that session (`session.transcript`). The chip and the call number of a resumed council turn name the combiner (the book's `model` for it is the engine's preset, which is not a model).
- Left: copying the book across a branch; a turn that completes while no UI listens is unknown; the divider for a governed route compares the last tier only.

## ADR-0037 Governed mode runs only on frontier models, and heavy ones only on the user's word (owner decisions, 2026-11-21)
**Context.**
- The owner, 21 November 2026: "our governed mode should probably be locked to frontier top models only. claude: opus and fable; gemini: carbon; codex/openai: astra; grok: don't know their names; etc."
- Ramp's SWE-Bench v2 (500 private tasks from merged production PRs, pass@1, high effort; each model in its lab's own harness and in a bash-only one). Solve rate in the native harness, bash-only in brackets, error bars about 4 points: GPT-6.2 Astra 76.4 (75.0), Gemini 4 Neon 76.2 (73.6), Fable 5.2 73.4 (73.0), GPT-6.2 Sol 73.4 (72.4), Gemini 4 Carbon 72.6 (74.0), Gemini 4 Hydrogen 72.4 (70.8), Opus 5.5 67.8 (71.2), GPT-6.1 Terra 70.4 (60.6), Grok 4.7 64.4 (55.4), Sonnet 5.5 63.2 (57.6), GPT-6 Astra 63.4 (54.6), Haiku 5.5 57.4 (52.8), GPT-6 Luna 52.4 (42.6).
- The owner, the same day, asked whether GPT-6.2 Sol, Gemini 4 Neon and Gemini 4 Hydrogen should also be allowed in governed mode: "sure."
- The owner, asked whether governed mode on the Claude subscription should climb to Fable by default: "no, fable and other big and cost-heavy frontier models like grok 4.7 should be a manual toggle or specification by the user, because they're too token heavy. the governor changing it automatically to fable and burning a user's entire subscription limit would be funny, but bad (obviously)".
- The same benchmark's cost per task (mean, in each lab's own harness): GPT-6.2 Astra $3.31, Gemini 4 Neon $4.38, Fable 5.2 $3.79, GPT-6.2 Sol $1.05, Gemini 4 Carbon $5.19, Gemini 4 Hydrogen $3.24, Opus 5.5 $1.53, Grok 4.7 $4.32 (and the most tool calls of any model, 161 a task). GPT-6.1 Sol solved 59.6, which is why the floor of that family is 6.2.
- The ladder ran cheapest first, and the cheap tiers (haiku, luna, flash) are what the gate buys its way up from; a governed session's own model orchestrates and is not on the ladder.

**Decision.** Every model that does governed work is frontier: each ladder tier and the session's own model.
- **The list is data, in one place** (`apps/shared/data/frontier-models.json`, copied into the plugin by `scripts/sync-shared-data.sh`, read by the host with `include_str!`): families with the lowest version that qualifies: Claude Opus 5.5, Claude Fable 5.2, GPT-6.2 Astra (OpenAI and ChatGPT; GPT-6 Astra at 63.4 does not qualify, so the floor matters), GPT-6.2 Sol (GPT-6.1 Sol at 59.6 does not), Gemini 4 Carbon, Gemini 4 Neon, Gemini 4 Hydrogen, and Grok 4.7 and later. Sonnet 5.5 and every other model stay available outside governed mode. The prefix and suffix rules give no clash: Sol, Astra and Luna differ by their suffix (Luna is in no family), and Neon, Hydrogen and Carbon likewise.
- **Matching is by family and version, never a fixed id list**, after normalising the id: lower case, the part after the last `/` (provider and vendor prefixes fall away), a `[1m]` suffix dropped, dots and dashes in versions the same, a date and a reasoning-effort suffix ignored; anything else after the name, or a model in no family, is not frontier (fail closed). The Claude subscription's aliases `opus` and `fable` resolve through a table in the same file. The engine's catalogue lags (it lacks `gpt-6.2-astra`), which is why nothing is matched against it.
- **The plugin is the authority.** `ladder_problems` (so `dispatch` and `describe` agree) refuses a ladder with a tier that is not frontier; `pre_llm_call` refuses a governed session's turn when its own model is not, each in one sentence naming the model, why and the allowed families. The default ladder is Opus 5.5 alone. The UI reads the same list from `describe.frontier`; Settings > Models reads the host's view of the same file. Not affected: ungoverned sessions, the `@` mention (it turns governance off for its message), the council and task-splitting tools.
- **Heavy models: frontier, but only on the user's word (the second answer).** A family in the data file can carry `"heavy": true`. Today that is Claude Fable (every version at or above its floor) and Grok 4.7 and later. A heavy model is frontier, so governed mode runs it; but it is never chosen by anything automatic:
  - **No ladder that setup writes or repairs, and not the plugin's default ladder, includes one.** Claude, on an API key and on the subscription, is Opus alone (the gate's retries happen at Opus). The API-key ladder used to climb Opus, then Fable on its own; that is gone. A test holds the plugin's default free of heavy models, and the host's ladder builders filter on the mark.
  - **Each heavy model has an opt-in switch in Settings > Models, governed section**, one per model the saved ladder can take: Fable on either Claude choice (the subscription or an Anthropic key, with the Claude Code 2.1.321 floor kept on the subscription), Grok on an xAI key. Each says in plain words why it is off by default (Fable bills usage credits from the first request on a Pro plan and costs $3.79 a task against Opus's $1.53; Grok 4.7 costs $4.32 a task and makes 161 tool calls a task). On adds the model as the top tier, off takes it away. The choice is remembered (`State::heavy` in setup.json: `fable`, `grok`; the older `subscription_fable` is read into it once), so setup run again keeps it. The host command is `setup_set_heavy(id, on)`; the models view carries `heavy`, one entry per heavy model.
  - **A provider whose only frontier model is heavy has no governed mode until its switch is on.** xAI is the case today: choosing xAI in setup saves the key and writes no ladder, and the models view says, in words, that the only frontier model an xAI key reaches is a heavy one, with the Grok switch right under it.
  - **A ladder the user wrote by hand that names a heavy model is the user's own specification:** accepted as it is by the plugin, never rewritten by the repair, shown in the models view as heavy and "on the ladder because you chose it".
  - **The other automatic pickers never pick one.** Smart (ADR-0032) spreads its levels over the ladder's tiers that are not heavy, so level 2 is the strongest of those, and with only heavy tiers it has nothing to choose from and says so; the council's defaults (`NOT_BY_DEFAULT` in `host/live/council.ts`) read the same mark from the same data instead of their own `fable|mythos` pattern, and a provider that lists only heavy models has no default member. A model the user picks in the "who answers next" menu, mentions with "@", names for a task or adds to a council is their specification and stays allowed. The UI reads the data through `data/frontier.ts`, the third reader of the file, tested against the same examples.
- **Setup writes frontier ladders only, cheapest first, each only from models the provider actually lists.** Claude on an API key: the plugin's own default, Opus alone. Claude subscription: Opus alone. ChatGPT: Sol, then Astra (the lowest 6.2-or-later model of each family the signed-in account's own catalogue lists; Sol is the cheaper rung, $1.05 a task against Astra's $3.31, and scores below it), a rung the account lacks left out, no ladder when it lists neither. Gemini: Hydrogen, then Neon, from the engine's Gemini catalogue, a rung it lacks left out, no ladder when it lists neither, with the reason said. **Gemini 4 Carbon stays allowed but is not on the default ladder:** it scored below Neon (72.6 against 76.2) at a higher cost ($5.19 against $4.38 a task), so nothing setup writes climbs to it; the models view says this where it lists the allowed models, so nobody wonders where it went. (OpenAI's API key has no setup choice; a ladder on it is hand-written, or comes from a named provider.) Free tier and OpenRouter free models are never frontier: governed mode is unavailable on them and says so. **Existing installs, once** (`State::ladders_checked`, the same once-per-install way as before): a ladder setup itself wrote is rewritten to what setup writes now: the 0.1.5 ones (exactly the old Claude aliases, luna and sol, flash and pro), and the 0.1.6 candidate's opus-and-fable subscription ladder (unless the user turned Fable on), astra-only ladder and carbon-only ladder. A candidate ladder is left as it is when the catalogue lists nothing better (it is still frontier). A ladder written by hand is never rewritten and its non-frontier tiers are reported. The API-key Claude ladder that climbed to Fable without an opt-in was the plugin's own default, which changed.
- **Fable on a Claude ladder is the opt-in above.** The owner listed "opus and fable", and Fable is frontier, so it is allowed and accepted on any ladder; but on a Claude Pro plan it bills usage credits from the first request (the plugin's README; `claude.rs`), so setup and the repair write `opus` alone, and the switch (formerly "Climb to Fable", subscription only, now on either Claude choice) adds the `fable` tier after `opus` (Claude Code 2.1.321 serves it on the subscription; on an API key it is the plugin's own `claude-fable-5-2` at per-token billing) and is remembered. It applies to sessions started afterwards.
- **When no frontier model is available governed mode is unavailable, plainly.** A new session does not start governed, the Governed chip explains in one sentence, names the allowed models and offers Settings > Models, and Settings > Models lists the allowed models and marks the saved tiers governed mode will not run. A Gemini key's access to Carbon is Google's decision and the engine does not say; it is handled by a refusal at run time, not guessed.

**Adding a family later.** One entry in `frontier-models.json` (`prefix`, `suffix`, `min`, a `name` template) and its `examples` on both sides of the floor; the plugin's and the host's tests read the same examples. GPT-6.2 Sol, Gemini 4 Neon and Gemini 4 Hydrogen were added this way (one line each, with examples on both sides of the floor). **To mark a family heavy later:** add `"heavy": true` to its entry and a `"heavy": true` example; the plugin, the host and the UI read it, and every automatic path (the plugin's default ladder, setup's ladders, Smart, the council's defaults) then leaves it out. Its opt-in switch is one row of `heavy_switches` in `providers.json` (ADR-0039: id, family, label, reason, engines, key way, pick rule, messages); the host's own `HEAVY` table is gone. Without that row the model is simply never on an automatic ladder, and the user can still name it.

**Consequences.**
- A heavy model is never spent by surprise: a user who wants it turns it on, names it, or writes it into their own ladder.
- A governed session on a model that is not frontier is refused at its first prompt with the sentence; changing the model is the user's call.
- The cost-conscious start (cheap tier first) is gone from governed mode by decision; ungoverned sessions keep every model.
- Three readers of one data file (Python, Rust and TypeScript) are tested against its examples, so they cannot drift quietly.

## ADR-0038 The store: one in-app marketplace for everything installable (owner decision, 2026-11-21)
**Context.**
- The owner, 21 November 2026: "we also need to add a plugin/skill/connector store."
- The owner, the same day: "hermes plugins should be added there too, and anything else really. github skills, anything installable. if we could centralize our things on a in-app marketplace with recommended/searchable stuff that would be super good"
- What exists: connectors have a curated collection, a plan with a hash, and a hold (ADR-0020 forms, `docs/CONNECTORS.md`); Claude plugins and mods have a trust store and a hash-locked local install (`docs/COMPAT.md`, `docs/MODS.md`), with fetch, pin and enable not built; the engine has its own plugin catalogue and skills hub. Nothing joins them, nothing is searchable, and nothing writes the allowlist a governed `exec` needs to call a connector (`plugins.entries.boopis.mcp_allowlist`).
- The research and design: the store report of 21 November 2026 (sections 5 and 6), as amended below. The built-to design is `docs/STORE.md`.

**Decision.**
- **One store, everything installable.** Five kinds: skills (any GitHub repository with `SKILL.md` files included), connectors (MCP servers, `.mcpb` bundles included), Claude Code plugins and marketplaces, mods, and engine plugins, Python ones included. This reverses the report's decision 4 (engine plugins out of v1).
- **Sources, all searched by default, in one place.** boopis's curated list; the engine's catalogue (every tier) and its skills hub; Anthropic's `claude-plugins-official` and `anthropics/skills`; the official MCP Registry; GitHub; any marketplace address or git repository the user adds; local folders and files. Each can be switched off in the store. The data is `apps/shared/data/store-sources.json`. The terms for Anthropic's catalogues were read on 2026-11-21 with the owner's go-ahead: both repositories are Apache 2.0 and Anthropic's Software Directory Policy governs developers who submit, not apps that read public repositories, so `anthropic` is on by default (`terms: checked`). Its own plugins and `anthropics/skills` are "Verified by its source"; third-party entries in its marketplace are "Not reviewed", as its README says Anthropic cannot verify them. The source is named only to say where items come from (Apache 2.0 section 6 grants no trademark rights).
- **The front page is "Recommended"**, from boopis's own list: only items checked against their source, no invented ratings or counts.
- **Tiers in plain words:** "Recommended by boopis" (only boopis's own list), "Verified by its source" (a source's own mark, credited to the source, never repeated as boopis's), "Not reviewed" (everything else). An item nobody reviewed carries the stronger warning on its card.
- **Its own view in the app**, reachable from the command palette, the Connectors tab ("Browse the store") and the session details panel, composed from existing kit patterns for the owner's review; no new component set. In the UI the engine's plugins are "plugins" from "the engine's store"; the engine's name appears only inside an item's own content (`data-store-item`, ADR-0031).
- **Search is local** over the host's cached catalogue; no query leaves the machine. GitHub: cached curated lists and "add from a GitHub URL" in v1, live search when boopis has a GitHub sign-in (unauthenticated limits are too low).
- **Kept from the report's defaults** (the owner can change them): pinned or refused; `dangerous` verdicts are blocked with no override; hold to approve for anything that runs code; "not known" for undeclared egress; no automatic code updates, updates are diffed (`widened` ones need the whole card again) and can be rolled back one step; per-bot install with per-project trust; no project-scope skill files; the boopis index compiled in, signing later; installs take effect in the next session only.
- **Engine plugins in governed mode: allowed, with the truth on the card.** They run in the engine in every session, governed ones included, outside `hx-sandbox`, and `policy.check` does not see them. Governed projects get a per-project switch, "no engine plugins and no plugin hooks", on by default for them; ungoverned projects allow engine plugins once approved. The engine loads plugins per process, so the switch is enforced at session start: a governed session in such a project, whose bot has an enabled engine plugin, is refused with `hx.store.governed_refused` (fail closed), and the project's plugin hooks are inert.
- **Remote (hosted) connectors are allowed, with a standing caution.** A hosted server has no digest, so it is pinned as `{type: version, repo: "remote:<url>"}` (the exact version the registry lists, and the address) and its plan carries the `not-pinned-remote` warning: boopis cannot pin what the service does, and its publisher can change it. The caution is on every review card, update and install, and is never hidden. Decided by the owner on 21 November 2026 when asked whether to refuse them: "keep it".
- **The terms check is recorded.** On 21 November 2026, with the owner's go-ahead, Anthropic's two catalogues were read: `anthropics/skills` is Apache 2.0 (each skill carries its own `LICENSE.txt`; the repository states it is for demonstration and educational purposes) and `anthropics/claude-plugins-official` is Apache 2.0 at its root; its README says Anthropic cannot verify third-party plugins and that the third-party part is being phased out. The Software Directory Policy governs developers who submit and says nothing about an app that reads the public repositories. So the source is on by default, each item shows its own licence ("not known" when the repository has none), and the source is named only to say where items come from.
- **The governed connector gap is fixed** for store installs and for the existing connector install: the server's name is written to `plugins.entries.boopis.mcp_allowlist` through the engine's own configuration, and removed with the server, with a live test that governed `exec` calls it.

**The trust model.** Layered, never one switch. (1) Every item is pinned (commit, archive or tree sha256, image digest, bundle `fileSha256`, exact registry version) or refused. (2) The host stages and verifies the bytes before any layer sees them: size and entry caps, no escaping path, link, device node, FIFO or setuid bit, the digest or commit checked, a tree hash computed. (3) Analysis runs nothing; it produces one plan listing what code runs and where, hosts (declared, verified or not known), secrets, files written, scope, consent items and warnings, with one hash, and the layer that installs rebuilds it and refuses on a difference. (4) A hold approves anything that runs code. (5) Trust is per item and content hash, per project for what runs code, and drops when the content changes. (6) A kill list (the engine's, the registry's, boopis's) blocks and switches off. (7) Declared lists are labelled as declared; unknown is shown as unknown (invariant 5). The report's incidents (a trusted npm package turned malicious in a later version; hundreds of malicious skills in an open registry; install links that look the same whether legitimate or not) are why: pins and re-review on update answer "trust, then change", the tier and warning answer breadth, and a link or a model's request only ever opens an item's page.

**Layer ownership** (`docs/STORE.md` 5.9). The host (Rust) fetches, caches, searches, checks digests and stages. Connectors keep the host's connector engine and the engine's `mcp.servers.*`. The plugin (Python) plans, installs, locks and records Claude plugins, mods and skills from outside the engine's hub, owns the project switch and the kill-list effect, and does the governed policy and the record for engine plugins. The engine installs hub skills and engine plugins through `skills.manage` and `plugins.manage`, driven by the host, with its own scanner, quarantine and lock. The UI draws the cards and screens. The contract between them is `apps/shared/data/store.schema.json`, the `store_*` host commands (`docs/PROTOCOL.md` 1a), the `plugin.boopis.store.*` RPCs (section 3) and the `hx.store.*` codes.

**Consequences.**
- Three workstreams build in parallel against one contract and a mock provider; the shared files take small additive edits only.
- The engine's hub installs are as pinned as the hub's index lets them be; an entry with no commit is listed and refused. Updating or removing a hub skill uses the engine's CLI, since the gateway has no action for it.
- An engine plugin is the one thing the store installs that boopis cannot contain, and the store says so at the point of consent, on the page, and again in the governed project's switch.

**Not in v1.** Project-scope skill files; a signing key and hosted index; automatic code updates and update-all; ratings, install counts and reviews unless a source supplies them; sandboxing local connectors; a GitHub sign-in and live GitHub search; installing from a link or a model's request without the item's page and card; Windows mods and the Windows secret channel (the store degrades the same way, `hx.store.kind_unsupported`).

**Amended, 22 November 2026 (the owner: "the entire store screen cuts off from the right, plus, even with the sources turned on, nothing appears ... the most common and popular connectors should appear first").**
- **It fits its dialog.** The cause was `.hx-store { width: 100% }` on the dialog's body, which also carries the dialog's padding: the body was 30 px wider than the card, and the card (`overflow: hidden`) cut every control at its right edge. The rule now only keeps the body from growing (`min-width: 0`); the kind filter is the kit's option chips, which wrap, instead of a segmented control of six.
- **The sources load, and say so.** Every network read panicked: the store's HTTPS agent named no rustls crypto provider (fixed for every agent by ADR-0041, `tls.rs`), and the view never read the sources on its own nor read their state back after a failure, so the rows said "Not read yet" forever. The store now reads the sources the host says are due (`stale`: on, read by a read, and never read, failed, or older than its period) each time it opens, one at a time with each row saying it is waiting or being read, then "n items. Read just now." or a plain reason from `store/reasons.rs` (could not reach a named host, the engine is not running yet, a rate limit with when to try again, a proxy page that is not a list, boopis's own failure). A source no read reaches says what it is. "This list is out of date" says which source and why, with the button to read again. `tests/live_store.rs` reads every source through the host's own code on Linux and Windows (`live-store.yml`).
- **The popular connectors lead.** boopis's list holds fifteen connectors, each read from its publisher's repository, its MCP Registry entry and its package or image manifest. The order is the GitHub stars of each official repository on a recorded date and run (`connectors.json` `popularity`, docs/CONNECTORS.md "The order"), chosen because every entry has one, it is public and re-readable, and it is the same kind of number for a package, an image and a hosted server; a repository shared by many servers follows, since its count is the collection's. Browse and the front page show boopis's list in that order before the other sources; within a search, relevance leads. The weekly `popularity` job says when the recorded order no longer follows the stars.
- **The lab opens the real dialog.** `store/dialog` boots the app and opens the store in the whole window (forty more items, long names, every source state, a read in progress and failed, an item's page and its review card), so a dialog that cuts its content is caught by the lab's cut check.

**Amended again, 22 November 2026 (the store's follow-ups: progress, reading while open, why a list is out of date, and recommended skills and plugins).**
- **Progress per source.** A read shows each source it covers: on Sources as the row's own words, on Browse as a "Reading the sources" section with one row per source (waiting, being read, read, could not be read, with the host's own reason) and the dots indicator for how many are done. The items of each source join the list as it finishes.
- **Sources are read again when they fall due while the store stays open.** The host only says a source is due when asked (`stale` is computed in `sources()`), and the view loaded it once, so a store opened hours later, or left open, decided from an old answer. The provider has an optional `reloadSources()` (it re-asks the host without reading anything); the store calls it each time it opens and every minute while its dialog is open, then reads what is due (six hours for a source, one for the registry, immediately for one never read or failed). A source that failed waits five minutes, then ten, doubling to an hour, before the automatic read tries it again; opening the store or pressing "Read the sources again" always tries. A closed store reads nothing.
- **"This list is out of date" says why and offers the fix, and the fix is checked.** The line names the cause: you are offline, which sources could not be read (the host's plain reason when one, and "Show why", which opens Sources, when several), which were never read, or which are older than their period and how old. "Read the sources again" is offered while the list is out of date. When a read that this page watched ends with nothing left out of date, the line says "The list is up to date: the 4 sources were read just now"; when a source still cannot be read, it keeps saying why.
- **Recommended skills and plugins are curated like the connectors** (`apps/shared/data/recommended.json`, `docs/RECOMMENDED.md`): each entry read against its publisher's own repository at a pinned full commit, with the manifest's hash, the licence from the publisher's own files (an entry with none is not listed), and a cited popularity signal with its date: skills by their installs on skills.sh, plugins by their installs in Anthropic's plugin directory. The signals have no common scale (nor with the connectors' stars), so each kind keeps its own order, most used first, and the kinds take turns on the front page and in Browse. Each item's page says which count placed it and when it was read. `scripts/read-recommended-popularity.py` reads both signals again every week in `live-store.yml`. What was left out, and why, is in `docs/RECOMMENDED.md`.

## ADR-0012 Prices
Prices come from the models.dev catalogue plus a user override table. Hermes's models.dev data is not reachable through its public plugin API, so:
- the plugin reads a cached catalogue file, `<profile home>/hypotaxis/prices/models-dev.json`;
- the host refreshes that file daily;
- in plain Hermes, the plugin can fetch it itself through RPC `prices.refresh` (one HTTPS GET to models.dev, on by default, switchable off in settings).

An unpriced model shows unknown cost, never zero. A session with a cost cap blocks on unknown cost. Rates are absolute per bucket (input, output, cache read, cache write, reasoning), never vendor multipliers. Dollars are always computed from tokens and never stored. A subscription provider prices at zero, with an API-equivalent projection shown beside it.

## ADR-0041 Every HTTPS request names its cryptography, a person never reads a raw failure, and the sign-ins are checked live (owner request, 22 November 2026)

**Context.**
- The owner, running 0.1.7 on Windows, 22 November 2026: "tried doing the step by step process for chatgpt login and it gave me this undecypherable error. all of these errors should be error treated, this is completely ass to understand. and again, all of the sign in flows should work seamlessly. you should test this one and all the other ones to make sure they're actually online. api keys flows should also work, but those are simpler." The ChatGPT step showed `i/o: task 424 panicked with message "No CryptoProvider for Rustls. Either enable feature `rustls`, or set process default using CryptoProvider::set_default(), or configure TlsConfig::rustls_crypto_provider()"`.
- **Why it panicked.** ureq is built with `rustls-no-provider`, so ring is the only cryptography in the tree. With that feature an agent takes the crypto provider its `TlsConfig` names, else rustls's process default, and panics on the first request when there is neither. No agent named one and nothing installed a default. **Linux panicked too**: a test making one real HTTPS request through `chatgpt::oauth::Https` and `providers::http::Https` at 019a4778 panicked the same way on Linux. Nobody had seen it there because no Linux flow in front of the owner had reached the network through the host (his model is the Claude subscription, which runs on Claude Code), the key check hid the panic behind "boopis could not check the key. The key is saved.", and every sign-in test answers over loopback `http`, which needs no TLS.
- **Why the raw text reached the screen.** A blocking task that panicked became `Error::Io(join_error.to_string())`, and the sign-ins' end events sent `e.to_string()` past the one mapper (`error::user_message`). The wires also put the transport's words, HTTP statuses and OAuth error names in their messages (`could not reach GitHub (io: ...)`, `answered 503 when finishing the sign-in`).

**Decision.**
1. **One TLS setup** (`src-tauri/src/tls.rs`): every agent (the sign-ins' transport, the provider checks', the store's) gets `tls::config()`, which names ring explicitly, and `run()` installs ring as the process default first thing, for anything that asks rustls without naming one. On Windows ureq also reads the system's proxy setting (`win-system-proxy`, the Internet Options proxy).
2. **A person reads what happened and what to do, never a raw failure.** `error::joined` maps a blocking task's `JoinError` to `hx.host.task_failed`, whose text is never shown ("Something went wrong inside boopis, and nothing was changed. Try again; if it happens again, the details are in Settings, General, Diagnostics."); the end events go through `error::shown`; each wire writes plain words (could not reach, check the connection or proxy; the service is having trouble, try again in a few minutes; an answer boopis could not use; the computer's clock is wrong; the answer could not be confirmed as OpenAI's) and keeps the raw words with `error::kept`. A web page where a sign-in service answers JSON, or a proxy's refusal, is `hx.provider.signin_blocked` ("Something on your network answered in place of the sign-in service"); xAI's "this account is not allowed" is kept for a 403 at the token step, after an account is known. In the UI an error with no code of the host's is `hx.host.unknown`'s sentence, and first-run shows a failed step in words without its code.
3. **Where the raw words go.** The log and Settings, General, Diagnostics ("errors behind the messages shown"), which already lists them: no disclosure was added to the cards, so a card stays one plain sentence and its button.
4. **Key checks that tell a wrong key.** A 400 whose error is about the key is a refusal (xAI answers a wrong key "400 Incorrect API key provided"). When a listing lists models, the check asks once more with no key; a list that answers again is open to anyone (NVIDIA NIM, Hugging Face, Kilo, Ollama Cloud, NovitaAI, Nous Portal). Where the provider has a route of its own that refuses a wrong key, the catalogue names it (`key.check` in `providers.json`) and the check asks it first, with the key in the wire's usual header and to that address only: a `GET` of an account or key page (OpenRouter's `/api/v1/key`, which moved from code into the data; Hugging Face's `/api/whoami-v2`; Kilo's `/api/profile`), or a `POST` of an empty JSON object to a chat route that checks the key before it reads the request (Ollama Cloud's `/api/chat`, NovitaAI's `/openai/v1/chat/completions`), so a working key is turned down only for the empty request (2xx, 400 or 422) and nothing runs. A route answer that says neither (a 404, a 5xx, a redirect) falls back to the list. NVIDIA NIM and Nous Portal have no such route (their chat routes read the request before the key, and their account routes take the key in a body or not at all), so a key for them is saved with words that say it is checked when first used, and no model count.
5. **A closed local port on Windows is nothing listening.** Windows retries a refused loopback connect for about two seconds; the local probe now gives the connect its own deadline, so only a server that accepted and said nothing is slow.
6. **A sign-in's tokens fit the Windows keychain.** Credential Manager holds 2560 bytes in one credential and the keychain library writes UTF-16, so one entry holds 1280 characters, and a ChatGPT ID token or access token is about 2000: the sign-in would have failed at its last step on Windows once it reached the network. `secrets/store.rs` keeps a longer value in parts on Windows (the entry names how many; `<account>.part-<n>` hold them; read, replace and delete handle them all); elsewhere one entry holds any value. A keychain failure is plain words for the platform, and what the keychain said is kept for Diagnostics.
7. **The live probe** (`tests/live_signins.rs`, ignored in normal runs) drives every sign-in and key check through the app's own code up to the step that needs a person, makes one real HTTPS request through each agent, and checks every message for plain words. `live-signins.yml` runs it on Linux, Windows and macOS on demand, every Monday and when the probe or the TLS setup changes, with no secret, and merges the platforms into one table (docs/RELEASING.md).

**Consequences.**
- On `windows-latest`, `ubuntu-22.04` and `macos-latest` every row passes: the three agents' HTTPS requests; ChatGPT's authorize page (on to OpenAI's sign-in), token endpoint (refuses a made-up code as documented) and signing keys; a real GitHub Copilot device code for boopis's client id and a pending poll; a real xAI device code and a pending poll; every key way's check of a key no provider issued; a custom endpoint's Test; no runtime shown on a clean runner; and, on Windows and macOS, the OS keychain keeping, returning whole and deleting a 2400-character token (the Linux runner's GNOME Keyring did not come up, so that row is `blocked` there; the owner's Linux keychain is the one boopis already uses). The first run on the three platforms found the seven key checks and the Windows ports above; the fixes are what made them pass.
- Not covered, because they need a person: signing in, approving a code, a real key. The owner's click-through covers those. The Claude subscription runs on the Claude Code program (its card is ADR-0039's and wave 24's Claude CLI work), so it has no row.
- New codes: `hx.host.task_failed`, `hx.host.unknown` (UI only), `hx.provider.signin_blocked`. `hx.signin.unreachable` and `hx.provider.unreachable` name the proxy.
- Not done: macOS's system proxy and Windows' automatic proxy scripts (PAC, WPAD) are not read (ureq reads the environment and, on Windows, the manual proxy setting only); NVIDIA NIM's and Nous Portal's keys are checked when first used (no route of theirs refuses a wrong key from a header, before the request). The key routes were seen to refuse a key no provider issued, from here and from the three runners; that each answers a working key as described rests on the providers' own documentation and clients (Hugging Face's `whoami`, Kilo's extension, Ollama's and NovitaAI's chat routes, which check the key first) and on the owner's click-through with real keys.

## ADR-0042 A bot is ungoverned unless the owner turns Governed on, and its home gets what the root has (owner decision, 22 November 2026)
**Context.**
- A bot is a named engine profile, `<root>/profiles/<bot>` (ADR-0006). The engine gives every home its own plugin manager (it scans `<home>/plugins`, gated by that home's `plugins.enabled`), its own configuration and its own secret sources, all inside one gateway process (`multiplex_profiles`). A bot made with `profiles.create` had none of what setup gave the root: no provider plugin ("Unknown provider" on the Claude subscription), no boopis plugin, no seat in groups (`groups.capabilities` offered `default` only).
- So the `gov`, `cap`, `workspace` and `approvals` boopis saved for each bot were written and never applied: every bot ran ungoverned, kai included, although its record said governed (the old default).
- The owner, 22 November 2026: "the bots actually should only be governed if i toggle it so. if i want an ungoverned opus bot, i should be able to have one. that's because technically the bot pipeline is already a governance of some kind, you just configure it manually. no need to make kai governed."

**Decision.**
- **Governance is opt-in per bot.** A new bot starts ungoverned, whatever its model; an ungoverned bot may use any model, opus included. The bot's Governed switch is the plugin's `plugins.entries.boopis.settings.mode` in the bot's own home, written from its `bots.write` record.
- **Turning Governed on needs a frontier model (ADR-0037).** On any other model the switch is refused with the plain reason and goes back; moving a governed bot to a model that is not frontier is refused the same way. Nothing flips silently.
- **Upgrade, once per install** (`governance_opt_in` in the host's `boopis/bots.json`): every existing bot whose record says governed is made ungoverned through the plugin's own `bots.write`, and one notice says, once: governed mode now really applies to a bot when turned on, these bots stay ungoverned as they ran, and Governed can be turned on per bot.
- **Main-window sessions keep their defaults**; this decision is about bots only.
- **Every bot's home gets what the root has, whether governed or not** (`bots::prepare`, at creation, restore, a model or switch change, for a bot that appears while the app runs however it was made (the engine's own CLI, another client: the live roster prepares any bot it did not have at its first read), and at every start through `bots::repair`, each step only when something differs; bots that need a restart together share one):
  - boopis and every plugin the runtime carries in `<bot>/plugins/`: a relative symlink on Unix, a versioned copy on Windows (symlinks need a privilege there); a link that already reaches the root's copy is kept however it was written, so hand-made links stay;
  - through the engine's CLI in the bot's home: the root's `secrets.boopis_host` wiring, the settings consented in setup, the plugin's `hx_path`, its mode and a ladder of the bot's own model when that is frontier; skills made for another OS are switched off whenever a bot is prepared (the engine leaves them out of the prompt but `profiles.describe` lists them as on), and on a new bot (and once on existing ones) the engine's bundled skills outside the bots' default index (ADR-0047);
  - `plugins enable boopis` after those, so the gateway loads the plugin with them; otherwise the control socket's `reload-plugins`, otherwise one gateway restart, never while work runs;
  - in the root, `hosted_rooms.profiles.<bot>` = the bot's home, so groups can seat it; removed on archive and delete, and a gone bot's entry is removed at start. A host-scoped ticket (what the engine's own desktop uses) was not chosen: the entries also work on Windows and for clients bound to a profile.
  - the hand-off skill (ADR-0033) in the bot's `skills/`, through the root plugin's `bots.guide`;
  - The plugin is in every bot's home because its hooks, the secret channel and the sign-in hand-overs must work for ungoverned bots too. Its copies share the host's captured credentials process-wide, in memory only, and only the root's copy syncs the sign-in pool (a bot reads the root's `auth.json`).

**Consequences.**
- An ungoverned bot is exactly what ran before, now with its model reachable; a governed one is really governed.
- The repair is idempotent over a home that already holds hand-made links and room entries; they are kept where they are right.
- A plugin update reaches every bot at the next start (a link follows the root; a copy is replaced when its version differs).

## ADR-0045 A local API for other clients: one feed, one inbox, one opt-in endpoint (owner request, 22 November 2026)
**Context.**
- The owner's Quickshell island (a bots extension of their desktop shell) reads the engine the way the host does: control socket, ticket, gateway WebSocket. Reading works. It asked for eight things (`docs/research/` has no copy; the asks are in the owner's playtest notes, "Asks for boopis, from the Panacea island"): a presence feed for every bot across every client, an approvals inbox answered from any client, a notifications feed, a send-to-bot call that shares the boopis window's thread, the look in the roster, a documented local entry point, a token-file loopback endpoint with Server-Sent Events, and a client tag (dropped by the owner: decision 5).
- **What the engine gives, read in its source (v0.23.2) and not patched (ADR-0023):**
  - One gateway process per host serves every profile (`gateway.multiplex_profiles`, `gateway/host_topology.py`). Each profile's link is its own *authority*, bound by the ticket.
  - An event reaches only the transports attached to its session. Sessions of the island, a cron job or a room turn are invisible to the boopis window's link.
  - What the engine does broadcast to every link is coarse: `sessions.changed`, `cron.changed`, `groups.changed`.
  - What a link can ask for any session of its profile: `session.active_list` (one row per live session: `source`, `status` of `working`, `waiting`, `starting` or `idle`, `model`, `title`), `approval.pending` (`request_id`, which is the `prompt_id`, `command`, `description`, `choices`), `session.events.since` (the ring, with each event's `execution_generation`) and `approval.respond {session_id, execution_generation, prompt_id, choice}`.
  - A creating client may name itself: `session.create {client: {name, version}}` (capability `session-client-v1`), kept in the session's frozen request and echoed as `session.info.client`: "a self-declared label, never an authentication". `session.create {source}` is a closed list (`cli`, `tui`, `gui`, `acp`, `tool`, `oneshot`), so the island's `source: "panacea-island"` is not the field; `client` is. (boopis does not use it: decision 5.)
  - The engine's gateway has no extension point for a client to add methods or events: a plugin can add `plugin.boopis.*` methods to a session's link, never a global event.

**Decision.**
1. **The host computes every feed, and nothing in the engine or the plugin changes.**
   - It already holds a link per profile, the app's data folder and the keychain's neighbours, and it is the only process that sees the boopis window's own turns event by event.
   - A plugin-side feed was weighed and refused: not every bot's home loads the plugin (the playtest's B1), a plugin hook sees tool calls but not the streaming words an orb needs, and the engine gives a plugin no global event to send.
   - **Each feed has two inputs.** The events on the host's own links give fine states (thinking, working with a tool's name, speaking, needs, done, error). A poll of `session.active_list` on every profile's link, while at least one consumer listens, gives the rest: other clients, cron runs and room turns, with their `source`, at a coarser grain (`working`, `needs`, `thinking` for a session that is starting, `idle`). A fine state wins for three seconds after its event, and a poll never invents a fine word.
   - A consumer is the boopis window's own feed readers and the endpoint's streams. With none, nothing is polled.
2. **The contract is boopis's own and versioned (`docs/LOCAL-API.md`, version 1), carried two ways.**
   - In process, as typed Rust values the UI's own toasts read.
   - For other clients, over the loopback endpoint of decision 3 (events as Server-Sent Events, calls as JSON over HTTP), and for what the engine already offers over its own gateway (`boopis connect --json`, which says how to dial it and which profile homes are served by which gateway).
   - **The island's ask for gateway methods (`bots.say`, a `look` in `profiles.list`, `bots.presence` on the user's link) cannot be met on the engine's own WebSocket without patching it.** The same calls exist as `GET /v1/bots`, `POST /v1/bots/<name>/say`, `GET /v1/events` and the rest, on the loopback endpoint. That is the stated place the island reads them.
3. **The endpoint is opt-in, off by default, and a small hand-written server** (no new dependency: the ChatGPT callback is the precedent, `chatgpt/callback.rs`). Its security model is the section below.
4. **Approvals answered by any client keep boopis's rules** (below).
5. **No client label anywhere** (owner decision, 22 November 2026: "if i sent a message in the island it should just mirror in the actual program, and vice-versa. no need to separate where they're from, be it messages or anything else."). This replaces the first plan, a client tag the engine keeps.
   - The contract has no `client` field and reads no `X-Boopis-Client` header (one an old script sends is ignored). A conversation started through the endpoint is created exactly as the app creates one (`session.create {source: "gui"}`), so it is named and shown like any other. Nothing tells a message, a session or an answer apart by where it came from.
   - Presence keeps `source`, which is the engine's own kind of session (the app, a scheduled run, a room turn, anything else), not who started it; a scheduled run is told apart because it is a different thing, not a different client.
   - The approvals audit file keeps only the surface an answer came through (`gui` or `endpoint`), a security record that no screen shows.
6. **A conversation is one thread, mirrored both ways** (owner decision, same day). A message the owner types in the app shows in a client, and one a client says shows in the app, in the same thread.
   - **Reading.** `GET /v1/bots/<name>/conversation` is the stored transcript the app itself reads (`session.transcript`, which never attaches to the session): the owner's and the bot's words, oldest first, no tool row, nothing the app hides. No engine patch, and no copy of the thread in boopis.
   - **Following.** A stream that asks (`conversations=1`, optionally narrowed with `bot=<name>`) gets `conversation.message` events: each message added, from either side, and a reply as it is written (the text so far, again at most every 250 ms, then once finished, under one id). The host copies the words of a reply and of a message typed in a window off its own link only while such a stream is open; otherwise a delta is never parsed and a typed message is never copied.
   - **Writing.** `say` keeps writing into the conversation the app shows (the engine's latest), by the engine's own `prompt.submit`, so both sides are one thread. It uses the bot's own link, the one the open chat holds, and the engine's resume of a live session returns the same session, so the reply streams in the open chat. The engine tells a window nothing about a message submitted elsewhere, so the host announces it (`connection.said`, before it submits; `connection.said_failed` if the engine refuses) and the chat draws it as the owner's own message with no mark of where it came from. A room is the engine's own `groups.send`: the open room shows it from the engine's `groups.changed`, as it does one typed there. It makes a message event too, so a following client sees what another client said.
   - **What is covered.** Sessions that run on the host's own link: the app's conversations and those `say` starts. A conversation a client runs on the engine's gateway by itself is invisible to the host's link (decision "what the engine gives"), so that client reads it there.
   - Same security rules as every other route: typed fields, the scrubber on every word (line breaks kept), a message cut at 16 KiB and says so, 6 bots at most in a narrowing, 200 rows at most in a read, the same limits and token.

**Security model of the endpoint.** The threats are a web page in the owner's browser (cross-site requests, DNS rebinding), another user of the machine, a client that floods or stalls the server, and anything that makes a secret leave. Another process of the same user is out of scope exactly as it is for the control socket and the keychain: it can read the owner's files.
- **Off until the owner turns it on** (Settings, one switch; a setting that is not read by anything else). Turning it off closes the listener and every stream and deletes the token file.
- **Binds `127.0.0.1` only**, never another address, never IPv6, on a fixed preferred port and else a free one. The endpoint's address is written beside the token (`<app data>/client-endpoint`).
- **Token.** 256 bits from the system's random source, compared in constant time after hashing. Written to `<app data>/client-token`, created mode `0600` by a temporary file renamed into place (never readable by another user, not even for an instant), re-checked on every start, **rotated at every start** and when the owner presses Rotate (every open stream is closed). On Windows the file relies on the user profile folder's access list; the owner accepted that (22 November 2026), and it is not tightened further. It travels only in `Authorization: Bearer`; **never in a URL**, so no log, history or referrer holds it; therefore no browser `EventSource`.
- **Host and Origin.** The `Host` header must be exactly `127.0.0.1:<port>` or `localhost:<port>`; any other name (the rebinding case) is refused before anything else is read. A request that carries `Origin` or any `Sec-Fetch-*` header is refused: this is not a web API, so no browser may call it. There is **no CORS**: no `Access-Control-*` header is ever sent and `OPTIONS` is refused. A `POST` must say `Content-Type: application/json`.
- **Caps.** Request head 8 KiB and 32 headers, target 512 bytes, body 64 KiB, a message to a bot 32 KiB; 5 s to send the head and the body; 16 connections at once, 8 event streams; a token bucket for requests and a stricter one for writes; five wrong tokens in ten seconds shut the door for ten seconds. A stream whose reader falls behind by more than 256 events is told so and closed, never buffered without bound. One request per connection (`Connection: close`) except the stream.
- **No secret ever crosses it.** Every response and event is a typed value with fields chosen one by one; no engine object is forwarded. No ticket, token, key, path of a secret or environment variable exists in any type. Free text from the engine (an approval's command, a description, a tool's name, a message preview) is passed through a scrubber that removes bearer tokens, ticket strings, well-known key shapes and long opaque strings, plus the exact values of the host's own token and any ticket it holds. A test sends a canary of each through every route and reads every response and event for it.
- **Errors say what to do and never echo input.** A refused request gets a code and a sentence, and the server logs the reason, never the token or the body.
- **`boopis connect --json`** is not the endpoint. It runs as the owner in their terminal and prints how to dial the gateway: with `--ticket` a single-use ticket (30 seconds) is minted through the control socket and printed to that process's output and nowhere else; without it, no credential. It is the control socket's own authority, which any process of the owner already has.

**Approvals from any client.**
- An approval is a row only the engine can make: from its `approval.request` event on a boopis link, or from the poll of a waiting session (`approval.pending`, with the generation and the time limit found in the session's ring). Nothing else creates one, and a row the engine no longer holds is closed.
- **First answer wins.** The inbox moves a row from pending to answering under one lock before it calls the engine, so a second client gets `409 already_answered` saying where the first came from (the app or the local API). If the engine refuses or the call fails, the row goes back to pending so another client can answer; if the engine says it was already settled, the row closes as settled by someone else. The engine's own atomic resolve settles a race with the boopis window.
- **The same rules as the window's card.** The window answers `once` or `deny` only; so does every other client. `session` and `always` (a standing grant) are refused from outside the window, whether the bot is governed or not, whatever the engine offered, with a sentence saying to grant that in boopis. The `choice` must be one the engine offered for that row, and the generation must be the row's. A governed session's rows carry `governed: true` and are never answered from a stale generation. A missing or unknown `choice` is a 400: there is no default, no "approve all", no timeout that approves.
- **Every answer is recorded with how it was given**: an append-only line in `<app data>/audit/client-answers.jsonl` (mode 0600, bounded, rotated by size) with the time, profile, session, prompt, choice, outcome and the surface (`gui` for the app's window, `endpoint` for this API), never a name; and the `approvals.changed` event carries the same surface. The boopis window's own answers are seen on the proxy and recorded the same way.

**Consequences.**
- The island needs no ticket dance and no per-bot link: one endpoint, one token file.
- Presence for sessions of other clients is polled (about two seconds) and coarse; the fine states exist for sessions the boopis window itself runs. Said in `docs/LOCAL-API.md`.
- **One token for every local client** (owner decision, 22 November 2026: per-client tokens are skipped). Any holder of the token can do everything the token allows, and no client is told apart from another. A client is cut off by Rotate, and by the new token every start makes.
- A gateway upgrade that changes `session.active_list` or the approval shapes is caught by tests built on the engine's shapes, and by the contract version.

## ADR-0046 A message written while a room's members work is held by the host, once for every client (owner report B30, 22 November 2026)
**Context.**
- The engine runs one discussion per thread and a newer user message ends it: a member still working has its answer dropped (`turn.cancelled`, `superseded_by_newer_user_event`, `gateway/hosted_room_discussion.py plan_publication`). It has no queue, steer or interjection for a room; `groups.send` is the only way in, and it is idempotent by event id.
- The 0.1.8 fix (B16) held such a message in the app's room only, in the webview's memory: `boopis groups send`, `run --group` and the local API's room say went straight in (B30, a 95-second table thrown away), and a held message was lost when the app closed or a second launch replaced it (B28).

**Decision.**
1. **The hold is the host's, and every client goes through it** (`rooms/hold.rs`): the app's room (`room_send`, `room_unhold`, `room_send_now`, `room_held`, `RoomHeldEvent`), the command line and the local API. The webview keeps only a mirror for the room's strip.
2. **One busy rule** (`rooms/discussion.rs`): members at work (`groups.state`), or a discussion the log shows open (the engine's own `_pending_discussion` reading) that showed life in the last 45 seconds; an open discussion silent for longer is taken as stuck, so nothing waits on it forever.
3. **Held messages are kept in a file** (`<app data>/room-holds.json`, versioned, changed under an exclusive file lock that is never held across a call to the engine, written by one rename), so they survive the app closing. The app's pump sends a room's oldest held message when the room is free, every two seconds while anything is held; a command that held a message waits for it and pumps too, so it goes out without the app, and an interrupted command leaves it for the app or the next command.
4. **Two senders make one message**: a held message carries the event id it will be sent with, minted when it was held, and the engine's `groups.send` returns the existing event for an id it has.
5. "Send now" stops the running turns first (`groups.stop`) and says so where it is offered; a message is taken back only while it is still held.

**Alternatives weighed.**
- *Hold in each client* (the 0.1.8 shape, copied to the command line and the local API): three implementations of one concern, and held messages die with their process.
- *The command line asks the running app to hold for it* (over the local API): the endpoint is off by default and the app may not be running, so a command would still need its own fallback.
- *A plugin-side queue*: the engine gives a plugin no hook before `groups.send`, and not every bot's home loads the plugin.
## ADR-0047 A bot's skill index is short by default (owner report B38, 22 November 2026)
**Context.**
- The owner's field report (0.1.9, engine 0.23.2): a one-word "ping" to a bot read `input 377, cache_write 42,695`. Every fresh chat, `boopis run --bot` call and kanban worker writes the whole prompt to the cache again: the SOUL, the skill index and the tool schemas. The report asked for a smaller default skill index for bots.
- Measured with the engine's own prompt builder (`agent/system_prompt.py` `build_system_prompt_parts`, an `AIAgent` built offline for a bot home with the 44 bundled skills, `hermes-cli` plus `kanban` toolsets, tool search off; token counts are the engine's own estimate, `estimate_tokens_rough`, about four characters a token): system prompt 3,558 (stable tier 2,106 with the SOUL, volatile tier 1,452), of which the `<available_skills>` block is 813; tool schemas 16,667 (35 tools, the 15 kanban tools about 6,800 of them). The engine already leaves skills for another OS out of the index (`skill_matches_platform`), so the macOS skills cost nothing in the prompt.
- That accounts for about 20,000 of the 42,695. The rest was not measured here: the Claude subscription provider (the official Claude Code program behind `claude-subscription-directsdk`), tools the measured home did not offer (the browser and computer-use toolsets the owner's bots list), MCP servers such as `fetch`, and a project's context files all add to it.
- The engine offers one per-home switch for skills: `skills.disabled` (read by the index, by `skill_view`, which refuses a disabled skill, and by `profiles.describe`). It has no allow list. A disabled skill is not force-loaded either, so a skill the engine itself loads (the kanban review lane loads `sdlc-review` into every review worker) must stay on.

**Decision.**
- **A bot keeps the bundled skills `apps/shared/data/bot-skills.json` names, and boopis switches the engine's other bundled skills off** in the bot's own `skills.disabled` (`bots::skills::outside_default`, step 2 of `bots::prepare`). The list is the owner's to change; this build's: `hermes-agent` (the engine never lets it go), `sdlc-review` (the review lane loads it), `grounded-citations` and `blocked-page-recovery` (the Paper Past researchers cite and fetch sources).
- **Only the engine's bundled skills, by the engine's own list** (`skills/.bundled_manifest` in the bot's home). A skill from the store, a team file, one the bot wrote and boopis's own `boopis-handoffs` are never touched; a home without that list loses nothing.
- **Once per bot**: when boopis makes it, and once for every bot made before this (`<root>/boopis/bot-skills.json` remembers which), so a skill switched on since is never switched off again. Set at preparation only, never in a running session (invariant 4).
- **Widening is per bot**: its skill switches in the app, `skills:` in a team file (`team apply` switches a new bot's named skills on after making it; `team export` writes every skill a bot has on that a new bot would not), or the engine's own `skills enable`.

**Consequences.**
- Measured the same way: the `<available_skills>` block goes from 813 to 89 tokens and the system prompt from 3,558 to 2,834, so a fresh prompt is about 724 tokens smaller, about 3.6 % of what the engine builds and about 1.7 % of the 42,695 the owner saw. The tool schemas are the larger part; which tools each bot needs is ADR-0048 (toolsets are fixed at `session.create`).
- A bundled skill the engine adds in a later version reaches existing bots switched on (the list is applied once per bot); one made for another OS is switched off at the next preparation.

## ADR-0048 A bot's toolsets fit its role, and kanban goes to a bot on a board (owner decision, 23 November 2026)
**Context.**
- After B38 (ADR-0047) the owner chose the proposal: a bot gets only the toolsets its role needs, and `kanban` only when it is on a board.
- Read in the engine (v0.23.2): a session's tools are its toolsets' schemas, fixed when the session is created. A chat, a `boopis run --bot` run and a kanban worker read the profile's `platform_toolsets.cli` (`gateway/session_policy.py` `_resolve_toolsets`); a group room's turn reads `platform_toolsets.api_server` (`gateway/hosted_room_execution_policy.py`). A kanban worker's session gets `kanban` added whatever the profile says (`gateway/session_kanban.py`), and its lifecycle tools are shown to a worker by the worker's own context (`tools/kanban_tools.py` `_visible`). The engine's own `hermes tools enable|disable --platform <p>` saves a list and keeps its record of what was offered and declined. `agent.disabled_toolsets` would subtract `kanban` from the worker too, so it is not used.
- Measured with the engine's own dry run, `hermes prompt-size` (offline, bytes; about four bytes a token), for kai's SOUL and the 44 bundled skills, tool search off (the browser, computer-use, cron and image tools could not load where this ran, so the real before is larger):

  | | chats and workers (`cli`) | room turns (`api_server`) |
  |---|---|---|
  | 0.1.9, `kanban` on, every bundled skill | 79,874 B (35 tools, 66,676 B) | 76,777 B (33 tools, 63,271 B) |
  | defaults, on a board | 59,859 B (30 tools, 49,738 B) | 60,167 B |
  | defaults, not on a board | 32,519 B (15 tools, 22,467 B) | 32,827 B |

**Decision.**
- **Defaults.** `apps/shared/data/bot-toolsets.json` lists what every bot has on (file, terminal, web, vision, skills, memory, todo, clarify) and off (kanban, browser, computer_use, delegation, code_execution, session_search, connections, cronjob, tts, image_gen), and what a bot on a board gets (kanban). A toolset in neither list is left as the engine has it (a plugin's, an MCP server's). The owner chooses the lists.
- **Once per bot**, like the skill index: when boopis makes it, and once for every bot made before (`<root>/boopis/bot-toolsets.json`). A toolset switched on later stays on.
- **On a board** means a card on a live board is assigned to the bot, or the bot is in a group whose board exists (the board named like the group, as the group's board view finds it). `kanban` is given once, when boopis first finds the bot there, at preparation or at the start-up repair, and never taken away by boopis. When the boards cannot be read, a bot's `kanban` is left as it is. A worker does not depend on any of this.
- **One writer, every platform.** The plugin's `bots.toolsets` runs the engine's own `tools enable|disable` for `cli` and `api_server` alike; the host's preparation, the bot's settings (a switch per toolset, saved at once) and a team file (`toolsets:`, every toolset on; export writes it) all go through it. A team file's list is the owner's own: boopis gives that bot no defaults afterwards.
- **Prompt caching.** A change applies from the bot's next new session; the settings say so in one line.

**Consequences.**
- A board bot's fresh prompt is about 20,000 bytes (about 5,000 tokens) smaller than in 0.1.9, a bot off the boards about 47,000 bytes (about 11,800 tokens). `kanban` alone is 27,241 bytes of a board bot's tools.
- An edit made with the engine's own editor changes the `cli` list only; boopis's switches keep both lists equal.

## ADR-0049 A bot can have a project folder (owner decision, 23 November 2026)
**Context.**
- After B14 (`bots::soul`) the owner chose the proposal: a bot has a project folder whose `AGENTS.md` or `CLAUDE.md` the engine loads itself, instead of an include copied into its SOUL.
- Read in the engine (v0.23.2): a named profile's `terminal.cwd` is where its sessions start (`gateway/session_policy.py` `_profile_workspace_cwd`), and the engine loads that folder's context files into each new session (`agent/prompt_builder.py` `build_context_files_prompt`, through `resolve_context_cwd`). A group room's turn runs in the member's profile scope (`gateway/platforms/api_server.py` `_profile_scope`, `_profile_runtime_scope`, which binds the profile's whole terminal policy), so it reads the same folder; checked offline (the profile's terminal scope carries the folder, and the loader reads its `CLAUDE.md`), not with a live room. A kanban worker starts in its card's workspace instead (`gateway/session_kanban.py`), which is why the hand-off skill makes cards with `workspace_kind: "dir"` in the project folder (B35). The engine treats a missing folder as unset and falls back silently.

**Decision.**
- **The folder is `terminal.cwd`** in the bot's configuration, through the plugin's `bots.project` (the engine's `config set|unset`): in the bot's settings (a path field and the system folder picker), in a team file (`project:`) and in `boopis bots create|set --project`.
- **Fail closed.** A folder that is not there or cannot be read is refused when it is set, and one that disappears later is a problem on the bot at every start, never a silent fallback. The SOUL path check stays as it is.
- **Prompt caching.** It applies from the bot's next new session.

**Consequences.**
- A bot whose project lives in a repository reads that repository's own instructions in its chats and rooms, fresh at each new session; nothing is copied into its SOUL.
- A kanban card made without `workspace_kind: "dir"` still runs in the board's scratch folder, without the project's instructions (an engine report asks for a better default).

## ADR-0050 A bot's own rules are enforced: budgets, capability tiers, labelled traffic, one body (owner request, 23 November 2026)
**Context.**
- A bot's "Cap per run" and its approval switches were saved in its `boopis/bot.json` (`bots/store.py`) and nothing outside the bots module read them. The only cap enforced was the plugin's `cost_cap_usd`, per session, in billed dollars, so a subscription never reached it. The app said so for the session cap ("it cannot be changed from here yet") and showed a bot's spend as a fixed "$0.00 of $0.60". That broke invariants 5 and 6.
- What the engine gives a plugin (v0.23.2, read in its source, not patched): `pre_llm_call` fires once per turn and may block it or add context to the user message; `pre_api_request` cannot block; `pre_tool_call` fires before every tool call and may `block`, `modify` the arguments, or return `approve`, which holds the call at the engine's own approval gate (`request_tool_approval`), the same gate the local API inbox, the app and chat platforms answer; `post_approval_response` reports a person's answer with the rule key; the engine's own gate auto-approves under yolo, `approvals.mode: off` and an approving cron mode, and then reports nothing.

**Decision: budgets (C1).**
- **The hierarchy, the tightest wins:** a bot's cap per run (`bot.json` `settings.cap`), a room's budget (not built: below), the team's monthly budget (`<root>/boopis/budget.json`, one number for every profile of the root, set with `budget.set`), and beside them the session's `cost_cap_usd` as before. `budget/` is the one implementation.
- **A run is one turn of the bot**: a chat message, a room turn, a kanban card's worker, a scheduled run, one step of `boopis run --bot`. Its spend is every model request of the turn (side calls and cascade workers included), accounted from `post_api_request` with its `turn_id`, the same usage the ledger and the turn book carry.
- **API-equivalent dollars**: the bot cap and the month count tokens priced as the API bills them, whatever the provider. The Claude subscription reports its aliases (`opus`, `sonnet`), so the price book prices an alias as the model the frontier table's alias names, at Anthropic's price (`PriceBook.resolve`); without that every capped run on the subscription would have been unmeasurable. On a subscription the plan bills nothing per token and its real limit is a quota the engine does not report, so what can be enforced there is a token budget expressed in dollars; the UI says so where the cap is set. What cannot be enforced is the plan's own window (the quota left); C6 is the place for it.
- **Enforced mid-turn.** The cap is checked before every tool call: a run overshoots by at most the model request that asked for the tool, and its reply after it is told to stop. At the cap the call is held at the engine's approval gate with the bot's name, what it spent, the cap and what Allow does; Allow raises this run's cap by the cap again, Deny or no answer stops the run and every later tool call is refused with a sentence telling the model to stop and report. Each pause has its own rule key, so an "always" cannot approve the next one, and a pause the engine let through without a person (no answer recorded) stops the run at the next call. A bot whose spend rule is Block stops at the cap with no card; Allow is read as Ask (a cap is never passed without a person). A model with no price makes the run unmeasurable: it pauses the same way, and Allow lets that run go on unmeasured.
- **The month** is computed on the way in from every profile's ledgers (each file re-read only when it changed, the set at most every 30 seconds), priced the same way; a model with no price is listed and left out, never counted as free, and a session whose own model has no price is refused while a budget is set. A spent month stops the turn at its start and the run mid-turn: raising it is the owner's change, not a run's. A budget file that cannot be read stops every turn.
- **Not built, said:** "continue on a cheaper model" at the pause: a plugin cannot change a running turn's model through the public API (the engine's `config.set model --once` is a client method), and swapping the model in an `llm_request` middleware would put the wrong model in the engine's usage reports and the turn book. Room budgets: a member's turn reaches the plugin as a session of the bot's profile, and the room id is not in what a hook receives (only the room's name in the engine's prompt), so a budget keyed by room cannot be counted reliably yet. The session cap in the Sessions details stays the plugin's `cost_cap_usd` and keeps its "cannot be changed from here yet" line.
- **Live spend**: the plugin emits `budget.updated` after every model request; the bot's room shows this run's spend against its cap where it showed a fixed number, and "—" until the plugin has said.

**Decision: capability tiers (S1).**
- **The switches are tiers, enforced in the one permission function.** Each kind of action a bot may take is Allow, Ask or Block: deploying anywhere (`deploys`), pushing to protected branches (`push`), reaching the network (`network`), spending past the run cap (`spend`), messaging people (`people`), writing outside its workspace (`outside`), deleting files (`delete`) and running commands (`commands`); and per tool, by name, where the record names one (an MCP tool `mcp__server__tool`, or `mcp__server` for every tool of a server). `policy.check` judges it for a session that runs for a bot (`SessionPolicy.bot`, read from the record at every call, so a change applies at once), after the deny rules, protected paths and governed mode and before the ask and allow rules: Block refuses, Ask holds the call at the engine's own approval gate (the same card the local API inbox, the app and the island show; a new rule key per call, so "always" never approves the next one; from an exec cell an ask is a refusal, as for every ask), Allow goes on and never widens a deny or an ask rule.
- **What a call is** is data, in one file (`policy/bot_tiers.json`): tools per category, command patterns read from `terminal`'s command line word by word (`sudo`, `env`, `sh -c` opened; a line the splitter cannot read is scanned token by token, so it over-asks rather than misses), MCP tools as network, the policy's own network tools as network, and a write whose path is outside the session's folder (or unknown) as outside. The strictest tier among a call's categories wins. A tool in no category and not on the quiet list (reading, planning, the board, boopis's own tools) asks: an unknown kind of action fails closed. A tier value that is not a tier asks.
- **Old switches** read as they said: on is Ask, off is Allow. Every bot made before tiers was given all six on; the owner decided (below) that those untouched records move to the defaults once.
- **Spending past the cap** offers Ask and Block only, and Allow is read as Ask (ADR-0021's protected spend class): a cap is never passed without a person.
- **Defaults** (a bot whose record names no tier for a kind): every kind Allow; spend Ask, the built-in protection (amended 27 November 2026, below; until then deploys, push, people, outside and delete were Ask too). **Presets** a record may name (`settings.preset`), for the owner to choose: `lead` (deploys, push, spend, people, outside and delete Ask, network and commands Allow: the defaults before 27 November 2026), `research` (network Allow, commands Ask, everything else Block), `writer` (network, delete and commands Ask, everything else Block), `builder` (commands Allow, spend and people Block, the rest Ask), `reviewer` (network and commands Allow, the rest Block), `publisher` (network Allow, spend, people and commands Ask, the rest Block). New bots are made with no tiers written, so the defaults apply. The app shows the tiers the plugin reports (`bots.read` `tiers`), one row each with the kit's segmented control; a kind it did not report has no row.

**Decision: bot-to-bot traffic is labelled, and no bot answers for the owner (S2).**
- **Where messages enter a bot's context**, through what the engine gives a plugin: `pre_llm_call` (once per turn, with `platform`, `sender_id` and the user message) and the session context the engine binds (`gateway.session_context.get_session_env`, on the public plugin API list: `HERMES_SESSION_SOURCE` is `bot_room` for a room member's turn, `a2a` for a forwarded one, `kanban` for a card's worker, and cron sets its own). A room member's turn arrives as the room worker's prompt, which already marks authors (`User (user):` for the owner, `@handle:` for a teammate, a scheduled job's post as automated); a forwarded message is written by the peer; a card's body by whoever filed it. `bots/origin.py` reads which it is, and the turn's user message gets one line (`pre_llm_call` context, never the system prompt) saying where it came from, which lines are the owner's, and that nobody but the owner approves anything. The owner's own surfaces get no line; a surface the plugin does not recognise is never taken for the owner.
- **No bot answers for the owner.** A bot holds no ticket of the engine and cannot read the local API's token: the token file is a denied read for every session (`denied_read_paths`, by name and by its place beside the engine's root). On top of that, for a session that runs for a bot, any tier: a command line, code or URL that names an answer method (the gateway's `approval.respond`, `clarify.respond`, `groups.approve`, the plugin's `form.submit` and `form.cancel`, the local API's approvals route, `gateway attach` or `connect --ticket`), and a message a people tool sends whose first word answers an approval on a chat platform (`/approve`, `/deny`, ...), are refused with a sentence telling the bot to tell the owner instead. The words are a best effort; the token and the ticket are the boundary.
- **Every approval card of a bot says which bot asks and at whose request**: the tier's card, the policy's own ask rules and the run cap's pause end with "(Asked for by @nina, a teammate in the room “paper past”.)", "(For kanban card t_ab12, ...)", "(On its schedule, ...)" or "(Asked for by the owner.)".
- **What needs the engine** (report written for its maintainers): structured origin in `pre_llm_call` (the author `{id, name, is_bot}`, the room, thread and discussion ids and the member id), so a plugin need not read the room's prompt; and a veto hook before an approval or a clarify is resolved, carrying the answering principal and surface, so a plugin can refuse an answer that does not come from the owner whatever path it took.

**Decision: one bot, one body (T1).** Enforced in the plugin, so it does not depend on a bot having read the `boopis-handoffs` skill (branch w29/bots-skills keeps that skill and `bots::give_handoffs`; this builds on its findings: a dispatcher's worker has no `kanban_list`, no tool archives a card, `kanban_block` refuses a todo card).
- **A bot's `kanban_create`** is the last step of `policy.check`, when the rest allows it. A room turn's card with no `idempotency_key` gets one derived from the room, the discussion (a digest of the owner's message that opened it, read from the room worker's prompt), the member and the title, so a retried turn gets the card that exists (the engine's `create_task` returns it); a key the bot passed is kept, as the skill asks. A card whose title or body says it waits for other work ("after iris's fixes", "once ... is done", "depends on"; patterns in `policy/bot_tiers.json`) and names no `parents` is refused with how to file it. A card that names no workspace, on a board with a `default_workdir`, gets `workspace_kind: "dir"`, so it runs in the project's folder (B35); the folder is read from the engine's own `kanban boards list --json` in the root home and kept a minute, and a board it did not list gets nothing.
- **A claim.** The turn that starts work for a bot (a room turn, a kanban card's worker, a scheduled run, a forwarded message) takes the bot's claim, one `O_EXCL` file in its home (the holders are in different processes). Another turn of other work is refused at its start, with what holds the bot and since when; the same work claims again (the next round of the same discussion, a card's next turn). It is released at the turn's end, the session's end, at the engine's `kanban_task_completed` and `kanban_task_blocked` hooks, and when its holder's process is gone or it is older than 12 hours; a claim file that cannot be read counts as held. `settings.parallel: on` in the record lets a bot work on several things (no row in the app yet: the owner places it). The owner's own chat with the bot takes no claim and is never refused; it is told what else the bot is doing.
- **Not built:** `claimed_by` and locked paths on the engine's card itself (the card already records its `assignee` and the dispatcher's `claim_lock`; writing a field of boopis's needs the engine), a claim for `boopis run --bot` (its turns reach the bot's session as the owner's own; the host's run would have to say so), the cards a cancelled turn created shown in the thread and put into the next turn (needs the engine's discussion events), and presence with `source: kanban` and the card's title (the local API's, on another branch).

**Decision: the defaults for the bots that exist (owner decision, 23 November 2026).**
- **Tiers.** A bot whose approvals are still exactly the switches boopis made it with (the first six kinds, all on) gets the default tiers written into its record once (since 27 November 2026, every kind Allow and spend Ask; before, deploys, push, people, outside and delete Ask too). Approvals changed by hand stay as they are.
- **No default limits for any bot** (this replaces a $5 default the same day). Budgets and caps are optional and off until the owner sets one; usage is still counted and shown (`budget.updated`, the bot room's meter shows this run's spend with or without a cap). New bots are made with no cap (the Bots form and `boopis team apply`, which also no longer write tiers). A cap that is still one boopis wrote is removed once: the first default, $0.60, and the $5 the earlier build of this move wrote (a bot that build recorded, still on $5). A cap the owner set to anything else stays. An empty cap in the settings removes it. The team's monthly budget stays unset unless the owner sets it.
- **Once, recorded.** `bots/defaults.py` makes these moves where the plugin first meets a bot (the roster read and the bot's own turn) and records each bot it looked at, moved or not, in `<root>/boopis/bot-defaults.json` (`{schema_version: 3, tiers: [bot], caps: [bot], cap: [bot], asks: [bot]}`: `cap` is what the earlier build looked at, kept to tell its $5 from one set by hand), as the host records the skills and toolsets it gives once. A bot is never moved twice, so a tier or a cap the owner sets later is never overwritten. A record that cannot be read is left and looked at again; an archived bot waits until it is restored.

**Amendment: bots have no asks of their own (owner decision, 27 November 2026).**
- **The owner's model.** Only the shared Approvals list makes a bot ask, plus a rule the owner sets for one bot. ## ADR-0059 Dictation is heard on this computer: native capture, whisper.cpp, a model fetched once, and only the person's press opens the microphone (proposed, 26 November 2026)
**Status.** Proposed: built on `w33/transcription` and proven with a recording through the real model; not yet tried with a person at a real microphone on any of the three systems.

**Context.**
- The owner: "the microphone button is simply a transcription button. it reads your voice and transcribes it into text. that is simple and should already exist." It did not: the live provider's dictation was a stub, nothing in the host heard audio, and only the mock invented a transcript.
- The owner writes English and Portuguese. Dictated text is often private, and a composer is a place for it.
- The app runs in WebKitGTK on Linux, WebView2 on Windows and WKWebView on macOS. A web view's own `getUserMedia` differs in each (WebKitGTK needs its media stream switched on and its own permission answer), and what it records would then have to cross into the host anyway.
- Talking to a bot (the voice circle, a voice model with a key) is another feature and is not decided here.

**Decision.**
1. **Local, with no key and no account.** Speech is turned into text in the app's own process. Audio is never sent anywhere and never written to disk, a log or a socket. No cloud transcription, not even as a fallback.
2. **The host captures, natively.** `crates/boopis-dictation` reads the system's default input device through `cpal` (ALSA on Linux, where PipeWire and PulseAudio answer as the default device, with no second backend; WASAPI on Windows; Core Audio on macOS). The page never opens a microphone.
3. **whisper.cpp on the CPU** (through `whisper-rs`), with the multilingual `base` model quantized to 5 bits (`ggml-base-q5_1`, 59,707,625 bytes), the language heard by the model itself. `boopis_dictation::model::MODELS` is the table a larger model is added to, and `AppSettings.speech_model` names a row (read at start; no control for it yet).
4. **The model is fetched on first use, never bundled**: from the whisper.cpp model repository on `huggingface.co` at a pinned commit, over HTTPS with the host's one TLS setup, redirects followed only to that repository's own hosts, to `<app data>/speech/`. It is written to a `.part` file, continued after a cut connection or a restart, and given its name only when its SHA-256 is the pinned one (`422f1ae4…8898`). It is hashed again every time it is loaded, and whisper.cpp reads the bytes that were hashed, not the file. A file that is not the model is deleted and reported; nothing unverified is ever loaded.
5. **Only the person's own press starts the microphone.** The one way in is the `dictation_start` command, which the capability file allows to the main window alone and which checks the calling window. The local API, the command line, the gateway proxy, bots, mods and deep links have no way to it, and two tests keep it so (the local API's `nothing_reaches_the_microphone`; the host's `nothing_but_the_command_reaches_the_microphone`, which reads the host's own sources). It stops when the composer says so, when the window closes or its page loads again, when its events cannot be delivered, and at a hard cap of 5 minutes with a plain sentence. One dictation listens at a time.
6. **Words appear while the person speaks.** Speech is cut into stretches at pauses (0.7 s) and at 24 s; the stretch being spoken is written down again every 2 s when the last attempt has come back (a `partial`, which replaces the last), and a finished stretch for good (a `final`). A slow computer gets fewer partials, never a queue of them, and a partial is given up when a final waits behind it.
7. **One whisper.cpp for every processor.** `.cargo/config.toml` names the x86-64 instruction set (AVX2, FMA, F16C, BMI2: processors since about 2013) instead of the build machine's own, and the loader refuses a processor without them with a sentence. Left to itself whisper.cpp compiles for the machine that builds it, so an installer from a CI runner would stop an older computer with an illegal instruction.
8. **What exists is used; only the glue is written** (the owner, 26 November 2026: "you can just use a real transcribing open source system that already exists, like voxtype or something. no need to actually build one"). The recognition is whisper.cpp, the capture `cpal`, the resampling `rubato` with a wrapper adapted from voxtype (MIT, its notice kept in `NOTICE` and `crates/boopis-dictation/LICENSE-voxtype`). voxtype itself (the same engine and crates, a Linux daemon with no Windows build and no library) cannot be a dependency or be shipped as it is, and nothing is shelled out to: the mic works from the app alone. The crate's README lists what is reused and what is written.
9. **Licences.** `cpal` is Apache-2.0, `rubato` MIT or Apache-2.0 and whisper.cpp is MIT, all on the list of `docs/STANDARDS.md` section 5. `whisper-rs` and `whisper-rs-sys`, the bindings, are under the **Unlicense**, a public-domain dedication with a permissive fallback, which that list does not name: this record admits it for these two crates. The model's weights are OpenAI's Whisper under MIT; boopis does not distribute them.

**Alternatives considered.**
- *The web view's microphone* (`getUserMedia`, a worklet, samples sent to the host): three engines to make behave alike, a permission prompt boopis does not control on Linux, and audio in the page, where a mod's script also runs.
- *A cloud transcription API*: needs a key or an account, sends the person's voice off the computer, and fails offline. Refused outright.
- *The Web Speech API*: absent in WebKitGTK, and a cloud service where it exists.
- *Bundling the model*: 57 MB more in every installer for a button many will never press, and a larger model would multiply it.
- *A separate process for capture and transcription*: more isolation, and a second binary, a protocol and a lifecycle. The crate boundary plus the source guard is the lighter version of the same rule; it can become a process later without changing the UI's seam.
- *The system's own speech recognisers* (SFSpeechRecognizer, Windows Speech): none on Linux, three behaviours, and on macOS a service that may leave the device.

**Consequences.**
- The first press fetches 57 MB (the composer says so, with progress); every press after it works offline.
- The app links ALSA's library on Linux (`alsa-lib` is a dependency of the Arch package; an AppImage takes the system's `libasound.so.2`, which the AppImage tools never bundle) and compiles whisper.cpp in every build that compiles the host: CMake, a C++ compiler and libclang, and on Linux `libasound2-dev`, in every CI job that builds it.
- The model is in memory (about 150 MB) only around a dictation: it is loaded on the first one, on its own thread, and dropped 2 minutes after the last. Nothing is loaded at start.
- A person who denied the microphone, or whose system has none, reads a sentence that says what to do (`no-microphone`, `permission-denied`); macOS asks once, in the app's name, with the sentence in `packaging/macos/Info.plist`, and the host reads the system's own authorization status (AVFoundation, through the `objc2-av-foundation` bindings, MIT) instead of guessing from silence: a question nobody has answered yet is waited for, never reported as a refusal.
- Quality is the `base` model's: good for clear speech in the languages the owner writes, weaker on names, code words and noise. A larger model is a row in the table and a setting.
- What is proven is that a recording becomes the right words through the whole pipeline (CI's `dictation` job, `crates/boopis-dictation/tests/speech.rs`); a real microphone, and each system's permission prompt, are tried by hand (`docs/RELEASING.md`, "Dictation").

## ADR-0060 The rules engine runs in the plugin's gate, for every tool, with its own reviewer (proposed, 23 November 2026)
**Status.** Proposed (w31 foundations; spec `docs/specs/rules-engine.md`).

**Context.**
- Owner decision 10 (23 November 2026): one plain-language rules list in Settings for every bot, defaults for dangerous actions pre-filled and removable, anything uncovered runs, a pattern pre-filter plus an AI reviewer, fail closed; the card names the rule and offers Allow once, Always allow, Deny, Allow all this turn. The owner's answers to the plan (same day): the per-bot Allow/Ask/Block rows of w30/governed-bots stay on top; the reviewer is the cheapest connected model, changeable; no default caps.
- Read in the engine (v0.23.2), not patched: its `smart` reviewer judges only shell commands its own detection flagged and takes operator policy as one prompt string (`tools/approval_smart.py`); plugin cards never pass through it (`tools/approval.py`, `_run_approval_gate`); `pre_tool_call` sees every tool call, receives `turn_id`, may return `approve` with a `rule_key`, and fails closed on error and timeout (`hermes_cli/plugins_dispatch.py`); plugins have LLM access through `ctx.llm` and may register their own auxiliary task (`agent/plugin_llm.py`, on the public plugin API list); `approvals.mode: off`, yolo and approving cron or unattended modes approve plugin cards without a person.

**Decision.**
1. **The rules engine is a step of the plugin's one permission function** (`policy.check`, inside `pre_tool_call`), for every tool of every bot: terminal, code, files, MCP and connector writes, messaging, browser, computer use. Not the engine's smart mode, which cannot judge per rule, cannot see non-shell tools, and would not show the owner which rule matched.
2. **Order:** host protections, the existing hard policy, per-bot Block, exceptions, global rule match (ask), per-bot Ask, then run. A per-bot Allow never switches a global rule off; an exception does.
3. **Pre-filter** for unedited default rules only, exact for structured calls (a miss means the rule does not apply) and a hint for opaque ones; **reviewer** for the rest, through `ctx.llm.complete_structured(task="boopis_reviewer")`, trusted rules in the system prompt, the action as delimited untrusted input, one verdict per rule id. A failure, timeout or wrong route holds the action at a card; where nobody can answer, it is refused and the owner notified.
4. **The card is the engine's approval gate.** "Allow all this turn" is the engine's `session` answer on a turn-scoped rule key; "Always allow" answers `once` and drafts a narrow exception the owner edits; the engine's `always` is never sent for these cards.
5. **`rules.json` is written by the host only** (Tauri commands from the window); the plugin reads it. The reviewer is the cheapest priced connected model by a fixed standard check, or the owner's pick.
6. `approvals.mode` stays as the owner has it (`smart` or `manual`); `off`, yolo and approving cron or unattended modes are refused for bot profiles (ADR-0062).
7. w30/governed-bots's tiers become per-bot rows whose default is "follow the rules list"; boopis-written tiers and caps are cleared once.

**Alternatives weighed.**
- *Feed the rules to the engine's smart mode* (`approvals.smart_policy`): shell-only, no rule named on the card, and its own decisions are not the owner's rules.
- *Reviewer on the bot's own model*: costlier, and a bot's model is the one the action came from.
- *Only deterministic rules*: the owner asked for plain language.

**Consequences.**
- One reviewer call at most per tool call that a rule's kinds cover and the pre-filter did not decide; cached per identical action. Latency budget p95 4 s, timeout 8 s.
- The engine's hardline runs after the plugin's card (inside the tool), so a hardline command can show a card and still be blocked.
- Room turns and kanban workers: whether their cards reach a person is to be verified on a live engine; behaviour is held where a person can answer, refused and notified where not.
- A scheduled run's refused step is parked as an approval card and re-run on approval, in a run that resumes the scheduled session with a one-time grant for that exact call (owner decision, 23 November 2026; spec section 8.3).

## ADR-0062 B47: host protections, and approvals answered only from an owner surface (proposed, 23 November 2026)
**Status.** Proposed (w31 foundations; specs `docs/specs/host-protections.md`, `docs/specs/approval-surfaces.md`). Changes part of ADR-0045 ("once or deny only" from outside the window).

**Context.**
- B47 (verified in source): a bot with `terminal` can read the Local API token and answer approvals, including its own. w30/governed-bots denies the token read and refuses answer words in a bot's command lines. Still open: the engine's control socket (it mints tickets for any process of the owner), speaking as the owner through the Local API's `say`, editing the files that hold a bot's rules or the engine's `approvals.mode`, and owner-only CLI commands.
- Owner decision 10: B47 and no self-approval are host protections, not rules. Bots run as the owner's user, so none of this is a sandbox.

**Decision.**
1. **Plugin, every session:** denied reads add `client-endpoint`, `gateway.sock` with its pointer and target, `host-ops.sock`, `activity.sock` and `activity.json`.
2. **Plugin, bot sessions:** governance files (`rules.json`, `bot.json`, budgets, the engine's `config.yaml`, the plugin's installed copy, audit and plan files) cannot be written by any tool; more denied command words (the control socket, the Local API's say routes, owner-only CLI commands, engine settings that silence cards).
3. **Host, Local API:** an answer or a message in the owner's voice (`approvals`, `say`, `retry`, room `say`) is refused when any process holding the client's end of the connection descends from the recorded gateway, was started with the per-launch `BOOPIS_ENGINE_LAUNCH` marker, or (Linux) sits in the gateway's own cgroup; and when the peer cannot be identified. Linux: `/proc/net/tcp` inode, `/proc/<pid>/fd`, `/proc/<pid>/stat`. macOS: `proc_pidfdinfo` socket info, `proc_pidinfo`. Windows: `GetExtendedTcpTable` gives the pid, but the gateway's pid is unknown there, so owner-voice routes are refused on Windows until it is known. Stops and reads stay open.
4. **Owner surface:** an approval is answered from the window, from a Local API client that passed 3, or from a chat platform the engine bridges with `approvals.approvers: []` for bot profiles; never from a bot's tool, a host-ops verb or a plugin RPC. From the Local API: `once`, `deny`, `session` (bounded to the turn on boopis cards), and `always` on a boopis card answers `once` and saves the exception disabled, for the owner to finish in the window.
5. **Owner-only commands** (`boopis team apply`, `undo`) refuse a bot caller; plugin RPCs that loosen tiers or budgets need a one-time owner grant redeemed over host-ops where it exists.
6. `approvals.mode: off` and approving cron or unattended modes in a bot profile are a problem on the bot, and cards it would need are refused.

**Consequences.**
- Said plainly in `docs/LOCAL-API.md`: a program that double-forks, clears its environment and leaves the gateway's cgroup passes check 3; reading the token is denied but can be built. Defence in depth.
- Follow-ups: per-client tokens (reverses ADR-0045's one-token consequence; the owner's call), an engine veto hook carrying who answered (an answer through a ticket minted at the control socket is invisible to the host today), the gateway's pid on Windows.

## ADR-0064 Feedforward reads the draft in the plugin, with the cheapest model of the answering provider, and its answers ride the next user message (proposed, 23 November 2026)
**Status.** Proposed (w31; spec `docs/specs/feedforward.md`). The owner's decisions (23 November 2026): on by default and shown live in first run; the reader is the cheapest fast model of the same provider the message goes to; it runs in sessions, bot chats and rooms, each switchable, with per-bot and per-room overrides; subscriptions may be read on if fast enough; everything the "Will assume" row shows travels, the person's picks marked (the last two are defaults).

**Context.**
- Liu Xingyu's demo: while the person types, the agent marks ambiguous words, missing parameters and assumptions, and the person fills them before sending. In boopis the composer, its marks and its menus exist, but the live provider feeds them the mock's fixed pattern catalogue behind a preview flag (`host/live-provider.ts`, `core/settings.ts` `readFlag`).
- Read in the engine (v0.23.2), not patched: plugins call a model with a JSON schema through `ctx.llm.complete_structured` and may route through an auxiliary task they registered (`agent/plugin_llm.py`); plugin RPCs run off the loop on an unbounded pool and cannot be cancelled by the client (`gateway/session_plugin_rpc.py`); `pre_llm_call` context is appended to the turn's user message, never the system prompt, and the sent bytes are persisted and replayed (`agent/turn_context.py`). The gateway session is created at the first send, so the first draft has no session.

**Decision.**
1. **The read is a plugin RPC**, `plugin.boopis.feedforward.read {session_id?, draft_id, rev, draft, cursor, prior, context}`, returning marks (`text`, UTF-16 `at`, `kind`, `reading`, `options`, `guess`, `confidence`) and assumptions. The model names a mark's text and occurrence; the plugin computes the offsets.
2. **Staleness by revisions on both sides**: the UI keeps one read in flight per composer and drops answers older than the last applied; the plugin answers an older `rev` as `stale` with no model call and runs one call per draft at a time. Marks are re-anchored on the live text between reads.
3. **The reader is the cheapest fast, priced, non-heavy model of the same provider the message goes to**, by the reviewer's chooser (one implementation, shared with ADR-0060), through the plugin's own auxiliary task; a route measured too slow is skipped, and with none left there are no marks. A subscription may be the reader. Not frontier-bound: a read does no governed work. Every read runs in the root profile and its cost is the person's.
4. **Fail quiet**: no reader, an error or a timeout gives no marks and never delays or blocks sending. Feedforward is advice, not a permission, policy or gate check.
5. **Cost on the ledger**: `usage.recorded` with `purpose: "feedforward"` in the session's ledger, or, before the session exists, in a monthly aside ledger in contraprova's format.
6. **The answers ride the next user message**: `feedforward.commit` arms the session's next turn (as `mode.once` does), and `pre_llm_call` returns a fixed `<boopis-readings v="1">` block after the typed text. The system prompt, toolsets and skills never change (invariant 4). Each travelled reading is a `feedforward.set` ledger event.
7. **Smart keeps the start-tier pick** (ADR-0032); the reading's level is one more signal, and the person's choice beats both.
8. **Everywhere, switchable:** sessions, bot chats and rooms, with a global switch, one per context and a per-bot and per-room override. In a room one read is made with the provider of the members the message reaches first; the commit is stored by the root plugin and each member's plugin copy adds the block on the first round only.

**Alternatives weighed.**
- *Keep patterns in the UI*: what exists; cannot read meaning, and invents nothing the model would actually ask.
- *The reader in the UI calling a provider*: the UI holds no keys and no price book, and the ledger is the plugin's.
- *Answers written into the message text*: changes the person's words in the transcript.
- *The global cheapest model*: cheaper, but sends a draft to a lab the message is not going to; the owner chose the same provider.

**Consequences.**
- The mock catalogue leaves the live path; the preview flag goes; a setting, on by default, replaces it; first run gains a "Try it" step that is live with a model and a labelled recording without one.
- At most one read in flight and one waiting per composer; a hard timeout of 5 s.
- `docs/PROTOCOL.md`'s `feedforward.preview` and `feedforward.set` are replaced by `feedforward.read` and `feedforward.commit`.

## ADR-0065 In sessions, blanks wait inline for a while through a plugin tool, then the agent goes on with its guess; bots ask only through approvals, with no time limit (proposed, 23 November 2026)
**Status.** Proposed (w31; spec `docs/specs/blanks-inline.md`). The rules are the owner's (23 November 2026): the answer must reach the agent inside its own reply, with no double output; a blank waits for a while, not forever, then the agent goes on with its best guess and the question stays answerable; **blanks are for sessions only, and bots have none, not even as an option**: a bot asks only where the owner set it up to ask (rules and its rows), as an approval card, and that ask has no time limit ("If it's asking you something ... it's because you made it so it asks whenever that happens, so it should ask"). Defaults and looks as design system v7 section 17.1: 30 s, 60 s (default), 2 min; "(my guess)"; one shared card for a lapsed blank and a bot's approval.

**Context.**
- Today a blank does not block: the cell goes on, the turn ends, and the answer is handed to `ctx.inject_message` as an unlabelled new user turn, which the model answers with a second reply.
- Read in the engine (v0.23.2), not patched: a plugin tool runs under the generic tool deadline of 420 s (`agent/tool_executor.py`; `ctx.register_tool` cannot declare a longer one); an interrupted tool is abandoned after 3 s and `on_session_end` fires for the interrupted turn. The engine's `clarify` returns an answer in the same turn and waits per profile, but its timeout result carries no guess (`tools/clarify_tool.py`), and the engine removes it from room member turns, cron runs and delegated children. An approval card expires after `approvals.timeout` (300 s by default, clamped to `MAX_SAFE_TIMEOUT_S`), and its wait is excluded from the tool deadline. A bot's toolsets are applied once per bot (ADR-0048).

**Decision.**
1. **In sessions, a blank is the plugin's `leave_blank`** (toolset `boopis_blanks`, root profile and governed sessions only), with a required `guess` per question. It blocks for the session's wait; an answer in time is its result, so the agent goes on in the same reply.
2. **With no answer in time it returns `no_answer_yet` with the guess** and tells the agent to go on, mention the assumption once and not ask again. The reply shows the guess marked "(my guess)"; the question stays as the shared v7 card under the reply.
3. **The wait:** Settings > General > Sessions > "Wait for my answer", 30 s, 60 s (default), 2 min, which is also the root profile's `agent.clarify_timeout`; never unlimited. The engine's `clarify` is off in the root profile, so there is one way to ask.
4. **A late answer is one labelled correction:** nothing when it equals the guess; otherwise one message starting "[Correction to your guess]", held until the current turn ends and merged with other late answers, submitted by the client as the person's message; not sent when superseded, undone, expired (24 h) or the session is gone. The `inject_message` path is removed.
5. **Bots have no blanks and no `clarify`.** `clarify` moves to `bot-toolsets.json`'s off list and is turned off once for every existing bot (a version of ADR-0048's once-per-bot record); neither it nor `boopis_blanks` can be switched on for a bot (settings, `bots.toolsets`, team files), and the plugin refuses both in a bot's session. A bot asks only through the rules engine and its rows, as an approval card, rendered in the app with the same shared v7 card (no countdown, no guess).
6. **A bot's approval has no time limit:** the host writes `approvals.timeout` = the engine's maximum into every bot profile. Where nobody can answer (scheduled runs), the step is refused for now and left as the shared approval card; approving it re-runs that step in a run that resumes the scheduled run's session, with a one-time grant for that exact call (`rules-engine.md` 8.3; owner decision).
7. **A lapsed session question stays answerable for 24 hours** (owner decision, a default). **Next wave:** `ask` and `request_input` follow the same rule (sessions wait with the same timer, bots get approval cards with no limit), and credentials and secrets still never reach the agent.
8. Blanks stay in contraprova's vocabulary (`blank.opened`, `blank.filled`, `blank.lapsed`) with extra fields.

**Alternatives weighed.**
- *The engine's `clarify` for sessions*: its lapse has no guess, and it is absent from governed sessions.
- *Blanks for bots, waiting off by default*: rejected by the owner; a bot asks only where the owner decided it must.
- *Keep injecting the answer*: the double output the owner rejected.

**Consequences.**
- One reply per message in sessions, proven by end-to-end tests that count submits, stored rows, completions and model requests; a late different answer costs one visibly labelled turn.
- ADR-0048 changes: `clarify` is off for every bot and cannot be turned on; a team file's list loses it on import.
- `approval-surfaces.md`'s "expired after 300 s" no longer applies to bots' cards.
