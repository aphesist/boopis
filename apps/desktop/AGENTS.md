# AGENTS.md: apps/desktop

The desktop app is a Tauri host (`src-tauri/`, Rust) and a UI (`ui/`, TypeScript, Vite, no framework). This file has two halves: **the host half** (`src-tauri/`, next), then **the UI half** (`ui/`).

# The host half: `src-tauri/`

## Job
The host is the **machine authority** of the three-authority model (`docs/ARCHITECTURE.md` section 1). It owns the Hermes lifecycle, the gateway connection, the OS keychain, windows, notifications and folder pickers, and it serves the UI. It does not render, and it does not decide any work (sessions, tools, governance and the ledger are the backend's). Crate `boopis-host`, library `boopis_host`, binary `boopis`, identifier `dev.aphesist.boopis`.

## Authority boundaries (each one is a rule)
- **The webview never receives a ticket, a token or a secret.** It holds a connection id. Tickets are single-use, minted per connect, and live inside `hermes::attach` types that are not `Serialize` and print `<redacted>`. There is **no command that returns a secret**: `secret_set`, `secret_delete` and `secret_exists` only.
- **The UI never opens a socket.** A browser WebSocket always sends `Origin`, which the gateway refuses; the host dials with **no `Origin`** and the ticket subprotocols (`hermes-gateway-v1`, `hermes-gateway-ticket.<ticket>`), on loopback only (`require_loopback`).
- **Frames are validated, never altered.** Shape (JSON-RPC 2.0) and size (`Limits`: 32 MiB in, 8 MiB out) are checked on the envelope only. The one rewrite is the top-level `id` of a UI request, so windows cannot collide; `params` and `result` are forwarded byte for byte (`rewrite_id` copies raw members).
- **Every command validates its input as untrusted** and fails with `{code, message}` (`error.rs`; `hx.engine.unavailable`, `hx.engine.incompatible`, `hx.config.invalid`, `hx.invalid_params`, and the host's own `hx.host.*` and `hx.secrets.*`). Nothing is fabricated: an unknown version stays unknown.
- **Capabilities list exactly the commands used**: `build.rs` declares them, `capabilities/main.json` allows them, `lib.rs` registers them, and the test `commands_match_the_capability` keeps the three lists equal. Plugins (store, notification, dialog, opener) are called from Rust only; none of their JS permissions are granted.
- **CSP** (`tauri.conf.json`): `default-src 'none'`, scripts `'self'`, `connect-src ipc: http://ipc.localhost` (Tauri IPC only), fonts bundled (`@fontsource`), no `unsafe-eval`, no remote anything. Styles allow `'unsafe-inline'` because the v6 markup sets `style=` attributes.
- **Fail closed**: a server request nobody can answer is declined (`hx.host.no_ui`), an approval the UI cannot deliver stays pending, `hermes_install` without `consent: true` is refused and with it still runs nothing (it reports the documented installer command). Never run an installer in tests.

## The command line
`run()` reads the arguments before it does anything else (`cli::dispatch`): no argument starts the app as always; `--version` and `doctor` print and exit, with no window, no thread, no logger and none of the renderer's environment changes. A path or link the system hands the app starts it; an option that does not exist is an error (exit 2), not a silent launch.
- `boopis --version` prints the compact logo, the version, the Hermes this build carries (from `runtime.json`) and the loaded WebKitGTK with its origin.
- `boopis doctor` is Settings > General > Diagnostics in a terminal: session type, GPUs, the renderer and GPU decisions with their rules, the frame-rate setting, WebKitGTK, the runtime's status and the data folders. It calls `startup(false)` (the same decisions `run()` applies), `frame_rate::decide`, `webkit::probe`, `runtime::plan_for` and `Source::resolve`; it never applies a variable. The frame rate shows the setting, not the display's rate (that needs the window).
- Started from a terminal with no argument, the app prints one line (logo, version, the renderer and GPU decisions) to standard output, and nothing to a pipe.
- Colour and marks follow `brand::Caps` (`NO_COLOR`, `TERM=dumb`, a pipe, `COLORTERM`, the locale); a pipe gets plain text with no logo glyphs.
- On Windows the release binary is a GUI program and has no console of its own, so these commands print nothing there yet (it needs `AttachConsole`).

## Hermes lifecycle
1. **Discover** (`hermes::discover`): the bundled runtime's launcher when the build carries one (the only Hermes then, in the private home), else `hermes` on `PATH`, then `~/.local/bin`, then Hermes's own places; `hermes --version`; `install-stamp.json` near the install. **`HERMES_HOME` wins, else `~/.hermes`** (Windows: `%LOCALAPPDATA%\hermes`; `HERMES_DATA_DIR_SUFFIX` is honoured). A named profile lives in `<root>/profiles/<name>` (ADR-0006: attach to the active profile by default; a setting switches).
2. **`requires_hermes`** (`>=0.23.2`, from the plugin manifest): an older Hermes is refused (`hx.engine.incompatible`). A Hermes that names no version (a source checkout with no stamp) passes with a warning; the gateway's `runtime.describe` is the real gate.
3. **Ensure once per run** (`hermes gateway ensure --json`). The `code_sha` check: `client_code_sha` against `endpoint.code_sha`; when both exist and differ the gateway outlived an update, so the host runs `hermes gateway stop --yes` and ensures once more. When the running gateway names no code identity (or the identity the install stamp names), the CLI is skipped: a control-socket round trip decides instead.
4. **Attach per connect**: the gateway's control socket (`$HERMES_HOME/gateway.sock`: `identify`, then `session-ticket`, about 2 ms; the home must belong to the socket's peer and not be group- or world-writable), falling back to `hermes gateway attach --json --start` (about 500 ms: a Python start; it also restarts a gateway that idle-exited). Windows uses the CLI route (the control channel is a named pipe).
5. **Link states** (`gateway::reconnect`): `connecting`, `ready`, `degraded`, `incompatible`, as `connection.state` event frames to every window and as the typed `ConnectionStateEvent`. The first retry after a loss is immediate (an idle-exited gateway is restarted by the attach), then 0.4 s doubling to 15 s. `incompatible` parks until the user retries (`hermes_retry`, or connecting again). After a reconnect the host asks `session.events.since {session_id, last_seen, replay_epoch}` for every session it saw events of (the 64 most recent), delivers the missed events, drops live duplicates, and sends `connection.replay_gap` when the buffer was truncated (the UI reloads that transcript).
6. **Handshake** is the host's, once per link: `gateway.ready`, `client.capabilities {server_requests: true}`, `runtime.describe`. A window's own `client.capabilities` and `runtime.describe` are answered from that cache and never reach the gateway.

## The proxy
One link per profile, shared by every window and multiplexed by request id (`gateway::hub`). Events go to every window; a **server request** goes to the window that attached last and is declined when none is attached. A bounded queue per window (`Outbox`): responses and every non-delta frame are never dropped; past 2048 queued frames adjacent `message.delta` frames of one session are merged (text concatenated, order kept) and counted, reported as a `connection.backpressure` frame and in `gateway_stats`; past 16384 that window alone is closed as too slow and its page reloads (it reads its state from the engine again). **Delivery is batched and acknowledged**: the Tauri `Channel` runs one script in the web view per message and never pushes back, so the drain sends a JSON array of up to 256 frames (1 MiB; adjacent deltas of one turn and segment merged on the way) and holds at most 4 unacknowledged batches; the page handles each batch to the end and calls `gateway_ack`. A busy, hidden or stuck page therefore stops taking frames and they wait in the bounded queue (where they merge, and `outbox_peak` shows it) instead of piling up unbounded inside WebKit (wave 24 measured page stalls of up to 8 s while six long replies streamed, and the old per-frame delivery never once filled the queue: `coalesced` stayed 0). A page that loads again (a reload, the watchdog) closes the old page's connections (`on_page_load`). Requests unanswered for 120 s are answered with a timeout error. Pings every 20 s; 75 s of silence is a lost link.

**Measured budgets** (debug build, real gateway from the spike install, `tests/live_gateway.rs`, three runs): attach (control-socket ticket plus WebSocket handshake) 8 to 16 ms (one outlier of 188 ms); first connect of a run about 1 s, which is discovery (`hermes --version`) plus `ensure`; the app warms discovery while the UI loads; proxy overhead per frame, p95: gateway to queue about 0.09 ms, UI to link about 0.08 to 0.4 ms (budget 1 ms); queue to the UI's sink about 0.02 to 0.07 ms in the test (the Tauri Channel's own cost is outside the test).

## The secret channel (host to plugin)
Secrets travel UI to host to keychain (ADR-0020, `docs/FORMS.md` section 3). Hermes reads credentials through a **secret source** (`ctx.register_secret_source`, `agent/secret_sources/base.py`: read-only, startup-time, synchronous, env-var-shaped), and a plugin cannot call Tauri, so the host listens on a local socket (`secrets::channel`, protocol `hx-host-secrets-v1`):
- **Transport**: a Unix socket `host.sock` (mode `0600`) in `$XDG_RUNTIME_DIR/boopis/` (else `<data dir>/boopis/run/`, mode `0700`). A live host is never replaced; a stale socket is. Windows would use a named pipe with a user-only ACL: **not implemented** (`start` says so and the plugin gets no secrets there yet).
- **Who may connect** (`secrets::peer`): the gateway the host started, and nothing else. The kernel's `SO_PEERCRED` names the connecting process and the host admits it only if it is (A) the recorded gateway (same pid, start time and executable; recorded from the pid the kernel reports on the gateway's control socket, and only if the process was started with this run's token in its environment) or (B) the daemon a `gateway ensure|attach --start` call is starting right now (a process started with the token below the `hermes` process the host spawned for that call, while it runs: the gateway reads its secrets as it starts, before the host has seen it; the command line is deliberately not used, as Hermes may retitle its process, and the launcher is matched by pid and start time but **not** by executable, because Hermes's launcher is a shell script that `exec`s Python, so the process the host noted as `sh` is `python` when its daemon asks. Compared by executable, the daemon was refused its first read, and an MCP server that needs a key at start-up failed for good). **A child of the gateway is refused**, which is what a tool the agent runs is. A refused process gets the same answer as a wrong token, and the store is never asked. Linux reads `/proc`; other Unix systems compare the pid only and never meet rule B (so a gateway there is not served at start-up). A gateway the host did not start in this run (an earlier run left it, a systemd unit, the user's own) holds no token and is not served; Hermes then keeps its own `.env`.
- **The token and where it goes**: a per-run 256-bit token (`getrandom`), compared in constant time. It is **written to no file**. The host puts it, with the socket's path, in the environment of the `hermes gateway ensure|attach --start` call that starts the gateway (`BOOPIS_HOST_SECRETS_TOKEN`, `BOOPIS_HOST_SECRETS_SOCKET`, through `Cli::run_launching`; no other `hermes` call gets them), and Hermes builds the daemon's environment from that call's. Hermes passes every variable of the gateway's environment to the children it builds unless its own policy strips it, so the plugin takes both values at load and **removes the token from the process environment** (`hostsecrets.channel.capture_environment`), and its secret source names the token as a bootstrap credential (`default_token_env`), which Hermes's environment policy strips from every child it builds when the source is registered before that policy is imported (checked on 0.23.2: a late registration is not seen, which is why the plugin removes the variable itself). The token can still be read from `/proc/<gateway>/environ` by a same-user process; the peer check is what stops it being used. The token never appears in a log line (`Debug` redacts it). The old `<hermes home>/boopis/host-channel.json` is gone; the plugin's policy still denies reading it.
- **Protocol**: one JSON line in, one out, then close; reads are capped at 8 KiB and 2 s. Request `{"v":1,"token":"...","op":"get"|"has","service":"boopis.<scope>","account":"<name>"}`; reply `{"v":1,"protocol":"hx-host-secrets-v1","ok":true,"value":"..."}` or `{"ok":false,"code":"hx.secrets.not_found"|"hx.secrets.unavailable"|"hx.host.unauthorized"|"hx.invalid_params"|...}`. `has` returns `{"found": bool}`. **There is no write op and no list op**; only the `boopis.` service namespace is reachable (a ref `secret://<scope>/<name>` is service `boopis.<scope>`, account `<name>`).
- **The plugin side** is `plugins/boopis/hostsecrets` (built): Hermes's secret source `boopis_host`, configured as `secrets.boopis_host.{enabled: true, env: {VAR: secret://scope/name}}` (Hermes runs a source only when its section says `enabled: true`). A ref `secret://<scope>/<name>` is service `boopis.<scope>`, account `<name>`, and the variable is derived (`secrets/refs.rs`, data in `crates/hx-proto/secret-refs.json`, tested against both languages). A missing or dead host is `NETWORK` (Hermes keeps its own `.env`), a missing secret a warning, a wrong token `AUTH_FAILED`. It never logs a value or the token. In the cloud (ADR-0019) the same source would read the control plane instead.
- **Keychain**: the `keyring` crate (v4): the **Secret Service** on Linux (GNOME Keyring, or KWallet 6 with its Secret Service enabled), Keychain on macOS, Credential Manager on Windows. With no Secret Service running the error is `hx.secrets.unavailable` with a message naming the fix. Calls run in `spawn_blocking` (a D-Bus round trip). Tests use `MemoryStore` behind the `SecretStore` trait; no secret is ever written to a plaintext file.

## Connectors (docs/CONNECTORS.md, docs/FORMS.md)
Install, test, switch, remove and sign in to MCP servers, through forms. **Hermes owns MCP configuration and tokens; the host drives Hermes's own mechanisms and never writes one of Hermes's files** (`config.yaml`, `.env`, `mcp-tokens/`).
- **What it uses** (`connectors::ops`, behind `McpOps`): the gateway's `mcp.servers.list`, `.status`, `.add`, `.test` and `.oauth.start|poll|cancel` on a short link (`gateway::oneshot::Link::call_rpc` keeps Hermes's refusal code apart from a broken link: 4090 conflict, 4064 not found, 4063 and 4001 rejected become `hx.connectors.*`); the CLI for `hermes config set|get|unset` (the enabled flag, the secret wiring), and `hermes mcp remove` (it also drops an OAuth server's tokens; `mcp.servers.remove` only edits the configuration, so it is the fallback).
- **What Hermes does not offer**: `config.set` over the gateway takes only display and session keys (so the enabled flag and the secret wiring go through the CLI, as setup does); the gateway's removal leaves OAuth tokens behind; there is no device-flow method (`oauth.flow: device` only runs from the CLI); `reload.mcp` resets the prompt cache, so the host never calls it (open sessions keep their tools, new ones use the change); a key saved after the gateway started is read only when it next starts, so an install that gives a key restarts it (`Supervisor::restart`: stop, wait until the control socket is quiet, ensure). Hermes's MCP client needs the `mcp` Python SDK, which the shipped runtime carries (default extras `anthropic,mcp,uvloop`).
- **OAuth is Hermes's own flow, not the host's.** Hermes runs discovery, registration, PKCE and the exchange, and a one-shot loopback listener (`127.0.0.1`, random port, the `state` compared in constant time, one callback, closed with the flow), and writes the tokens to its own store. The host opens the page Hermes names after `validate::auth_url` (https, no credentials, a `state`, and a loopback `redirect_uri` with a port when it names one), polls (`Limits::connector_poll_every`), and cancels on request or at `Limits::connector_signin_timeout`. The host holds no redirect listener, no code and no token: a second implementation would be a second place for them to leak (invariant 7). `client_redirect_uri` is Hermes's seam for a gateway on another machine (the Remote endpoint, which does not exist yet); the host would then host the loopback and relay the code with `mcp.servers.oauth.callback`.
- **Keys**: `connector_install` stores each in the keychain as `secret://connector.<name>/<field>` and the config holds `${BOOPIS_...}` (`SecretRef::env_name`), wired with `secrets.boopis_host.env.<VAR>` and `secrets.boopis_host.enabled`. A removal reads that wiring back (`config get secrets.boopis_host.env`) to find a connector's keys, so no state file of ours exists. Every message built from Hermes's or a process's words is passed through `engine::scrub` with the values the call handled.
- **A provider's login command** (`connector_login`) takes a **provider id**, never a command: `connectors::logins` maps it to a program and argument vector from the host's own table (`apps/shared/data/logins.json`, reviewed data with sources and dates, read by the UI too; plus a collection entry's own reviewed `login`). A form's schema is written by an agent, a teammate or a mod, so nothing in it may choose what the host runs: `command`/`args` in an `x-signin` are ignored (the card is disabled and says "not one boopis knows"), an id outside the table is `hx.connectors.unknown_login`. The table's entries are still checked by `validate::command`/`args` when it is read, and it is run with `env_clear` plus the allowlist of `hermes::cli` and the browser variables, stdin closed, a timeout and an output cap (`Limits::login_*`), its output cleaned of escape sequences and anything that reads as a credential. `program: "hermes"` is the Hermes the host runs (`McpOps::hermes_program`, with its home). Output shows when it ends, so a login that needs a code read while it runs does not belong in the table. **`claude-code`** is in it (`claude auth login --claudeai`, ADR-0029): `program: "claude"` means the user's own Claude Code, found the way the Claude subscription plugin finds it (`claude::resolve`, not a bare `PATH` name); `--claudeai` is the subscription (the default) and never `--console`, which bills API usage. It was run here with stdin closed and a stand-in browser: it opens the loopback authorize link and accepts the callback without any input (a made-up code reached the token exchange and was refused, exit 1); no account was signed in to. Its printed fallback link is the code-showing one, so a sign-in whose browser never opened waits for a code the host cannot give and ends at the host's timeout. Setup uses it: the Claude form's "Sign in to Claude" (`Form::signin`, provider `claude-code`) and Settings > Models run it through `connector_login`.
- **Restarting Hermes for a key is never silent**: `Engine::install` asks `McpOps::running_turns` (`session.active_list`, any status but `idle`) before it changes anything. None running: it restarts without `--yes` (`Supervisor::restart(home, false)`: Hermes refuses a gateway with live work, answered as `hx.connectors.busy`, and the host then waits). Some running, or Hermes cannot say: the caller must pass `restart` (`now` interrupts, `when_idle` saves everything and a single waiter, `Engine::wait_for_idle`, restarts when `running_turns` says 0, tests each waiting connector and emits `ConnectorRestartEvent`; it gives up after `Limits::restart_wait_max` and says the key is saved); without it `hx.connectors.restart_choice` and nothing is changed. The review (`Engine::review`, async) carries the same facts so the card says them first.
- **Tests**: `connectors::validate` (every refusal), `catalog` (every entry is sound and pinned), `plan` (what is written, the hash), `connectors::tests` (install order and rollback, keys never in a config or a report, removal and keys, plugin-owned servers, the sign-in's ends: approved, refused address, no browser, Hermes's failure, timeout, cancel, one at a time; a provider outside the table is refused and nothing runs, a table entry runs exactly its vector (made-up entries over `printf`, `false`, `sleep`), the restart policy: no turn restarts at once without interrupting, a running turn changes nothing until the user chooses, `now` interrupts, `when_idle` saves then waits and restarts only on an answer that says idle, one waiter for many, giving up, the review's words), `logins` (the shipped table parses, is unique, has the one Claude entry exactly as above and no shell string) and `tests/connectors_live.rs`. Hermes's loopback properties are checked against a real Hermes with the fake authorization server (`tests/connectors_live.rs`): a callback with a forged `state` is answered 400 by Hermes's listener and nothing is exchanged; the host's timeout cancels the flow and the listener's port stops accepting; the same callback sent twice completes once (the second is refused or finds nothing listening) and the authorization server sees one token exchange; the tokens land in Hermes's own store and go with the server on removal. Hermes starts a flow it still counts as open for a moment after a cancel, so the host retries that answer for `Limits::connector_start_wait`.
- UI: `host/connectors-bridge.ts` (the typed commands as an interface), `host/connectors.ts` (Settings > Connectors; the list, the three forms, remove), `host/forms.ts` `fromConnectorForm` and `connectorSigninForm`, `host/live/forms.ts` `hostSignin` (an agent's `signin` form), `host/live/details.ts` (the session details panel's switch and Sign in), `host/logins.ts` (the table the card checks a sign-in against), `host/connectors-notice.ts` (the notice of a restart that waited for idle sessions). Tests: `host/connectors.test.ts`, `host/live/signin.test.ts`, `live-sources.test.ts`, `modules/cards/form.test.ts`.

## First-run setup
`setup_check` (read-only) and `setup_advance` drive `setup::Setup`. Every call recomputes the steps from reality, so it resumes after an interruption and running it again changes nothing that is already right; `<home>/boopis/setup.json` (versioned, atomic) holds only decisions and what is pending, never a secret.
0. **The runtime** (a build that carries one, ADR-0023; `BOOPIS_HERMES=existing` skips it): `runtime.json` is read, the archive hashed before anything is extracted (a mismatch extracts nothing) and again while it extracts into `<app data>/runtime/.unpack-*` (bounded by `unpacked_size` and `entries` of `runtime.json` plus a margin; a device node, a FIFO or a setuid bit never reaches the disk), moved into `runtime/<version>-<sha8>/` with one rename; the private `HERMES_HOME` is `<app data>/engine` (ADR-0031; `migrate::engine_home` moved the former `hermes-home` once), and Hermes's own update check is switched off (`updates.check: false` through `hermes config set`). While it runs the host pushes `setup-progress` events (`SetupProgress`: `step`, `phase` `verify` or `unpack`, `read` and `total` in bytes of the archive, the manifest's own size; each pass runs 0 to `total`, nothing is estimated and an already unpacked runtime reports nothing), which the first-run view draws as the design system's dot progress. A failure is a blocked step with a stable code (`hx.setup.runtime_*`) and the reason; setup resumes on the next call. **Retry** is that same call: every blocked step gets a Retry in the first-run view, which calls `setup_advance` with no answer; steps are recomputed from reality, so what is done stays done and the stopped one runs again, with no restart of the app. `setup_check` is `needed` while the runtime is not unpacked, so an app update that carries a new Hermes runs this step again. Older runtimes are removed (`runtime::remove_old`) only at the end, after the gateway restarted on the new one, and only directories with the host's marker file. The bundled Hermes is run with no `HERMES_*` or `UV_*` variable from the user's environment and never reads `~/.hermes`.

## The renderer (ADR-0024)
WebKitGTK reads its renderer switches when the web view is created, so `run()` decides first, before any thread (`renderer::probe`, `decide`, `apply`). In WebKitGTK 2.44 to 2.52, `WEBKIT_DISABLE_DMABUF_RENDERER=1` means acceleration policy `never` (no GL, the CPU paints every frame; `webkit://gpu` shows it), `WEBKIT_DMABUF_RENDERER_FORCE_SHM=1` keeps GL and copies frames through shared memory. The automatic rule touches only NVIDIA proprietary as the display GPU on X11 (`FORCE_SHM`); everything else is `BOOPIS_RENDERER=auto|default|shm|cpu|nosync|software`, and a switch already in the environment wins. The decision table is unit-tested; the choice is logged at startup. Settings > General > Diagnostics (desktop only) copies `renderer_report` and opens `webkit://gpu` (`renderer_open_gpu_page`, a window with no IPC). The report also carries the runtime WebKitGTK version and origin (bundled or system), the display's refresh rate, whether WebKit's 60 fps preference is off, the power profile, the GPU choice and its rule, and the page's WebGL renderer; Measure frames reports the measured rate against the display's (`118 of 120 fps, p99 9.1 ms`). `app_restart` applies a GPU choice (it is read at start).

**Frame rate and GPU (ADR-0025).** Both are decided from the environment before any thread: `gpu::probe/plan/apply` runs first in `run()`, then `renderer`. The host's `unsafe` is three small blocks, each with a SAFETY note: `renderer::apply` and `gpu::apply` (`set_var`, before any thread) and the `dlsym` call in `webkit::native`. `BOOPIS_FPS=auto|60|max` lifts `PreferPageRenderingUpdatesNear60FPS` through `webkit::native::Live` (the single `unsafe` block resolves the symbols with `dlsym` and calls them; `webkit::set_feature` checks version >= 2.42, the symbols and the feature's existence first, and reads the value back). `BOOPIS_GPU=auto|integrated|dedicated` (and the saved setting) offloads to the NVIDIA GPU with PRIME render offload; `auto` needs AC power, a bound NVIDIA proprietary driver and WebKitGTK >= 2.54.2. Only variables on the allowlists are taken from switcheroo-control (never an EGL vendor file: ADR-0025), and `busctl` is run by absolute path from a fixed list (`/usr/bin/busctl`, `/bin/busctl`) with an empty environment, never through `PATH`. Test the logic through the traits and pure tables, never with a display. Do not add a blanket workaround: Tauri's own guide says it slows every machine that did not need it.

## Endpoints (ADR-0018 seam)
`trait Endpoint { connect() -> GatewayConn }`. `Local` is done. `Remote {url, token}` and `Cloud {control_plane, session}` are typed and return `hx.engine.unavailable` "not yet supported". Neither the proxy nor the UI knows the kind. A remote token belongs in the keychain, never in settings (`EndpointConfig` redacts it in `Debug`).

## Typed commands and bindings
`tauri-specta` generates `ui/src/host/bindings.ts` from the registry in `lib.rs`. **Never edit it.** The test `bindings_are_fresh` (CI runs it) fails when it is stale; refresh with `HX_UPDATE_BINDINGS=1 cargo test -p boopis-host bindings`. `Frame` and `Json` are typed `unknown` in TypeScript (specta cannot export `serde_json::Value`'s 64-bit numbers); the UI narrows them with Hermes's generated contract.

## What not to do (host)
- Do not add a command that returns a secret, a ticket or a token. Do not log them, in any level.
- Do not build an HTTPS agent without `tls::config()`, and do not put what a transport, a server or a parser said in a message a person reads: say what happened and what to do, and keep the raw words with `error::kept` (Diagnostics and the log). A blocking task's `JoinError` goes through `error::joined`, a sign-in's end event through `error::shown` (ADR-0041).
- Do not put the engine's name in text that reaches the UI (ADR-0031): an error goes through `error::user_message` (`HostError`'s `From` does it), a step or note that may quote the engine through `error::unless_engine`. `engine_words.rs` is the guard.
- Do not send an `Origin` header, dial a non-loopback address from `Local`, or let the UI dial anything.
- Do not alter a frame's `params` or `result`; do not drop a response; do not queue without a bound.
- Do not hold a `std` mutex across an `.await`, block an async worker (use `spawn_blocking`), or `unwrap` outside tests.
- Do not inherit the whole environment into a child: the allowlist is in `hermes::cli`.
- Do not hand-edit `bindings.ts` or `permissions/autogenerated`. Do not put a number in code that belongs in `config::Limits`.
- Commits are the owner's alone (`scripts/setup-hooks.sh`), no co-author lines, nothing that names an agent, a model or a tool.

## Corners and overlays in code
Two rules of the design system are primitives, so a screen cannot get them wrong: nested corners (R-corner-3, R-corner-4, R-corner-5, R-corner-9) and floating surfaces (R-float-1, R-tip-2, R-elev-6). **Never hand-set a radius, an inset or a tooltip offset for something in a corner.**
- **A container** (anything that holds controls or surfaces near its edge) declares only `--r-outer` and `--pad`, from the tokens (`--pad-menu`, `--pad-toast`, `--pad-seg`, `--composer-pad`, ... in `tokens.css`; the `--r-in` it derives then equals that container's `--r-in-*` token, which a unit test checks at every corners setting) (and `--corner-size` when what sits in its corners is not a `--ctl-s` square), and carries `.ui-nest`; the library's own containers (composer box, menu, popover, listbox, tooltip, toast, segmented track) are already in the one rule at the top of `components.css`. A pill declares its real radius (half its height). That rule derives `--r-in` (nested surfaces: `.ui-fit`), `--r-corner`, `--corner-inset` and `--corner-ring` (DESIGN-SYSTEM.md §8.2; `components/corners.ts` is the same arithmetic, tested: where `R − pad` would go under `--r-floor` the inset gives way, and where a control is too small to be as round as `--r-in` it moves in so both curves share a centre).
- **A control in a corner** takes `.ui-corner` (`html.send({corner: true})`, or `class: 'ui-corner'` on a button): its radius, size and focus-ring offset come from the container, so its rest, hover, pressed and disabled fills and its ring stay inside. A row along an edge whose ends are corners is `.ui-corners` (inset from both sides and the bottom; `data-edge="top"` or `"both"`); one control set into a corner on its own is `.ui-corner[data-corner="tr"]` (`tl`, `br`, `bl`) in a `position: relative` container. Do not rely on the page's `box-sizing` (the session view sets `border-box` on everything inside it, which is what put the send half outside the composer): size a corner row by its content, not a fixed height.
- **A squircle-drawn container** exposes the radius it draws as `--r-outer` when it declares none (`squircle.ts`), so its children nest the same way.
- **Overlays** (tooltips, menus, popovers, the card layer's blank) are placed by `components/place.ts` and nowhere else: outside the anchor, `--float-gap` (8) from it on every side and at least `--float-margin` (8) from the window's edge, flipped and shifted to stay in the window; under a modal dialog they mount inside it (R-elev-6). A control's preferred side is `data-tip-pos` on it **or on a container** (`top`, `bottom`, `left`, `right`, with `-start` or `-end` to align to the control's edge instead of centring on it); a container that holds text an overlay must not cover names it in `data-overlay-avoid` (a selector matched inside it), and the overlay moves past it on the same side (R-tip-2: a composer control's tip sits above the composer). The composer does all three: its bar and its actions ask for `top` (centred on the control like every tooltip, R-float-3; the window's margin is all that moves it sideways), and its text and assumptions are avoided. Menus take `place` and `align` as before (`layer.place` is the same primitive).

## Frame cost (WebKitGTK is the target, not Chromium)
The desktop app draws with WebKitGTK; the owner's machine paints on the CPU at 3600x2250 buffer pixels (GTK3 renders a 1.6 scale at 2x). `tests/perf/README.md` has the harness (`pnpm perf:webkit`); the findings that became rules:
- **No `getComputedStyle`, `getBoundingClientRect`, `offset*`, `getClientRects` or `scrollWidth` inside a frame or a layout handler unless the value is needed in that frame, and never between writes.** Read everything, then write. A read after a write forces a style and layout pass over the whole page; the dock's slab path, the clips check and the dock's layout handlers each did it and cost a quarter of a morph. Cache a token you read per frame (`components/shape.ts`), and re-read it on `hx:theme`.
- **No `mask-image`, `filter` or `backdrop-filter` over a large moving area.** The one mask is the scroll area's edge fade (R-scroll-9, `.ui-scroll` with `scroll-edges.ts`'s flags): static while it scrolls, it is redrawn only when the flags or the scroller's size change. A conversation fades with strips of its ground instead (`.ui-scroll--ground`: `.ss-view::after`, `.bt-room::after`), since a mask whose edge moves with the dock's lift costs twice a frame on WebKitGTK; never put a mask on anything resized per frame.
- **Every scroller is a `.ui-scroll`, and every cut edge fades.** Where more lies beyond an edge, its content fades out over `--scroll-fade`; nothing to opt into. A scroller whose foot lies under the composer and the dock is `scrollClass({ ground: true })` and draws the strips itself.
- **Orbs** (`components/orb-runtime.ts`): a resized canvas repaints in the same task (a cleared canvas painted empty is the flicker), ambient orbs update on alternate frames by group (the dock's, and the rest), and the ones outside the dock wait while the dock moves. When the CPU paints, a frame repaints the bounding box of everything that changed once more than ten rectangles did: scattered animating orbs repaint the window between them. Do not add another always-animating thing in a second corner of the window.
- A dock handler that needs the new layout takes it from `hx:layout` (`d.resized` says a window resize), not from `window`'s `resize`.

## Motion (ADR-0025, STANDARDS section 6)
Motion runs at the display's full rate, so what moves must not wait for the main thread. The rules, then where every animation stands.
- **Compositor first.** Animate `transform`, `translate`, `opacity` (and `filter` only where the design needs it). A spring that has a known end is a Web Animation sampled from its closed form with `core/spring.ts` (`springKeyframes`; `springLinear` for a CSS `linear()` easing). Use keyframes, not `linear()`, for anything that must composite on WebKitGTK before 2.54, where `linear()` with points forces main-thread animation. An interrupted spring hands its velocity on from `springAt` (the exact state), never from a layout read.
- **Per-frame JavaScript is only for what follows live input**: the dock's slab outline (a path whose corners depend on its size), magnification under the pointer, a page dragged by touch. It writes transforms and one path, in one rAF, and reads nothing from layout or style.
- **Animated custom properties never inherit.** The shell publishes layout targets as `--hx-*-to`; an element that uses one declares its own `--hx-*: var(--hx-*-to)` and transitions it (`shell.css`). An inherited property animated on a root restyles the whole page every frame.
- **An orb that draws in the worker is never taken out of the page and put back** (WebKitGTK drops its picture until the worker's next commit). The dock's live orbs are connected once in the `.dk-orbs` layer (`modules/dock/layer.ts`) and follow their slot's rect by transform: the slot's FLIP and entrance are played again on the orb with the same keyframes (`engine.ts`), the row's magnification and the roster's scroll are written as one `transform` on its `.dk-op` point, and the layer sits in the Bots page's section so slides and fades take it along. A view draws an empty `data-slot="orb:<id>"`, never an orb. A new place that must show an orb needs a slot, not an `append`. The sidebar keeps its rows' orbs connected by updating them in place (`modules/bots/list.ts`). The lab's `orbs: 'stay'` and `tests/e2e/dock_webkit.py` (lit pixels over each orb) guard it.
- **Orbs draw in a worker where the engine has OffscreenCanvas in workers** (`components/orb-worker/`; `setupOrbs()` in `main.ts` decides once). The page's `<orb-avatar>` is a thin element (attributes, size, visibility, resolved colours); the worker runs the vendored orb2 file as it is against `shim.ts` and applies `orb-runtime`'s frame policy. Anywhere else, or when the worker fails to start, the vendored element draws on the main thread as before; `?orbs=main` forces that. `orb-worker.test.ts` runs the vendored file against the shim and checks the shadow template the page copies.
- Measure with `tests/perf` (its README): frame times at the owner's geometry, the `-load` scenarios (a 30 ms task every 200 ms), `--probe` for main-thread work per frame.

## Names and long names
- **Autoname** (`modules/bots/names.ts`): the curated list is shared data, `apps/shared/data/bot-names.json`, imported by the UI (bundled by Vite, so there is one copy; `scripts/sync-shared-data.sh` copies files into the plugin package and the plugin does not read this one). Availability is derived on every call from the bots the module holds (which the provider keeps current: the Hermes profiles), and the names the provider reserves (`catalog().reserved`: Hermes's `default`), never stored. An archived teammate is renamed out of the way in Hermes, so its name really is free. "Surprise me" is the dice button and alt+R in the name field; an empty name is auto-named on create.
- **Long names** are cut with an ellipsis and shown whole as the tooltip while cut (`modules/bots/clips.ts`, `modules/cards/fit.ts`, the dock's `tipOf`); the accessible name always carries the whole name. Tests use the `long` fixture (`BOT_FIXTURES` in `mock-data.ts`): `createMockProvider({ fixtures: ['long'] })`, or `?fixture=long` in the e2e build only.

## The data seam
Modules read **only** through `DataProvider` (`src/data/provider.ts`): `Watch`/`Feed` streams plus commands. Never import `mock-data.ts` or `mock-provider.ts` from a module, never keep a second copy of data a provider owns, never fabricate a value (an unknown value is `null` and is shown as unknown). The live provider (`src/host/live-provider.ts` and `src/host/live/`: the Hermes gateway and the boopis plugin through the host) implements the same interfaces and serves the whole Sessions section (sessions, the conversation, approvals, blanks, the details panels, the run, diffs, file mentions); the bots and their schedules are Hermes profiles (`src/host/live/bots.ts`: `profiles.*`, `cron.manage` on the teammate's own link, the plugin's `bots.*`; `bots.archived` and `bots.restore` are the archived profiles, `Bot.madeOutside` the ones boopis has no store for), and only the feedforward catalog stays the mock's (`MOCK_SOURCES`), marked Preview. Never show mock content in a live session; a value the sender did not give is shown as unknown. **A governed session is created with `toolsets: ["boopis"]`** (also when its mode is the plugin's default, and when that default could not be read), and a `plugin.boopis.mode.set` that fails is **fatal for that session**: it is closed, never bound, nothing is sent to it, and the error is shown in the conversation (`ensureLive` in `live-provider.ts`). Read `src/data/README.md` before touching anything under `src/data` or any module's data flow.

Intentional differences from v6, all invisible:
- accessible names contain their visible text (WCAG 2.5.3): the session rows say when they ran, the command field and the account button name their words; the avatar's initial is drawn by CSS; a space separates the row's parts and a key's chips in the markup;

- fonts are bundled (`@fontsource`, latin) instead of fetched from Google, because the app runs under a strict CSP;
- the mock's streams persist what v6 lost (a turn typed in a non-first session survives switching away).

## What not to do
- Do not name the engine in anything a person reads (ADR-0031, `docs/BRANDING.md`): say "boopis's engine" or, better, what failed in the user's terms; a teammate is a bot. Show an error with `sentence(e)` (already mapped by the host, or by `GatewayError.fromFrame`), and pass a text that may quote the engine through `unlessEngine` (`host/errors.ts`). A store item's own name is the one exception: wrap it with `storeItem` (`core/engine-words.ts`). `engine-words.test.ts` is the guard.
- Do not redesign, "improve", re-space or re-colour anything. If the design looks wrong, tell the owner; do not change it.
- Do not edit `design/v6/` (the reference). A change that only moves where motion runs (compositor, worker) does not touch it: the look is the same.
- Do not add a framework (no React). Do not add a dependency without an ADR (licences: STANDARDS section 5).
- Do not read `localStorage` directly: go through `core/settings` (wrapped, versioned). Do not use `console` directly: use `core/log`.
- Do not use a control the platform draws (`<select>`, date, colour, number, range, `title=`, a stock checkbox): `ui.select`, `ui.listbox` and `ui.field({ kind: 'model' })` are the choosers; `docs/UI-CONTROLS.md` is the audit and `components/native-controls.test.ts` the guard.
- Do not duplicate a primitive: look in `src/components` first (STANDARDS section 9); two places that need a helper put it in `core/` or `components/`.
- Do not import a component's file or re-draw a kit pattern in a module: import `@boopis/ui`, and extend the kit with a typed variant (`kit.guard.test.ts` fails otherwise).
- Do not hand-edit `src/styles/tokens.json`: `pnpm tokens` generates it from `tokens.css`, and the build checks it.
- Do not make the UI depend on the dock: everything it shows is reachable elsewhere.
- Do not add a global key inside a module: the shell owns global keys (`keymap.ts`); modules handle keys on their own elements and call `preventDefault()`.
- Commits are the owner's alone: `scripts/setup-hooks.sh` once, no co-author lines, nothing that names an agent, a model or a tool.
